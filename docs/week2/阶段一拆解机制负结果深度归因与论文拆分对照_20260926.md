# 阶段一拆解机制：负结果深度归因，与各论文"拆分"的逐项对照

日期：2026-09-26
性质：**离线综合归因分析**，零模型调用、零新实验。全部数字来自既有冻结报告与论文原文，不产生新的实验结论。
结论标签上限：**APPS custom split 缩小规模机制复现**。

---

## 摘要

**一句话**：阶段一的"拆解—独立实现—组合"之所以是负结果，不是因为它"采样不够"或"代码没写成函数"，而是因为它落在一个**"代价全担、补偿全无"**的位置上——它同时承担了跨函数接口风险、格式税和组合稀疏性，却没有任何训练去学习"怎么拆、怎么协同实现"。

六条要点：

1. **候选池覆盖不足是最直接原因**：困难层 M2a/M2b 的池上限是 `0/20`，连"事后作弊挑最好一份"都无一题可解；简单层拆分反而**降低**了覆盖（M0 15/20 → M2a 10/20 → M2b 7/20）。
2. **接口契约断裂是拆分专属的超额损失**：困难层运行时异常中，接口类异常（NameError/TypeError/RecursionError/EOFError）占 M2a 55%、M2b 61%，而 M0 为 0%。
3. **组合空间不等于完整解法空间**：P5d 中 M2a 的 284 个组合只产出 105 个独特程序；组合出的多数是"局部都像样、整体算法不对"的拼接体。
4. **穷举已排除"采样太稀"**：把已保存实现池的全部组合（M2a 250、M2b 232）穷举后，上限仍为 0/20。
5. **成本效率差一个数量级**：每 10 万输出 token 的池全过题数，简单层 M0 105.2 对 M2a 7.5、M2b 6.0。
6. **论文自身的证据与本地同向**：DecompRL 原文 Table 4 明确报告，**无 RL 的层级推理 pass@1 为 11.0%，低于标准生成的 14.0%**；其收益来自 RL 训练，且要到每题 5 万 token 以上才开始领先——本机预算量级远低于该阈值。

**关键结构判断**：在我们梳理的全部"拆分"文献中，**项目 M2a/M2b 是唯一同时具备"跨候选重组"与"零学习"的配置**。所有其他方法至少放弃其中一项：DecompRL 有重组但有 RL；MoT 无学习但不重组；CodeT 无学习且拆的是测试而非程序。

## 2. 为什么是负结果：七层因果链

以下每层按「观察 → 推断 → 排除的替代解释 → 证据来源」组织。**观察与推断严格分开**。

### 第 1 层：候选池覆盖不足（最直接的原因）

**观察**：困难层 M2a/M2b 池上限 `0/20`；简单层池有全过的题数 M0 15、M1 14、M2a 10、M2b 7；M2a/M2b 在困难层分别有 5 题、7 题**连一个候选都产不出**。

**推断**：拆分把"一次完整算法尝试"替换成"n 次局部实现尝试"。任何一次函数实现失败就让整份分解报废，因此**候选产出率**本身下降。选择器再强也无法从空池里挑出正确答案。

**量化损失**：M2a 35 份有效分解中有 **11 份（31%）**、M2b 中有 **14 份（40%）**因某函数实现全部解析失败而**完全无法组合**。这是此前被"组合数上限"掩盖的协议级损失。

**来源**：失败归因报告结果 2；全组合穷举报告"附带发现"。

### 第 2 层：接口契约断裂（拆分专属的超额损失）

**观察**：困难层"有候选但全为零"的候选中，主导异常类型分布如下：

| 方法 | 候选数 | 算法类（ValueError/IndexError） | 接口类（NameError/TypeError/RecursionError/EOFError） |
| --- | ---: | ---: | ---: |
| M0 | 9 | 9（100%） | 0（0%） |
| M1 | 8 | 6（75%） | 2（25%） |
| M2a | 33 | 15（45%） | **18（55%）** |
| M2b | 46 | 18（39%） | **28（61%）** |

**推断**：这是**拆分独有**的失败模式，不是题目难度造成的（同一层、同一批题，M0 为 0%）。两条直接证据链：

- M2b 的 `TypeError` 达 24 次——JSON schema 协议下模块之间**参数类型约定不一致**；
- P5d 的 oracle 复测中出现 `NameError: name 'dict_scores' is not defined`——某函数使用了另一个函数实现本该提供的**隐式共享状态**，组合器无法发现。

**与论文假设的关系**：DecompRL 的数学前提是"给定分解 D 后各实现**条件独立**"，即组合通过**当且仅当**全部实现正确——此时奖励张量近似为外积（rank-1）。上述 `NameError` 恰是**该假设被违反的直接反例**：某个实现的正确性依赖另一个实现的具体写法。

**必须注明的严谨限制**：我们**没有**在本地做奖励张量的 rank 检验，因此只能说"存在违反条件独立的直接反例"，**不能**说"我们证明了论文假设失效"。论文自身的 rank-1 验证也只在 20 个"至少有一个正奖励"的分解上做了统计（17 例一致，另有 34 个 false positive），样本小且经过筛选。

**来源**：失败归因报告结果 4；P5d §4；DecompRL 原文 §2.1、Appendix J。

### 第 3 层：组合空间 ≠ 完整解法空间（命题层面的错配）

**观察**：P5d 中 M2a 的 284 个组合只产出 **105 个独特程序**（重复 179/284）；P5c 中每题采样 64 个组合，k=8 时池上限仅 `3/20`。

**推断**：理论组合数 `k^n` 是个**误导性的上界**。4 个函数 × 8 个实现 = 4096 组合，但这些组合中的绝大多数不对应任何一个"完整的算法思路"——它们只是把若干局部片段机械地接在一起。

关键对比：

- **直接生成**：每次尝试 = 一次完整的算法求解；
- **模块化**：每次尝试 = 一个局部职责片段；只有把 n 个片段都凑对，才等价于一次完整求解。

**这条解释了为什么"提高 k"在数学上不可能弥补差距**：提高 k 提升的是局部片段的数量，而正确性要求的是**所有片段同时正确**的联合事件。

**来源**：P5d §4；P5c §解释 2。

### 第 4 层：公共测试信号对模块化候选失效（选择层）

**观察**（Interview-25）：

| 方法 | 最高 public 分并列率 |
| --- | ---: |
| M0 | 17/25（0.680） |
| M1 | 16/23（0.696） |
| M2a | **20/20（1.000）** |
| M2b | 16/18（0.889） |

另有：简单层"public 全过但 private 未全过"的候选占比——M0 12%、M1 14%、M2a **26%**、M2b 17%。

**推断**：M2a 在**每一道**有候选的题上都出现最高 public 分并列，说明 public 测试对模块化候选**完全失去区分力**。同时模块化候选更容易"通过公共测试却不真正正确"（26% 对 12%）。这意味着即使池里偶然存在更好的候选，选择阶段也挑不出来。

**来源**：9.18 结果文档 §4.3；失败归因报告结果 5 辅助项。

### 第 5 层：成本效率差一个数量级（预算层）

**观察**：每 10 万输出 token 的"池全过题数"（简单层）：

| M0 | M1 | M2a | M2b |
| ---: | ---: | ---: | ---: |
| **105.2** | 93.2 | 7.5 | 6.0 |

**推断**：约 **14 倍**的效率差距。P5c 的等预算对照进一步给出 2.6 倍的 token 差距（M0@17 解出 8 题对 M2a k=8+A1 解出 3 题，同样约 6.7 万输出 token）。

**与论文的量化对照（本次核对原文）**：DecompRL 原文 Table 1 给出 LiveCodeBench 上"给定 token 预算下的解出率"：

| Token 预算/题 | GRPO | instruct | pass@8 | **DecompRL** |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0.18 | 0.06 | 0.15 | 0.18 |
| 5,000 | 0.29 | 0.16 | 0.27 | 0.18 |
| 10,000 | 0.32 | 0.21 | 0.31 | **0.25** |
| 50,000 | 0.38 | 0.30 | 0.39 | **0.40** |
| 100,000 | 0.40 | 0.33 | 0.41 | **0.44** |
| 500,000 | 0.44 | 0.39 | 0.46 | **0.48** |

**这是本次核对中最重要的发现之一**：DecompRL 在 **1 万 token 时是 0.25，低于所有基线（0.31--0.32）**；要到 **5 万 token 才开始领先**（0.40 对 0.39），10 万/50 万 token 才拉开到 0.44/0.48。论文摘要也明确写"outperforms ... beyond 10^5 tokens per problem"。

**推断**：本机的每题预算量级（P5c 中等层约 3,336 输出 token/题；P5d M2a 约 1,058 输出 token/题）**比论文中 DecompRL 开始占优的 5 万 token 阈值低约 15 倍以上**。也就是说，我们把一个"设计要求高预算"的方法，用在了论文自己承认它不占优的预算区间。

**来源**：失败归因报告结果 5；P5c 表；DecompRL 原文 Table 1、摘要。

### 第 6 层：任务适配性与模型能力阈值（根本原因）

**观察**：

- 困难层 **19/20 题**连 M0 都没有全过候选，且各方法在同题上的候选表现高度一致（同题通过率离散 ≈ 0）；
- Papers 自认：CodeContests 训练集中**只有 65% 的参考解法包含函数**，且"decomposition and function generation are **off-policy** tasks for the model"——即模型本身没有被训练过模块化生成；
- MoT 论文（此前未读，本次首次阅读）报告：**prompt-only 的模块化提示**在 **GPT-4o-mini 与 DeepSeek-R1** 上、8 个基准上取得正收益（Pass@1 58.1%--95.1%，相对其他提示技术平均提升 0.03%--32.85%）。

**推断**：存在一个**模型能力阈值**。同一个"模块化提示"策略：

- 在强模型上（MoT：GPT-4o-mini / DeepSeek-R1）能提升**单次生成**的理解质量；
- 在本地 7B Q4 上（本项目 M2a/M2b）无法产出可用候选。

第二层原因是**任务形态**：APPS 函数式题目的难点常常是"一个整体算法洞察"，而不是"多个可独立验证的阶段"；这类题目拆开后并不产生更简单的子问题。

**必须注明的差异**：MoT 与本项目 M2 **不是同一件事**——MoT 只做"分解推理步骤 + 图组织 + 顺序生成一份代码"，**不产生候选池、不做跨候选重组、不用执行反馈做选择**；它的收益来自"理解提升"，不是"搜索扩展"。因此 MoT 的正收益**不能**用来反驳本项目的负结果，但它有力地说明"模块化本身不是无用的，只是需要配套条件"。

**来源**：失败归因报告结果 1；DecompRL 原文 §6；MoT 原文摘要与 Algorithm 1。

### 第 7 层：缺少学习补偿（方法论层面的结构性原因）

**观察与对照**：把各方法的"承担代价"与"获得补偿"列成表：

| 方法 | 跨候选重组（承担接口风险） | 格式税 | 学习补偿 |
| --- | --- | --- | --- |
| CodePRM | 否 | 低（只多写思路） | 学习过程评分器 + GVR 修正 |
| FunPRM | 否 | 低（提示组织函数） | 学习函数级评分器 + 元奖励校正 |
| DecompRL | **是** | **是** | **RL 训练分解策略与实现策略** |
| MoT | 否 | 中（3 层图 + 框架先行） | 无（prompt-only），但只输出一份程序 |
| Reason-Code | 否 | 低 | 无，但用执行反馈做 UCB 搜索 |
| 本项目 M2a/M2b | **是** | **是** | **无（prompt-only）** |

**推断**：M2a/M2b 在**全部"拆分"文献中占据唯一的"高代价、零补偿"象限**。它承担了重组接口风险和格式税，却没有：
- 学习"哪些题该拆、拆成几段、边界在哪"（DecompRL 的第一步）；
- 学习"怎样写才能与其它函数协同"（DecompRL 的第二步）；
- 用组合后的完整程序奖励把"局部看着合理但拼起来错"的分解压下去。

**论文自身的证据与本地同向**：
- **格式税**：原文 §6 明确写，无 RL 层级推理 pass@1 **掉 3 个百分点**（Qwen 2.5 7B：14.0 → 11.0）；Table 4 同时给出 CWM 32B 的 11.9%；Llama 3.1 8B 在 CodeContest 上从 26.6% 掉到 14.5%。论文结论是"DecompRL's gains come from RL training, not from the hierarchical structure alone"。
- **规模坍缩（size collapse）**：论文报告分解训练会导致分解规模下降，极限退化为单函数，也就等价于整段生成——论文把它视为一种 reward hacking，需要靠降低 logmeanexp 的 β 和交替训练来抑制。**这说明"缩小规模"这条看似更简单的路径，连做了 RL 的论文自己都在与之搏斗。**

**来源**：DecompRL 原文 §6、Table 4、Appendix J；本项目 P5b/P5c/P5d。

## 3. 与各论文"拆分"的逐项对照

### 3.1 三个判别维度

"拆分"这个词在不同论文里指完全不同的操作，必须按三个维度切分：

1. **拆什么**——拆的对象是自然语言思路、完整候选内部的函数、还是可独立实现并可跨候选拼装的模块？
2. **拆完之后是否跨候选重组**——这是本项目所有困难的来源所在。
3. **谁在学习**——不学、学评分、还是学策略？

### 3.2 逐篇对照表

| 方法 | 拆什么 | 拆完是否跨候选重组 | 学习对象 | 收益来源 | 与 M2 的关键差异 |
| --- | --- | --- | --- | --- | --- |
| **CodePRM** | 自然语言**思路步骤**（thought） | **否** | 过程评分器（监督） | 执行反馈 + 学习评分 + GVR 定位修正 | 不做跨候选函数拼装，因此无接口风险 |
| **FunPRM** | **完整候选内部**的函数步骤 | **否** | 函数级评分器 + 元奖励校正 | 函数级过程分数做 Best-of-N 选择 | 函数是**评分单位**，不是独立零件池 |
| **DecompRL** | 可**独立实现**的函数模块 | **是** | 分解策略 + 实现策略（RL，PPO） | 组合搜索把 GPU 成本换成 CPU 评测 | 有 RL 补偿重组代价；且需 ≥5 万 token/题 |
| **MoT** | 推理步骤（3 层 MLR 图） | **否**（单轨迹内 `FinalizeCode` 整合一份程序） | 无（prompt-only） | 结构化推理提升**单次生成**的理解 | 不产生候选池、不做组合搜索，无接口风险 |
| **Reason-Code** | 搜索树的**完整程序节点** | 否 | 无 | 失败后 MCTS + 执行报错驱动的修正 | 节点本身是完整可执行程序，无接口断裂问题 |
| **CodeT / DiffCodeGen** | **测试**（生成测试／差分测试） | 否 | 无 | 用自生成测试替代缺失的公开测试来选择候选 | 拆的是测试，不是程序结构 |
| **LEVER** | 不拆 | 否 | 验证器（从执行结果训练） | 学习"代码 + 执行结果 → 正确概率" | 与本项目的"候选选择"最接近，但不拆解 |
| **ReCode** | 自然语言推理步骤 | 否 | 过程奖励（训练生成器） | 过程奖励进入训练，防止迎合奖励 | 是训练生成器，不是测试时选择 |
| **本项目 M1** | 自然语言计划 | 否 | 无 | 多一个计划步骤 | 同样的"只加提示"路线，同样未产生稳定收益 |
| **本项目 M2a/M2b** | **可独立实现的函数模块** | **是** | **无（prompt-only）** | 假设来自组合搜索 | —— |

### 3.3 四象限定位（本对照的核心结论）

以"是否跨候选重组"和"是否有学习补偿"为两个轴：

| | **有学习补偿** | **无学习补偿** |
| --- | --- | --- |
| **跨候选重组** | **DecompRL**（RL 训练分解与实现策略） | **本项目 M2a/M2b** ← 唯一落在这一格的 |
| **不重组** | CodePRM、FunPRM、LEVER、ReCode | MoT、Reason-Code、CodeT、DiffCodeGen、本项目 M1 |

**这张表就是"为什么论文有正收益而本项目没有"的结构性答案**：论文的"拆分"要么不重组（因此不承担接口风险），要么重组但有学习补偿（因此能把接口错误压下去）。本项目 M2 恰好落在唯一一个"既要重组、又没学习"的位置上。

### 3.4 FunPRM 的消融值不值得注意

FunPRM 原文的消融数据是：去掉 Chain-of-Function 为 `80.1`、去掉元奖励校正为 `80.2`、完整方法为 `80.9`。三个数字的差距都很小，说明**"函数组织 + 函数级评分 + 奖励校正"是一组需要同时具备的条件**，不能拆开单独归因给"拆函数"这个动作。这也是理解后面 P5d F1 结果的关键背景：本项目只搬了"函数组织"，没有搬"函数级评分"和"奖励校正"，因此在 F1 上只得到一个选择层的 +1，池上限没有变化。

### 3.5 一个此前未被使用的对照：MoT

`articles/extra/09_MoT.pdf` 在项目里一直处于"无中文总结、无文档引用、来历待确认"状态。本次首次阅读，其价值在于：

- 它是**最接近本项目 M2 动机的 prompt-only 模块化工作**（都主张"把复杂编程问题分解成更小、独立可解的模块"）；
- 它报告了**正收益**，且使用了与我们相同的论证语言（"monolithic reasoning structure 限制了分解能力"）；
- 但它的收益机制与本项目完全不同：Algorithm 1 显示它做的是"生成 3 层 MLR 图 → 由高层节点生成代码框架（函数名/签名/接口）→ 填充细节节点 → `FinalizeCode` 整合为**一份**输出"，**没有候选池、没有跨候选组合、没有执行反馈驱动的选择**；
- 它使用的模型是 GPT-4o-mini 与 DeepSeek-R1，远强于本地 7B Q4。

**因此 MoT 提供了"模型能力阈值"这一层解释的外部支持**：同样的模块化主张，在强模型上通过"提升单次生成的理解质量"获得收益；在本地 7B 上，即便是更弱的"只拆不重组"版本（本项目 M1、top-down 阶段 1/1b/1c）也没有通过门槛。

## 4. 不能推出的结论

- **不能说"函数拆分没用"**：MoT 在强模型上、FunPRM 在函数级评分下、DecompRL 在训练后都有正收益。本项目的负结果只覆盖"本地 7B + 当前提示 + prompt-only + 本机预算"这一格。
- **不能说"本项目复现了 DecompRL 的失败"**：本项目从未做 RL 训练，只实现了论文的第一步（prompt-only 的动作空间）。
- **不能说"论文的收益只是因为模型更大"**：差异同时来自训练机制、数据规模、预算区间和任务选型，这些因素在本样本中无法分离。
- **不能说"我们证明了条件独立假设失效"**：我们只有 `NameError` 这类直接反例，没有做奖励张量的 rank 检验。
- **不能把阶段一的负结果外推到 RL 之后**：论文恰恰报告了"训练前为负、训练后为正"的同向模式。
- **不能把 `3/20` 对 `8/20`、`105.2` 对 `7.5` 写成论文级统计结论**：均为 APPS custom split、单 seed、20 题规模上的机制证据。
