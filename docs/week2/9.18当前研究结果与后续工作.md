# 当前研究结果与后续工作

更新时间：2026-09-18

## 1. 研究问题

本研究要回答的问题是：

> 在本机 8GB 显存、Qwen2.5-Coder 7B、本地 Ollama 推理和有限执行预算下，先把编程题拆成多个函数，再分别生成函数实现，是否比直接生成完整程序更可靠？

这里研究的是 DecompRL 的核心机制原型，不是论文中大规模 RL 训练的完整复现。当前所有 M2 实验都是 prompt-only modular generation，不能称为已经完成 DecompRL 训练。

## 2. 已完成工作

已完成 P0--P5：

1. 固定了 Introductory development20/holdout30 的题目切分和 hash。
2. 实现了 M0、M1、M2a、M2b 四种生成方法。
3. 实现了 JSON/skeleton 分解验证、DAG 检查、AST 拼接、代码 hash、候选去重和断点恢复。
4. 固定 public-only candidate selection；private 测试只在选择冻结后执行。
5. 加入每测试 10 秒、每候选每个 split 10 秒的双层预算。
6. 修复了候选程序启动子进程后超时无法退出的问题：超时会终止整个进程树。
7. 完成了 10 道题的盲评分和人工分解实验。
8. 获取并审计 APPS train 的 Interview-30 数据，预先筛出 25 道函数题用于模块化比较。
9. 完成 P5 的候选池 oracle、pool solve@k、public tie rate、paired bootstrap 和失败边界分析。

## 3. 方法定义

| 方法 | 做法 |
| --- | --- |
| M0 | 直接生成一个完整程序 |
| M1 | 先生成文字计划，再生成一个完整程序 |
| M2a | 输出 Python skeleton 分解，再分别实现函数并组合 |
| M2b | 输出 JSON 分解，再分别实现函数并组合 |

所有正式结果使用 Qwen2.5-Coder 7B、seed 42。M0/M1 每题生成 2 个完整程序；M2a/M2b 每题生成 2 份分解、每个函数 2 个实现，每份分解最多取 8 个组合。所有方法均记录模型 token、调用数、测试执行数和时间。

## 4. 实验结果

### 4.1 Introductory development20

| 方法 | 有候选 | Selected private 全通过 | 私有测试通过数 |
| --- | ---: | ---: | ---: |
| M0 直接生成 | 20/20 | 10/20 | 51/82 |
| M1 计划后生成 | 20/20 | 13/20 | 58/82 |
| M2a skeleton | 19/20 | 12/20 | 50/79 |
| M2b JSON | 18/20 | 7/20 | 42/75 |

这批题只能作为机制 smoke。它显示 M1 在该切片上较强，但不能单独证明计划式生成稳定优于直接生成。

### 4.2 Interview function25

Interview-30 一共 30 道题，其中 25 道是函数式 starter，5 道是标准输入输出题。M2 的 AST 协议要求可调用函数入口，因此 5 道 stdin/stdout 题在看到实验结果前按协议排除；M0/M1 在分析时也过滤到同一 25 道题。数据文件和 hash 记录在实验 manifest 中。

接口参数一致性在正式运行后又做了一次离线复核：M2a 剔除 3 条入口参数不匹配的分解，M2b 剔除 2 条；没有重新调用模型。下面的数字是 API revalidated 后的正式数字。

| 方法 | 有候选 | Selected public 全通过 | Selected private 全通过 | Private selected tests | Pool oracle |
| --- | ---: | ---: | ---: | ---: | ---: |
| M0 直接生成 | 25/25 | 11/25 | 9/25 | 54/183 (0.295) | 9/25 |
| M1 计划后生成 | 23/25 | 8/25 | 6/25 | 74/178 (0.416) | 8/25 |
| M2a skeleton | 20/25 | 3/25 | 5/25 | 37/146 (0.253) | 6/25 |
| M2b JSON | 18/25 | 7/25 | 5/25 | 51/150 (0.340) | 5/25 |

其中：

- **Selected private 全通过**：只用 public 选择一个候选，再看该候选是否完整通过 private；这是最接近实际部署的 pass@1 指标。
- **Pool oracle**：事后把候选池全部放到 private 上检查，只要其中有一个完整通过就算成功；这是候选池上限，不是可部署指标。

### 4.3 成本和选择信号

| 方法 | 模型调用数 | 模型时间（秒） | Prompt/output tokens | Public tie rate |
| --- | ---: | ---: | ---: | ---: |
| M0 | 60 | 380.4 | 36,492/11,238 | 17/25 (0.680) |
| M1 | 60 | 572.8 | 37,632/16,569 | 16/23 (0.696) |
| M2a | 308 | 1,578.4 | 238,358/33,560 | 20/20 (1.000) |
| M2b | 354 | 1,389.3 | 266,644/41,248 | 16/18 (0.889) |

M2 的组合数量更多，但调用数、prompt token 和模型时间也大幅增加。M2a 所有有候选的题都出现了最佳 public 分数平局，说明 public 测试无法有效区分候选；此时增加组合数量并不会自动转化为更好的选择。

### 4.4 题目级统计

Selected private 全通过的题目级 paired difference：

| 比较 | 差值 | Bootstrap 95% CI | Exact paired sign p |
| --- | ---: | ---: | ---: |
| M1 - M0 | -5/25 | [-0.400, 0.000] | 0.1250 |
| M2a - M1 | 0/25 | [-0.160, +0.160] | 1.0000 |
| M2b - M1 | 0/25 | [-0.200, +0.200] | 1.0000 |

本次 M0/M1 只生成 2 个候选，所以 solve@32 和 solve@64 不可估计；M2a/M2b 的候选预算也不足以报告 solve@32/64。没有根据有限候选池外推这些指标。

## 5. 失败边界分析

Interview function25 的失败归因如下：

| 方法 | 无候选 | public 选错但池中有 private 正解 | 候选池无 private 正解 |
| --- | ---: | ---: | ---: |
| M0 | 0 | 0 | 16 |
| M1 | 2 | 2 | 15 |
| M2a | 5 | 1 | 14 |
| M2b | 7 | 0 | 13 |

这说明 M2 的主要问题不是只有 selector 弱，而是候选池本身覆盖不足：M2a/M2b 的 pool oracle 都低于 M0。失败还集中在分解数量、入口顺序、依赖关系、嵌套函数、额外函数和空实现池等协议层问题。

## 6. 人工评审结果

在 development20 中抽取 10 道题进行盲评：

- skeleton 分解平均 7.00/10；
- JSON 分解平均 6.50/10；
- 人工分解经过同一实现器执行后，selected private 全通过为 3/10；
- 同一 10 道题上，M0 为 3/10、M1 为 5/10、M2a 为 6/10、M2b 为 3/10。

人工评审表明模型输出的分解在文字质量上可以看起来合理，但分解质量并没有稳定转化为组合程序质量。人工样本很小，只能作为诊断，不能替代 P5 主结果。

## 7. 当前结论

当前最强、最谨慎的结论是：

> 在 Qwen2.5-Coder 7B、当前 prompt、当前分解协议、当前候选预算和 APPS custom split 上，自动函数分解没有显示出相对整体程序生成的稳定收益。它增加了模型调用、token 和组合复杂度，但没有提高候选池对 private 正确程序的覆盖。因此本轮不进入 RL 训练。

这不是“函数分解永远没用”，也不是“7B 模型不能运行”。它只说明当前机制尚未证明值得训练。7B 推理已经在本机验证可行；7B QLoRA 训练仍然需要独立的显存和吞吐 gate，不能从推理结果直接推断。

## 8. 对“数据是否太弱”的判断

当前 Interview 数据并不算很弱：题目描述中位数约 217 个词，包含 Connect Four、保龄球、棋盘状态、表达式求导、组合计数等任务。但“题目难”不等于“适合函数拆分”。

最可能受益于 M2 的题目应同时满足：

1. 有多个自然处理阶段；
2. 阶段之间的输入输出接口清楚；
3. 单个函数可以相对独立地验证；
4. public 测试足够丰富，能够区分候选；
5. 正确性不只依赖一个无法拆开的数学洞察。

因此下一轮不能只增加题目难度，而要增加“可分解性”分层。否则可能得到更难、但同样不适合拆分的题目。

## 9. 后续工作建议

### 阶段 A：可分解性分层验证

预先固定约 60 道题，分为三组，每组约 20 道：

- 简单单阶段题：负对照；
- 中等多阶段题：主要测试区间；
- 困难且天然可拆分题：验证 M2 最可能发挥作用的场景。

题目筛选必须在看到任何 private 成绩前完成，记录来源、难度、筛选规则和 hash。每组至少跑 M0/M1/M2a/M2b 两个 seed，报告 selected private、pool oracle、有效率、tie rate、调用数、token 和时间。

### 阶段 B：先改协议，再考虑训练

优先修复以下问题：

1. 分解器必须复制 starter 的完整入口参数，而不是只复制函数名；
2. 实现器禁止嵌套函数和未声明的额外函数；
3. 允许模型明确标注“不拆分”，把整体生成作为合法选项；
4. 在组合前增加接口静态检查；
5. 让 public 评估尽量提供能区分候选的测试，而不是只看是否全错。

### 阶段 C：RL 进入条件

只有同时满足下列条件，才启动 P6：

- M2 在“困难且天然可分解”分组上超过 M1；
- 至少两个或三个 seed 方向一致；
- pool oracle 与 selected private 同时提高；
- 提升不是由更多 token 或更多组合单独造成；
- 分解、实现和组合的协议失败率降到可接受水平。

如果阶段 A 仍没有正信号，就停止 DecompRL 主线，转向研究“何时不该拆分”“接口设计”和“public 测试如何选择组合”。

## 12. 2026-09-20 更新：P5c 与论文正收益的差异

### 12.1 P5c 结果覆盖了原先的“提高 k / 修协议”疑问

P5c 在中等层 20 题上复用了冻结分解，只把每个函数实现数从 `k=2` 提高到 `k=8`，并放宽嵌套函数规则，再与等生成预算的 M0 对照：

| 方法 | 池 oracle | 选择后私有全通过 |
| --- | ---: | ---: |
| M0@2 | 3/20 | 3/20 |
| M0@17（等预算） | **8/20** | **7/20** |
| M2a@2 | 2/20 | 2/20 |
| M2a k=8+A1 | 3/20 | 3/20 |

这说明放宽接口规则和增加实现量确实能增加候选覆盖，但不足以超过直接生成。L0--L2 通过，L3--L4 不通过；当前不再把“再提高 k”或“再修同一套协议”作为进入 RL 的理由。完整报告见 `codeprm-reproduction/reports/p5c_medium_k8_vs_equal_budget_m0_20260920.md`。

### 12.2 为什么论文中的“拆分”不能直接与 M2 等同

- CodePRM 主要拆自然语言思路，并把执行反馈用于过程评分、错误定位和修正；它不做函数零件的交叉拼装。
- FunPRM 把完整候选中的函数当作评分步骤，最后选择一份完整候选；它不把不同候选的函数混合组合，并且使用元奖励校正中间标签。
- DecompRL 才是最接近的分解—实现—组合系统，但论文的正收益来自训练分解策略和实现策略。论文自报的无 RL 层级结果约 `11.0%`，低于直接生成的 `14.0%`。

因此，本项目的结论应限定为：**prompt-only 的独立函数实现与组合在当前 APPS custom split、模型、预算和 seed42 下没有同预算优势；这不是对函数级过程监督或完整 DecompRL 的否定。** 论文与本地实验的逐项对照见 `docs/week2/论文中的拆分为何有效_与本地No-Go的差异.md`。

### 12.3 更新后的决策

当前保持 No-Go for RL，不启动 seed43 或新的模型生成。后续只有两种合理方向：收束交付并报告模块化失败边界；或者明确改写研究问题，研究“何时应该拆分、何时应该保留整题生成”，并为新问题重新预注册。

## 13. 2026-09-20 更新：P5d 完整函数化候选确认

P5d 在预注册的 19 道新确认题上，把三种容易混淆的做法放到同一比较中：直接生成完整程序 M0、同一份完整程序内强制函数化 F1、独立分解后再组合 M2a。结果如下：

| 方法 | 选择后私有全通过 | pool oracle |
| --- | ---: | ---: |
| M0 direct | 10/19 | 12/19 |
| F1 functionized | 11/19 | 12/19 |
| M2a modular | 8/19 | 8/19 |

F1 的选择后结果比 M0 多 1 题，但候选池上限没有提高，因此按预注册标准不能称为正向信号，只能记为选择层的探索性 +1。M2a 在总体和预先标记的 13 道结构适用子组都低于 M0/F1。F1 的 190 次响应中 140 次满足结构规则；M2a 的 284 个组合只有 105 个独特程序，说明组合数并不等于独立完整解法数。

该结果进一步支持一个较窄的解释：当前的主要问题不是“模型不会写 helper”，而是独立 helper 之间的状态、接口契约和完整算法协调。oracle 复测发现过 `NameError: dict_scores is not defined` 一类跨函数断裂。因而不建议继续扩大当前 prompt-only M2a 或直接进入 RL；若继续，优先检验“完整函数化候选 + 函数级评分”以及“更强模型只负责生成分解”的隔离实验。正式结果见 `codeprm-reproduction/reports/p5d_functionized_vs_recombination_confirm19_20260920.md`，逐题汇总见 `codeprm-reproduction/data/processed/p5d_confirm19_analysis_20260920.json`。

2026-09-21 的后验诊断把 M0/F1 候选池合并后得到 `13/19` 的 pool oracle，但 public-only 路由仍为 `11/19`；额外的一个正确候选来自 F1 的 `apps-train-2714`。这给出一个明确但尚未验证的下一步：如果评分器/路由器不能在新的留出题上把 selected private 从 `11/19` 提高到至少 `12/19`，就没有继续训练的理由。该诊断不是新的确认性实验，private 只用于选择冻结后的事后统计。详见 `codeprm-reproduction/reports/p5d_union_router_diagnostic_20260921.md`。
