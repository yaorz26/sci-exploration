# 论文中的“拆分”为何能有正收益：与本地 No-Go 的差异

更新时间：2026-09-20

## 一句话结论

论文里的“拆分”不是同一种操作：CodePRM 主要拆的是自然语言思路，FunPRM 主要把完整候选按函数组织后做函数级评分，DecompRL 才是最接近本项目的“分别实现函数再组合”。前两者没有承担本项目的跨函数拼装代价；DecompRL 的正收益主要出现在经过 RL 学习之后，而论文自己报告的无 RL 层级结果低于直接生成。因此，论文有正收益与本项目 prompt-only 模块化 No-Go 并不矛盾。

## 1. 三篇论文的“拆分”分别是什么

| 方法 | 被拆成的步骤 | 拆分后怎么生成 | 主要收益来源 | 与本项目的关键差异 |
| --- | --- | --- | --- | --- |
| CodePRM | 自然语言思路步骤 | 每条思路继续生成完整代码；不把多个函数实现交叉拼装 | 执行反馈 + 学习到的过程评分 + GVR 定位修正 | 不是函数模块化，也没有 M2 的组合空间 |
| FunPRM | 函数级代码步骤 | 一个候选仍是一个完整、按函数组织的程序；对函数前缀打分，再选择完整候选 | 函数级 PRM + 元奖励校正 + 多候选选择 | 函数是评分单位，不是独立零件池；没有跨候选函数拼装 |
| DecompRL | 分解出的函数/模块 | 分解策略产出函数，实施策略生成函数实现，再组合完整程序 | RL 训练分解策略与实现策略，使其学会“怎么拆、怎么实现、怎么组合” | 本项目只做 prompt-only 机制，没有训练这两个策略 |
| 本项目 M2a/M2b | skeleton/JSON 函数分解 | 每个函数分别请求多个实现，再从实现池中组合 | 主要依赖提示词、固定规则和 public 选择 | 独立实现、接口约束、组合稀疏和格式税全部由当前小模型直接承担 |

这里的“格式税”是指：模型为了先写骨架、再遵守函数签名、再让多个函数接得上，必须额外输出和遵守一套格式。这些 token 没有直接用于解决题目本身。

## 2. CodePRM 为什么能有收益

CodePRM 的核心不是“把程序拆成函数”，而是把“思路是否靠谱”绑定到它产生的代码和执行反馈上。

它的流程更像：

```text
生成思路和完整代码
→ 运行公开测试
→ 给每个思路步骤打分
→ 找出最可疑的思路
→ 只重写这个思路
→ 重新生成和验证
```

因此它的收益来自三个环节：

1. 执行结果给了模型额外证据。只看“题目 + 思路”时，很多错误看起来都合理；报错和失败测试能指出边界条件或算法方向有问题。
2. CodePRM 是专门训练的评分器，不是直接拿 public pass rate 临时排序。它学习“哪一种思路更可能继续生成好代码”。
3. GVR 会定位并修正错误思路，而不是只在若干独立函数之间做组合。

本项目已经复现了其中最容易成立的部分：直接用执行反馈选择候选确实有价值。没有成立的是“在本地小数据和小模型上训练出的神经评分器超过直接 public 选择”。因此本项目的负结果不是“执行反馈无用”，而是“当前学习型评分器没有学会超过一个很强的直接信号”。

## 3. FunPRM 为什么能有收益

FunPRM 的“函数即步骤”容易被误读成 M2。两者的关键区别是：

- FunPRM 要求模型把**一个完整候选程序**组织成高层函数和辅助函数；
- FunPRM 对这些函数逐步打分，最后从完整候选中挑一个；
- 它没有把候选 A 的 `main`、候选 B 的 `helper`、候选 C 的另一个函数拆出来重新拼成新程序。

可以把两种流程比成两种施工方式：

- FunPRM：让三支施工队各自交付完整房子，再按房间质量评分，选一套最好的房子；
- 本项目 M2：让不同施工队分别造客厅、厨房和卧室，再把不同队伍的零件拼成房子。只要门的尺寸、管线或材料约定有一点不一致，整套房子就会坏。

FunPRM 还多了一个本项目暂时没有的训练环节：它用完整程序的单元测试结果，去校正函数级中间奖励的噪声。它报告的消融是：去掉 Chain-of-Function 为 `80.1`，去掉元奖励校正为 `80.2`，完整方法为 `80.9`。这说明收益来自“函数组织 + 函数级评分 + 奖励校正”的组合，不能简化成“只要拆函数就会变好”。

此外，FunPRM 的候选由更强的基础模型生成，实验使用 LiveCodeBench、BigCodeBench 等更大测试集；本项目的主要模块化结果是 Qwen2.5-Coder 7B Q4、本地 Ollama、APPS custom split、20 题和单 seed。模型、数据规模和训练资源都不相同，不能直接比较绝对分数。

## 4. DecompRL 为什么与本项目最接近，但仍然不同

DecompRL 才是“先分解，再分别实现，再组合”的同类方法。但它的论文收益不能归因于 prompt-only 的拆分动作本身。

本地整理的论文对照已经记录：DecompRL 的无 RL 层级推理结果约为 `11.0%`，直接生成约为 `14.0%`。这与本项目 P5c 的方向一致：只增加模块化实现量和组合，仍可能输给同预算的直接生成。

因此更准确的理解是：

1. **论文先用分解格式提供动作空间。** 模型可以把复杂程序表示成多个模块。
2. **RL 再训练分解策略。** 分解器需要逐渐学会哪些任务值得拆、拆成几段、每段边界放在哪里。
3. **RL 同时训练实现策略。** 实现器需要学会遵守阶段契约、正确调用依赖、输出可组合的函数，而不是只在单独看函数时“像是合理”。
4. **奖励来自组合后完整程序。** 也就是说，训练会把“局部看起来不错但拼起来错误”的分解和实现压下去。

本项目做的是第 1 步的 prompt-only 版本，并且使用冻结分解、独立函数请求和固定组合采样。它没有执行第 2--4 步的策略学习，所以不能把 M2 的结果当作完整 DecompRL 的结果，也不能用 M2 的负结果断言 RL 后一定不会有效。

但现有结果仍足以支持一个更窄的判断：在当前本地模型、提示、预算和题目切分下，模块化的初始动作空间质量不够好，且组合成本很高；在这个基础上直接开始 RL，缺少值得训练的正向信号。

## 5. 本项目为什么没有复制出论文收益

目前证据支持的差异有以下几类，强度不完全相同：

### 5.1 研究对象不同：评分步骤不等于可重组模块

CodePRM 和 FunPRM 主要把结构用于评分、定位或选择；本项目 M2 把结构用于跨候选重组。后者多了一层接口风险：每个函数都可能单独通过解析，但组合后出现 `NameError`、`TypeError` 或阶段契约不一致。

### 5.2 训练方式不同：论文学习“如何拆”，本项目只要求模型“按提示拆”

提示词可以让模型输出函数名和 docstring，却不能保证它学会稳定的职责边界。P5b/P5c 中已经看到，修复嵌套函数和实现报废后，候选形成率上升，但正确率没有追上直接生成。这说明“格式遵守”不是“算法正确”。

### 5.3 预算使用方式不同：组合预算不等于完整解题次数

直接生成一次候选，就是一次完整的算法尝试；模块化生成一次函数，只覆盖局部职责。若有 4 个函数、每个有 8 个实现，理论上有 `8^4=4096` 个组合，但绝大多数组合并不对应一个完整正确的算法。本项目 P5c 在每题采样 64 个组合，最终模块化池 oracle 为 `3/20`，等预算 M0 为 `8/20`。

### 5.4 任务和模型不同

FunPRM 的任务更强调多函数代码组织和函数复用；本项目的 APPS custom split 是函数式题目，题目是否天然适合拆分已经单独分层，但仍有不少题目的主要难点是一个整体算法洞察。Qwen2.5-Coder 7B Q4 在局部函数上能写出“像样”的代码，不代表它能把多个局部方案协调成同一个正确算法。

### 5.5 论文报告的正收益可能包含训练和规模效应

论文使用更大的题目集、更多候选和专门训练的 PRM/RL 策略。本地实验使用单 seed、20 题和本地量化模型，结论只能限定为机制复现。这里不能把差异全部归因于某一个因素；真正的因果拆分需要新的受控实验。

## 6. 当前最稳妥的统一解释

可以把三类方法放在同一张图里：

```text
CodePRM：        思路步骤 ──> 执行反馈评分 ──> 定位/修正
FunPRM：         完整函数化候选 ──> 函数级评分 ──> 选择完整候选
DecompRL：       学习分解 ──> 学习实现 ──> 组合后奖励 ──> RL 更新
本项目 M2：      提示分解 ──> 独立实现 ──> 固定组合 ──> public 选择
```

所以当前结论应写成：

> 论文说明“结构化过程信息”在有合适评分器、足够训练和正确任务条件时可能带来收益；本项目说明“仅靠提示词把程序拆成独立函数再组合”在当前本地条件下没有带来同预算收益。两者研究的不是同一个系统。

## 7. 不能过度推出的结论

- 不能说“函数拆分没有用”；FunPRM 和 DecompRL 的论文结果不支持这种绝对说法。
- 不能说“本项目已经复现了 DecompRL 失败”；本项目没有做 RL，只做了 prompt-only 机制层复现。
- 不能说“论文收益完全来自模型更大”；CodePRM/FunPRM 的训练目标、评分方式、候选生成方式和数据规模也同时不同。
- 不能把本项目的 `3/20` 对 `8/20` 写成论文级统计结论；它是 APPS custom split、单 seed、20 题上的机制证据。

## 8. 如果要继续，什么最可能带来正收益

### 8.1 先区分三种“变强”

用户所说的“更强模型生成 prompt”可能指三件不同的事：

1. **让更强模型润色提示词。** 这主要改善格式遵守、字段完整和输出稳定性。P5c 已经说明，格式和接口问题明显下降后，模块化仍然落后于等预算 M0，所以它不太可能单独解决核心问题。
2. **让更强模型生成分解方案。** 这直接针对当前的分解质量瓶颈，比“让模型写 prompt”更有价值，但仍需验证：更好的分解能否让同一个实现器产出更好的完整程序。
3. **专门训练分解器、实现器或路由器。** 这改变的是模型行为，而不是文字说明。它的潜力最大，但需要高质量成功/失败记录和题目级 held-out 验证，不能直接从当前 noisy modular reward 开始 RL。

### 8.2 推荐的实验顺序

| 顺序 | 做法 | 主要回答的问题 | 判断 |
| --- | --- | --- | --- |
| 1 | FunPRM 风格：生成完整的函数化候选，再做函数级评分和完整候选选择 | 函数结构本身有用，还是跨函数重组造成了损失？ | **优先级最高，成本相对低** |
| 2 | 更强模型只负责生成分解，固定本地模型负责实现；与本地自动分解同预算比较 | 当前瓶颈是不是分解质量，而不是实现器？ | **必要的隔离实验** |
| 3 | 用成功的完整程序、接口审计和失败归因训练分解器/路由器，先做监督或排序训练 | 模型能否学会“什么时候拆、怎么拆、什么时候不拆”？ | **比直接 RL 稳妥** |
| 4 | 把“直接生成 / 计划后生成 / 函数化生成”作为路由动作，按题目选择路径 | 即使模块化只在部分题目有效，能否提高总体平均效果？ | **实际部署价值最高** |
| 5 | 只有前面在 held-out 题目上出现正向信号后，才做联合 RL | 最终奖励能否进一步优化分解和实现策略？ | **最后才做** |

这里的路由器是一个先做选择的小模型：它可以决定某道题直接生成、先写计划，还是按函数组织。这样不会强迫本来只有一个整体算法洞察的题目承担模块化格式税。

### 8.3 最值得先做的不是“更强 prompt”，而是“完整候选 vs 独立重组”对照

当前最关键的未知量是：函数结构带来的收益，是否被跨候选重组的损失抵消。最小对照可以固定题目、模型、候选数和总 token，只改变生成方式：

- A：每次生成一份完整但按函数组织的程序，再用函数级评分选择；
- B：每个函数分别生成，再跨实现池组合；
- C：直接生成完整程序。

如果 A 能接近或超过 C，而 B 仍然落后，说明函数结构有价值，主要问题是独立重组；如果 A、B 都不如 C，才更像是当前模型或题目不适合函数粒度。

### 8.4 专门训练应该训练什么

若后续进入训练，优先级应是：

1. **训练分解器或路由器**：学习是否拆、拆几段、每段输入输出是什么；把“不拆分”作为合法动作。
2. **训练接口/实现约束**：把函数签名、返回值形状、依赖顺序和组合后完整正确率放进监督信号。
3. **最后再做 RL**：奖励至少要同时包含完整程序正确率、接口有效性、候选成本和是否选择了合适粒度，不能只奖励局部函数通过或 public 测试分数。

更强模型适合先当“教师”产生候选分解和正反例；它不应被直接当成“只要写出更长 prompt 就能修好模块化”的证据。

## 9. 当前建议

在本项目的资源条件下，我建议采用以下判断顺序：

> 先做 FunPRM 风格的完整函数化候选对照，再做更强分解教师的隔离实验；只有这两步显示结构信息确实能改善完整程序质量，才投入分解器/路由器训练，最后才考虑 RL。

这比直接把当前 M2 管线送入 RL 更可能得到可解释结果，也更容易判断收益究竟来自结构、评分器、模型能力还是训练。
