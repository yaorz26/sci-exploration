# 研究方向重设：面向真实项目的代码过程奖励

创建日期：2026-09-10
状态：**从零规划**（不依赖此前 `codeprm-reproduction` 的任何结论、数据与代码）

---

## 0. 目标与前提

**最终目标**：大模型在**真实复杂项目**（多文件、多函数、有依赖、有测试）上生成代码。

**为什么"过程奖励（PRM）"值得做**：只判断最终代码对错，模型学不到"哪一步想错了"。
如果能给中间步骤打分，就能在生成过程中定位并修正。

**为什么这个方向现在没有定论**：所有人都在谈"步骤"，但**没有一个工作真的定义过"代码的步骤"是什么**。

---

## 1. 靶子：三个从未被验证的默认假设

现有代码 PRM（CodePRM、FunPRM 等）都隐含下面三条。它们在入门级单函数题目上勉强能用，在真实项目上会失效。

| 编号 | 假设 | 在真实项目上为什么失效 |
| --- | --- | --- |
| **A1 链式假设** | 步骤是一条链：第 1 步 → 第 2 步 → …，分数可沿链回传或求和 | 真实代码的函数构成**有向图**：互相调用、循环、递归。没有"第 1 步"，求和没有定义 |
| **A2 固定粒度假设** | 整篇 / 函数 / 行，全局选一个粒度 | 粒度太粗（函数=整体）失去定位力；太细（几百个函数）成本爆炸、语义碎裂 |
| **A3 独立标签假设** | 一个步骤的质量可由"它后续产生的结果"单独估计（蒙特卡洛） | 一个函数的正确性依赖**调用关系**，孤立评估会漏掉"接线错误" |

**你的定位**：不是再做一个 PRM，而是**把这三个假设拆开检验并重建**。

---

## 2. 三个研究问题（层层递进）

### RQ1（结构）：真实代码的"步骤"是链还是图？图上的过程奖励怎么定义？

- 现状：所有方法都假设链。图上没有定义。
- 要回答：函数调用图是链、树还是网？在什么规模上从链变成网？
- 可能的贡献：把过程奖励从"链上传播"改成"**DAG 上分层传播**"
  （按调用依赖做拓扑分层；错误可以定位到**节点**或**边**；循环/递归单独处理）。

### RQ2（粒度）：粒度能否随代码结构自适应？有效区间在哪？

- 现象假设：存在**U 形**关系 —— 太粗失去定位力，太细失去语义与稳定性。
- 关键：把粒度选择的准则从"粒度本身"换成**"可定位性"**
  （这个信号能不能指出错在哪个单元），这样才能量化。

### RQ3（信号）：当执行反馈已经很强时，过程奖励还能提供什么增量？

- 这是**大模型时代最致命的问题**：模型越强，4 个候选越像，测试反馈越准，
  PRM"比测试多出来的信息"越少。
- 干净的实验设计：把候选分成两类
  - 类 1：公开测试通过率与隐藏测试结果一致 → 执行反馈已经够用
  - 类 2：公开测试通过但隐藏测试失败 → **只有这类才是 PRM 可能有用武之地的地方**
- 把 PRM 的增益精确对齐到类 2 子集，而不是报一个平均提升。**这是最容易被审稿人认可的设计。**

## 3. 第一优先实验：用变异测试拿到"已知错误位置"

**为什么**：要度量"定位能力"，必须有**准确知道错在哪**的样本。真实项目里这很难拿到。

**做法**：拿正确的多函数程序，**人工/自动注入错误**（改条件、改循环边界、换错变量、删掉一次调用），
于是你**精确知道**错误落在哪个函数、哪条调用边。

- 这是**免费的标注**：不需要大模型推理、不需要人工标注、不需要 Docker。
- 可以直接测：① 执行反馈能否指出位置；② PRM 分数能否指出位置；③ 粒度改变时定位准确率如何变化。
- 规模可控：先 30–50 个多函数程序 × 每种变异若干次。

**这个实验不需要训练任何模型，单机可完成，一到两周能出结果。**
它是你整条研究路线的地基，也是目前最缺的证据（论文都只报最终正确率，不报定位准确率）。

## 4. 数据集三层策略（解决"评测跑不动"的问题）

| 层级 | 来源 | 特点 | 作用 | 本地可行性 |
| --- | --- | --- | --- | --- |
| **L1 合成** | 自建多函数任务 + pytest 测试 + 变异注入 | 完全可控、知道错误位置 | 机制验证、定位指标 | 完全可以 |
| **L2 真实中等规模** | ClassEval（类/方法级）、BigCodeBench（多库函数调用）、LiveCodeBench（时间切分，便于与 FunPRM 对比） | 真实、有测试、规模适中 | 主实验 | 可以 |
| **L3 真实仓库** | RepoBench / CrossCodeEval / SWE-bench-Lite 的公开轨迹 | 最接近最终目标 | 外部有效性验证 | 评测需容器，**先只做静态分析或复用公开轨迹** |

**生成候选**：本地 3B 不够时可用 API 模型（环境里已有可用的 API key，用量需自己控制）；
或用已公开的模型输出轨迹，避免自己生成。

**静态分析只做三件事**（不需要执行代码）：函数/方法/类个数、调用图形状、思路步数与函数数之比。

## 6. 指标体系（不要只报正确率）

| 类别 | 指标 | 说明 |
| --- | --- | --- |
| 结果 | pass@1、pass rate | 常规 |
| **定位** | 错误定位准确率（是否指到被变异的函数/边） | **本方向的核心指标** |
| 定位 | 定位到"边"的比例（调用关系错误） | 链式方法测不出来的部分 |
| 成本 | 步骤数、评分调用次数、token 成本 | 太细的粒度会在这里暴露 |
| 结构 | 从链变网的临界规模 | 描述性发现 |
| **归因** | 增益在"公开通过/隐藏失败"子集上的分布 | 能否证明 PRM 有不可替代性 |

## 7. 可证伪预测

| 编号 | 预测 | 什么情况算被推翻 |
| --- | --- | --- |
| P1 | 超过某个规模后，函数调用图不再是链（分支/递归显著增加） | 若始终接近链 → RQ1 的动机减弱 |
| P2 | 执行反馈只能定位到"程序级"，无法定位到函数/边 | 若执行反馈定位准确率已很高 → PRM 价值下降 |
| P3 | 粒度与定位准确率呈倒 U 形 | 若单调 → 自适应粒度没有意义 |
| P4 | PRM 的增益集中在"公开通过/隐藏失败"子集 | 若增益均匀分布 → 说明只是通用排序能力，不构成独立贡献 |
| P5 | 图结构奖励在"接线错误"上的定位优于链式方法 | 若无差别 → 图结构这一支不成立 |

## 8. 风险（提前写好答案）

1. **模型越强，PRM 越没用**：这是对本方向最根本的威胁。必须用 RQ3 的归因实验正面回答，
   否则整个方向会被一句"强模型下不需要过程奖励"驳回。
2. **评测成本**：真实仓库要容器与依赖。策略是先做静态与合成，把重评测留到有条件时。
3. **数据污染**：LiveCodeBench 等平台有时间切分，必须用；自建数据可完全避免。
4. **与现有工作的区分度**：必须明确说清"CodePRM/FunPRM 假设链与固定粒度，我们检验并重建这两个假设"。
5. **负结果也要预置**：P1–P5 每条都写清"什么结果算失败"，避免事后改口径。

## 10. 本周的第一条命令（具体到动作）

1. 写一个脚本：输入一份 Python 代码 → 输出 ① 函数/方法/类列表 ② 调用图 ③ 最长调用链 ④ 是否有递归 ⑤ 判定"像链还是像网"。
2. 找一个真实的**多函数**代码来源（自己写 10 个、或从 ClassEval 取 20 个），跑一遍。
3. 结果写成一张表：规模 vs 图形状。
4. 如果这批代码里真的有明显的分支与递归 → RQ1 站得住，继续做 M1。
