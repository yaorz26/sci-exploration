## 1. 每篇论文必答的 8 个问题

| 问题 | CodePRM | FunPRM |
| --- | --- | --- |
| ① 什么算一个"步骤" | 自然语言**思路步骤**（thought step），在搜索树上逐节点展开 | **函数**（提示词要求模型按函数组织代码，先写高层函数再写辅助函数） |
| ② 为什么选这种粒度 | 思路与代码之间存在"间隔"，思路本身太抽象；需要把思路绑到它产生的代码上评价 | 单行代码太细（可能数百步）、整段程序太粗；函数是"相对独立的逻辑模块"，语义清晰 ⚠️（原论文 §1 有具体论证） |
| ③ 监督标签从哪来 | 树搜索中每个思路节点的**所有后继代码 private pass rate 的均值**（软标签） | ① 噪声部分奖励：对部分解继续采样完整解估计通过率；② 干净最终奖励：完整程序的单元测试结果（用于元校正） |
| ④ 标签噪声/偏差/泄漏 | 软标签缓解了 0/1 的过度惩罚；但公开测试反馈可能被过拟合 ⚠️（原文局限性一节） | 明确承认蒙特卡洛部分奖励噪声大，用元学习校正表修正；这是论文的核心卖点 |
| ⑤ 评分模型看到什么输入 | 问题 + 完整思路链 + 当前代码 + **执行反馈** | 问题 + 代码前缀（生成式 PRM，输出 `+`/`-`） |
| ⑥ 分数怎么用 | 训练：MSE 回归软标签；推理：GVR（Generate-Verify-Refine），阈值策略或最低分策略定位错误思路 | 推理：Best-of-N，每题 8 个候选，聚合函数级分数选最高分；**不依赖公开测试用例** |
| ⑦ 评测指标 | APPS（Intro/Inter/Comp 各 100 题）+ Codeforces（1200/1500/1700）；`pass rate`、`pass@1` | LiveCodeBench（601 训 / 454 测 + 131 题排行榜）+ BigCodeBench（800 训 / 340 测）；泛化到 HumanEval+、MBPP+；`pass@1` |
| ⑧ 可能在哪些任务上失效 | 无执行反馈的任务（如数学）；换骨干模型未验证；修正依赖生成器，验证对≠改得对；可能过拟合公开用例 | 基础模型不遵循"按函数组织"提示时步骤不稳定；主要在 Python + 有限基准；单元测试通过 ≠ 无漏洞 |

## 2. 关键差异（汇报时最容易被追问的三点）

| 维度 | CodePRM | FunPRM | 对"子任务拆分"方向的意义 |
| --- | --- | --- | --- |
| 步骤的载体 | **思路**（自然语言） | **函数**（代码结构） | 两种"subtask"定义分别落在自然语言侧与代码结构侧，说明领域内对粒度没有共识 |
| 步骤与代码的关系 | 一个思路 → 多份代码 | 一个函数 → 代码片段本身 | CodePRM 的步骤是"一对多"，FunPRM 的步骤是"一对一" |
| 反馈的使用方式 | 反馈进**训练输入**，也是修正触发信号 | 反馈只作**标签来源**，推理时不看测试 | 前者依赖可用测试环境，后者可无测试部署 |

## 3. 两篇论文共同留下的空白（你的切入点）

1. **"函数 = 步骤"的适用条件没有被界定**：FunPRM 假设候选代码按函数组织。若任务本身是单函数函数式题目（APPS starter code 形态），函数级划分会退化为单步。
2. **粒度对任务难度的适配没有被研究**：FunPRM 自己提到"有些困难题只需一个函数"，但没有据此调整步骤定义。
3. **两者都没有回答"步骤划分错误率"这个量**：没有报告过"函数边界与语义边界不一致"的比例。
4. **公开测试反馈的定位能力没有量化**：CodePRM 用公开反馈触发修正，但没有报告公开反馈"指错位置"的频率。

## 4. 与我方实验条件的落差（写在汇报里防止被问倒）

| 项目 | 论文 | 我方现状 |

| 生成模型 | GPT-4o-mini、DeepSeek-Coder-V2-Lite（CodePRM）；O4-mini、Qwen3-Coder-30B 等（FunPRM） | Qwen2.5-Coder 3B（本地 Ollama） |
| 评分模型 | Qwen2.5-Coder-7B-Instruct SFT + value head；FunPRM 用 7B + LoRA | 3B + QLoRA 4-bit（RTX 4060 8GB） |

| 结论强度 | 论文级 | 上限为"缩小规模复现" |
