# 科研流程：从论文阅读到提出新想法

## 1. 当前研究方向

导师给出的总体方向是优化大模型的代码生成过程，其中一条路线是：

> 把一个代码生成任务拆分成多个有意义的子任务（subtask），评价每个子任务的质量，并在生成过程中选择或修正错误步骤。

当前重点阅读的两项工作是：

- **CodePRM**：把自然语言思维过程中的步骤作为评价对象，并结合生成代码和执行反馈进行评分。
- **FunPRM**：把函数作为代码生成过程中的步骤，用函数级过程奖励选择更好的候选程序。

这一方向最基础、也最值得继续追问的问题是：

> 什么样的代码单元才是合适的 subtask？函数是否总能代表一个独立子任务？

## 2. 总体研究流程

```text
理解 CodePRM
  -> 理解 FunPRM
  -> 手工分析函数与 subtask 的对应关系
  -> 完成小规模、可解释的复现
  -> 收集和分类失败案例
  -> 从失败现象形成研究假设
  -> 设计对照实验验证假设
  -> 再决定是否扩大数据和模型规模
```

现阶段不应直接追求更大的模型或更多实验。首要目标是能够独立解释论文的方法、已有代码和实验结果。

## 3. 第一阶段：读懂两篇论文

### 3.1 阅读顺序

1. 先读 CodePRM，理解执行反馈如何转化为过程奖励。
2. 再读 FunPRM，理解函数为什么可以作为过程步骤。
3. 最后对比两篇论文的步骤定义、标签构造和使用方式。

对应材料：

- `2025.findings-acl.428.pdf`：CodePRM 原论文。
- `2601.22249v1.pdf`：FunPRM 原论文。
- `CodePRM_中文总结翻译.md`：辅助理解，不能代替原论文。
- `FunPRM_中文总结翻译.md`：辅助理解，不能代替原论文。

### 3.2 阅读每篇论文时必须回答的问题

1. 论文把什么定义为一个步骤？
2. 为什么选择这种步骤粒度？
3. 每一步的监督标签从哪里来？
4. 标签是否存在噪声、偏差或信息泄漏？
5. 评分模型能看到哪些输入？
6. 过程分数如何参与候选选择、搜索或修正？
7. 最终使用什么指标评价方法？
8. 方法可能在哪些任务上失效？

### 3.3 第一阶段完成标准

- [ ] 不看论文，也能画出 CodePRM 的完整流程图。
- [ ] 不看论文，也能画出 FunPRM 的完整流程图。
- [ ] 能用自己的话解释 soft label、binary label、pass rate 和 pass@1。
- [ ] 能列出 CodePRM 与 FunPRM 至少三个关键差异。
- [ ] 能指出每篇论文至少两个局限，而不只是复述论文原文。

## 4. 第二阶段：把现有复现变成自己的学习实验

当前 `codeprm-reproduction` 目录提供了实验基础设施，但 AI 跑完代码不等于自己理解了复现。需要亲自追踪一次完整的数据流：

```text
题目
  -> 生成多个思路或代码候选
  -> 执行公开测试
  -> 保存代码、反馈和通过率
  -> 构造步骤标签
  -> 评分或选择候选
  -> 使用独立测试评价结果
```

需要弄清楚：

- 数据集中的一道题如何被加载；
- 公开测试和私有测试如何划分；
- 每道题生成了多少候选；
- 候选代码如何执行以及如何处理超时和异常；
- step label 如何计算；
- PRM 输出如何决定最终选择；
- 汇总表中的每个指标由哪些样本计算得到。

### 第二阶段完成标准

- [ ] 能从一道输入题目追踪到最终结果文件。
- [ ] 能解释一条训练记录中的所有字段。
- [ ] 能手算至少一个步骤标签。
- [ ] 能手算一道题的候选选择结果。
- [ ] 能说明已有复现与论文正式实验的区别。

## 5. 第三阶段：进行小规模、可解释的人工复现

先选择 3 至 5 道简单编程题，每题生成 4 个候选程序。暂时不训练新模型，重点分析步骤划分是否合理。

### 5.1 每道题的操作

1. 阅读题目并写出自己认为合理的 subtask。
2. 查看四个候选程序。
3. 按函数划分每个程序。
4. 再按语义划分每个程序，例如输入处理、状态更新、边界处理和结果汇总。
5. 记录函数和语义 subtask 是否一一对应。
6. 执行公开测试并保存反馈。
7. 在不知道私有测试结果的情况下，尝试判断错误位置。
8. 最后查看私有测试结果，检查判断是否正确。

### 5.2 比较的候选选择方法

- 第一个候选；
- 随机候选；
- 公开测试通过率最高的候选；
- 按函数步骤评分选择的候选；
- 按语义 subtask 评分选择的候选；
- 使用私有测试事后选择的最优候选，仅作为分析上限。

### 5.3 重点收集的失败案例

- 一个函数内部实际包含多个不同子任务；
- 一个子任务横跨多个函数；
- 单个函数局部正确，但与其他函数组合后失败；
- 执行反馈能发现程序错误，却无法定位到具体函数；
- 简单函数获得高分，但关键边界条件仍然错误；
- 函数划分改善了可读性，却没有改善正确率；
- 所有候选都失败，导致候选选择方法没有正确答案可选。

## 6. 第四阶段：从失败案例形成研究问题

不要为了“创新”凭空添加复杂模块。新想法应当采用下面的形式：

```text
观察到的失败现象
  -> 对失败原因的解释
  -> 一个具体、最小的方法改动
  -> 可以通过实验验证的预测
```

### 示例研究假设

#### 假设 A：函数粒度有时过粗

- **观察**：一个长函数可能同时负责解析、计算、边界处理和结果组织。
- **解释**：函数边界不一定等于语义 subtask 边界。
- **改动**：先按函数划分；当函数复杂度较高或定位不确定时，再按分支、循环或语义阶段细分。
- **预测**：动态细分会提高长函数程序的错误定位准确率，并进一步提高最终 pass@1。

#### 假设 B：固定粒度不适合所有题目

- **观察**：简单题可能只需一个函数，复杂题则包含多个层级的逻辑。
- **解释**：所有题目统一使用函数级步骤会造成粒度不匹配。
- **改动**：根据题目和代码结构动态选择整段、函数级或函数内部步骤。
- **预测**：动态粒度在复杂题上的收益高于简单题，并且不会显著增加简单题的推理成本。

#### 假设 C：不同错误需要不同反馈

- **观察**：语法错误、运行时错误和逻辑错误提供的信息不同。
- **解释**：只使用一个总通过率会丢失错误类型和错误位置的信息。
- **改动**：将异常类型、失败测试摘要、AST 结构和覆盖位置加入步骤评价。
- **预测**：结构化反馈能改善错误定位，尤其对运行时错误和边界条件错误更有效。

## 7. 第五阶段：设计可以证明观点的实验

一个合格实验必须明确以下内容：

| 项目 | 需要回答的问题 |
| --- | --- |
| 研究问题 | 想验证的核心判断是什么？ |
| 基线 | 与 CodePRM、FunPRM 或简单公开测试选择相比如何？ |
| 自变量 | 改变了步骤粒度、反馈形式还是评分方法？ |
| 控制变量 | 是否使用相同题目、生成模型、候选和测试预算？ |
| 指标 | 除 pass@1 外，是否测量定位准确率、修正成功率和成本？ |
| 消融实验 | 方法中的哪个组件真正产生了收益？ |
| 失败分析 | 方法在哪些题型和错误类型上无效？ |

推荐优先关注以下指标：

- `pass rate`：平均通过多少比例的独立测试；
- `pass@1`：有多少道题完全通过独立测试；
- 错误定位准确率；
- 修正成功率；
- 错误修正后的退化率；
- 每题生成或执行次数；
- 不同函数长度、复杂度和错误类型下的结果。

## 8. AI 在这个过程中的角色

AI 适合承担：

- 整理论文结构和术语；
- 解释代码和实验配置；
- 生成候选程序；
- 自动执行测试和计算指标；
- 整理实验表格和失败案例；
- 检查实验是否可以重复运行。

以下判断必须由研究者自己掌握：

- 为什么这样定义 subtask；
- 为什么步骤标签能够表示步骤质量；
- 为什么对照实验可以验证假设；
- 实验结果是否真的支持结论；
- 一个失败结果应该推翻假设，还是说明实验设计有问题。

判断自己是否真正理解的简单标准是：

> 能否脱离代码和 AI，用纸笔解释“输入、步骤划分、标签、评分、候选选择、最终指标”之间的关系。

## 9. 近期可向导师汇报的阶段成果

近期目标不应表述为“已经完整复现论文”，而可以是：

1. 理解并比较 CodePRM 与 FunPRM 的步骤定义、标签构造和推理流程。
2. 完成 3 至 5 道题的小规模可解释实验。
3. 整理函数划分与语义 subtask 不一致的具体案例。
4. 提出一个关于步骤粒度或结构化反馈的可检验假设。
5. 给出与 CodePRM、FunPRM 和公开测试选择进行比较的实验设计。

## 11. 当前原则

1. 先理解，再扩大复现。
2. 先观察失败，再提出方法。
3. 先验证最小假设，再增加模型和数据规模。
4. AI 可以完成工程操作，但研究问题、实验逻辑和结论必须能够自己解释。
5. 现有复现是研究基础设施和学习材料，不是最终科研贡献。
