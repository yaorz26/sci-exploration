# 从四篇新论文中提取的可做方向（2026-09-10）

> 说明：本文档从 `articles/` 下四篇新论文（SecCodePRM、AdapTrack、PSC、LAVE）的**局限性章节与"作者明确没做的事"**出发，提取可以落地成小课题的方向。每个方向都标注来源空白、假设、最小实验、资源需求与判定标准（Go/No-Go）。
> 本地实测基线来自 `docs/阶段4_研究假设一页纸.md` 与 `codeprm-reproduction/reports/`；论文细节可在 `articles/*_中文总结翻译.md` 中查到。

## 0. 先划清资源边界

方向能不能做，先看手里有什么。下表决定了后文每个方向的档位。

| 资源 | 现状 | 影响 |
| --- | --- | --- |
| GPU | RTX 4060 Laptop 8GB（约 6.5GB 可用） | 3B 4-bit LoRA 可行；7B 全参/QLoRA 基本出局 |
| 本地生成器 | Ollama `qwen2.5-coder:1.5b / 3b` | 候选池可以自己造，成本几乎为零 |
| 训练环境 | WSL Ubuntu 22.04 + torch 2.6 cu124 + peft | 小规模微调链路已跑通 |
| 数据 | APPS train Introductory 50 题 × 4 候选，598 节点 / 1196 条记录 | 样本量小，结论只能写成"探索性" |
| 执行器 | 函数式 APPS 已支持，public/private 划分自定义 | 标签与评估闭环可跑 |
| 已有负结果 | 神经 CodePRM 0.514 < 首候选 0.533 < public 选择 0.683 | 直接重跑同配置没有意义，必须换变量 |
| 缺的资源 | 多卡 80GB、CodeQL 全库分析、255 GiB 内存预处理、dLLM 权重的推理算力 | 大算力型复现全部排除 |

一句话总结约束：**能在单卡 8GB + 纯 CPU 分析里做完的方向，才是当下的候选。**

## 2. 方向卡片

每张卡片的结构固定：来源 → 假设 → 最小实验 → 指标 → 资源 → 风险 → 判定标准 → 工作量。档位含义：**A 级**＝本机 1–2 周可完成；**B 级**＝本机可做但需要额外数据或一两周工程；**C 级**＝需要超出当前资源，只作为延伸。

---

### D1 约束解码的"代价"：候选池质量与 Best-of-N 上限（A 级，主推）

- **来源**：G1、G2、G11。
- **一句话假设**：在消费级小模型 + APPS 函数式任务上，语法约束解码把语法错误率压到 0，代价是候选池多样性下降，"能通过测试的候选数"未必变多；因此 Best-of-N / 过程奖励的可用信息减少，`pass@k` 的净收益明显小于"语法错误清零"所暗示的量级。
- **为什么值得做**：这条把两条线接在一起——约束解码决定**候选池长什么样**，过程奖励只负责**给候选排序**。如果候选池本身被约束压扁了，再怎么训 PRM 都很难有收益。这正好解释了我们这边的现象：候选池 4 个候选、12/50 无解，排序器再准也没用。
- **最小实验**：APPS train-50，固定温度与种子，跑四组候选池：
  1. 无约束采样；
  2. 无约束采样 + 事后语法过滤（只保留能编译的）；
  3. 文法约束解码（限制生成必须是合法的 Python 函数体）；
  4. 约束解码 + 事后过滤。
  每组 4 候选，比较随后的 `pass@1 / pass@4`、Best-of-N 增益（public 选择相对首候选的提升）。
- **指标**：语法错误率；去重后的唯一程序数；候选间编辑距离或 token 熵（多样性代理）；有解题目占比（对照现有 38/50）；`pass@k`；public 选择的增益。
- **资源**：本机 8GB + Ollama。Ollama/llama.cpp 自带 GBNF 文法约束，可用「必须输出合法的 Python 函数体」这类简单文法；无需训练。
- **风险**：约束器实现质量会引入噪声（AdapTrack 自己也踩过约束器 bug）；必须固定温度与种子，并按题目配对比较。
- **判定标准**：若约束组的唯一解数与 `pass@k` 相对无约束组下降超过 5%，方向成立（说明约束有实质隐性代价），可继续做"约束强度扫描"；若两者基本无差异，写出负结果即可关掉，成本也就几天。
- **工作量**：3–5 天。

### D2 对比式步骤标签：用"差异集合"替代 Monte Carlo 软标签（A 级，主推）

- **来源**：G7、G12。
- **一句话假设**：在功能正确性任务上，把"错误候选 vs 正确候选"的代码差异集合映射回思路步骤，得到的步骤标签比"每条步骤采样若干 continuation 求平均通过率"的标签噪声更小，步骤排序相关性更高。
- **为什么值得做**：我们踩的坑正好是标签方差——每个节点只有 2 条 continuation，`step_label` 是 Monte Carlo 估计。T03.5 是在"补到 4 条"这条路上加成本；差异集合标签提供的是另一条路：**不靠采样、直接从成对数据里读出哪一步错了**。SecCodePRM 已经证明这套机制在安全任务上可行（差异对齐 + AST 传播），但**没有人把它用到功能正确性任务上**。
- **最小实验**：
  1. 在 train-50 固定候选池上筛出"同一题既有错误候选又有正确候选"的题目（现有数据里有 38/50 题有解）；
  2. 对每一对（错误候选，正确候选）做行级/语句级差异对齐，把差异行归属到对应的思路步骤，得到步骤级标签；
  3. 与现有软标签在同一批节点上做一致性对比：`test-retest`（若有多个正确候选可以互相比）、与 private pass rate 的 Spearman；
  4. 用同一套 3B LoRA 配置分别训练两种标签的评分器，比较步骤排序与选择结果。
- **指标**：标签自一致性（同一节点的两个独立估计之间的相关性）、步骤排序 Spearman、Best-of-N 相对 public 选择的增益。
- **资源**：纯 CPU 分析 + 复用现有 3B 训练链路；新增成本只有"修复候选"的生成（可用 GVR 的重写模型产出，或者直接复用已有正确候选）。
- **风险**：APPS 候选普遍很短（多数只有 1 个顶层函数），差异对齐可能退化成"整段不同"，此时标签与传统标签等价；这本身就是要测量的现象。
- **判定标准**：标签自一致性 ≥ 0.7 且步骤排序 Spearman 相对现有软标签提升 ≥ 0.10，则继续；否则说明"差异集合"在短代码上信息量不足，方向关闭。
- **工作量**：5–7 天。

### D3 自适应粒度：把"步骤定义"从超参数变成可观测统计量的函数（A 级）

- **来源**：G12 与 `阶段4_研究假设一页纸.md` 的 S0–S3。
- **一句话假设**：步骤粒度的最优取值可由候选代码的静态结构统计量（顶层函数数、分支/循环数、AST 深度、思路步数）预测；按此自适应选档，比任何固定粒度都好。
- **为什么值得做**：这是现有假设的直接升级版。现有版本只声明"函数化在单函数任务上退化"，新版本给出**可计算的粒度选择规则**，并把它做成一个可复现的 predictor。SecCodePRM 用 `\n\n` 切分 + AST 调整边界，正好提供了"块级切分"这一档，于是粒度谱系变成四档：整段 / 函数 / 语义块（AST）/ 思路步。
- **最小实验**：在 train-50 上先做零训练的部分——计算每个候选的结构统计量，用回归或简单阈值规则预测"选哪一档最能让步骤标签的区分度最大"（区分度用步骤分数与最终 private 结果的相关性衡量）；再对 4 档粒度各训一个轻量 head 验证相关性排序。
- **指标**：各档粒度下的步骤排序 Spearman、粒度选择规则的准确率、以及无解题目（12/50）上的表现是否如预期无增益。
- **资源**：静态分析用 Python 的 `ast` 模块即可；训练复用现有管线。
- **风险**：50 题样本量太小，规则很容易过拟合，必须留题目级 hold-out。
- **判定标准**：自适应档在 hold-out 题目上的 Spearman 不低于最好的固定档，且在选择规则上能被解释（例如"函数数 = 1 时落到思路步档"）。
- **工作量**：4–6 天。

### D4 监督来源的正面比较：执行反馈 vs 静态差异（B 级）

- **来源**：G10。
- **一句话假设**：在同一个候选池上，"执行反馈"与"静态差异集合"两种监督来源给出的步骤排序不同；当公开测试覆盖不足时（我们有 5/200 条 public 全过而 private 全败的候选），静态差异标签更稳。
- **为什么值得做**：现有工作里这两条线是分开的（CodePRM 要执行、SecCodePRM 不要），没人做过同条件比较。我们有 `public_feedback / private_feedback` 与执行日志，正好能做。
- **最小实验**：把 D2 的差异标签与现有 public 反馈标签放在同一批节点上，按"public 是否覆盖了真实错误"分层比较两者的一致性：在 public 全过但 private 全败的候选上，差异标签是否仍能指出问题步。
- **指标**：分层后的标签一致性、错误步定位准确率（以修复后是否通过 private 为最终判据）。
- **资源**：不需要新 GPU 工作；依赖 D2 的标签构造工具。
- **风险**：定位准确率的 ground truth 只能靠"改对是否通过"来近似，评测有噪声。
- **判定标准**：在"public 反馈不可靠"的子集上，静态差异标签的定位准确率显著高于执行反馈标签。
- **工作量**：与 D2 叠加，额外 3–5 天。

### D5 双目标选择：正确性 + 安全性（B 级）

- **来源**：SecCodePRM 的 CWEval 报告方式（`func@k` 与 `func-sec@k` 并列），以及其关系一节提出的"双通道 PRM"。
- **一句话假设**：把安全性当作第二个目标加入 Best-of-N（先按安全分筛掉危险候选，再用正确性分挑选），能在不明显损失功能正确性的前提下降低生成代码的安全风险。
- **为什么值得做**：这是一个天然的交叉题，而且**不需要训一个 7B 安全 PRM**：用轻量静态分析（Bandit、Semgrep 的社区规则、或 `pylint-bugbear`）给候选打安全分即可，重点在"多目标选择的收益是否真的存在"。
- **最小实验**：在现有 APPS 候选池（已有 200 条候选代码）上跑轻量静态分析，标注危险候选；比较三种选择策略的功能通过率与"危险代码进入 top-1 的比例"：(a) 纯 public 通过率；(b) 纯安全分；(c) 安全过滤 + public 排序。
- **指标**：`pass@1`（功能）、危险候选进入 top-1 的比例、安全过滤的误杀率。
- **资源**：纯 CPU，8GB 机器足够；不需要 CodeQL。
- **风险**：APPS 入门题里的安全风险类型很窄（多数是边界与异常处理），静态分析信号可能弱；需要先看危险样本比例，比例过低就放弃。
- **判定标准**：危险候选比例 ≥ 5% 且策略 (c) 的 `pass@1` 下降 ≤ 2 个点，方向成立。
- **工作量**：5 天。

### D6 局部重写的"可补全性"约束（B 级）

- **来源**：G6（LAVE 的"可扩展性"不变量）与 CodePRM 的 GVR Refine 阶段。
- **一句话假设**：GVR 的 Refine 阶段让模型整段重写代码，会引入"改完连语法都不完整"的失败；若把重写限制为**受语法约束的局部编辑**并要求每一步中间结果都可补全成合法程序，修正成功率与接受后退化率都会改善。
- **为什么值得做**：LAVE 的可靠性不变量在自回归生成里是自动成立的，但在**代码编辑/局部重写**这个场景里恰恰不成立——编辑过程中间态可以既非完整的也非可补全的。这给"LAVE 的思想"找到了一个自回归侧的落点。现有 T05 的 GVR 分析里已经要分离记录"接受率 / 接受后退化率"，正好是天然的评价位。
- **最小实验**：对现有 GVR 记录中"重写失败"的样本做错误分类（语法错误 / 未改到目标步 / 引入新错误）；对语法错误类样本改用在局部区域做受限生成（只允许改被定位的那几行，生成后用解析器验证），比较修正成功率。
- **指标**：不接受率、修正成功率、接受后退化率、重写后的语法合法率。
- **资源**：3B 生成 + `ast.parse` 验证，本机可行。
- **风险**：样本量小，失败样本可能只有几十条。
- **判定标准**：语法类失败的占比 ≥ 30%，且受限重写在「语法合法率」上有可观测提升。
- **工作量**：5–7 天。

### D7 消费级硬件上"约束的代价"到底是多少（A 级，可作 D1 的副产品）

- **来源**：G11、G2。
- **假设**：在 1.5B–3B 模型与消费级 GPU 上，约束解码带来的吞吐损失与它换来的语法合法性之间存在一个可测量的交换比；这个交换比在批量较大时明显恶化。
- **为什么值得做**：PSC 明确说"模型越大，吞吐差异越不显著"，反过来说**小模型正是约束开销最显著的区间**，而这个区间恰好是我们所处的区间。三篇 GCD 论文都在 7B 以上做实验，没人报告小模型上的数字。
- **最小实验**：同一台机器上，对 Ollama 的 1.5B 与 3B，分别在无约束 / GBNF 约束下生成同一批 APPS 题的代码，记录 tokens/s、首 token 延迟、总时长与语法合法率；批量从 1 扫到能承受的最大值。
- **指标**：tokens/s 下降比例、语法合法率、单位时间产出的"有用候选"数。
- **资源**：本机即可，无需训练。
- **判定标准**：不需要 Go/No-Go，这是一组测量数据，本身就可以作为 D1 的任何结论的支撑材料。
- **工作量**：2 天。

### D8 标签范式比较：软标签、硬标签、差异标签的三方对照（B 级，D2 的扩展）

- **来源**：G8、G12。
- **假设**：在步骤级监督里，标签形式（连续软标签 / 二元硬标签 / 差异集合标签）的影响大于输入模态（是否带代码、是否带执行反馈）的影响。
- **为什么值得做**：CodePRM 的结论是"执行反馈这个模态重要"，我们的小规模实验却发现模态带来的差异不明显，怀疑瓶颈在标签本身。把三个标签形式在同一条管线上正面比较，能把"模态问题"和"标签问题"分开。
- **最小实验**：同一候选池、同一划分、同一随机种子，只改标签形式，跑三组 3B LoRA，报同一套指标。
- **指标**：步骤排序 Spearman、Best-of-N 增益、`pass@1`，并附 bootstrap 区间（小样本必须报）。
- **风险**：3 组 × 3 seed 的生成成本要提前算清楚；宁可只跑单 seed 并明确标注探索性。
- **判定标准**：三种标签形式之间的差异大于"带不带执行反馈"的差异，则该结论有价值。
- **工作量**：7–10 天。

### C 级方向（需要超出当前资源，只作为远期储备）

| 方向 | 来源 | 为什么现在不能做 |
| --- | --- | --- |
| 复现 PSC 的预处理与掩码加速 | G3 | SQL 预处理 255.3 GiB 内存、实验用 8×A100；本机最多验证 Java/JSON 的小规模子集 |
| 训练一个安全 PRM（SecCodePRM 缩小版） | SecCodePRM | 需要 4×80GB 与 CodeQL 标签流水线；退一步可以做 D5 的静态分析版本 |
| 扩散 LLM 上的约束解码复现 | LAVE | 最小的 LLaDA-8B 也需要远超 8GB 的显存；可以作为纯阅读/汇报材料 |
| 真实仓库级（SWE-bench 类）过程奖励 | — | 需要容器化依赖环境，单机不可行；可先做静态调用图分析（见现有假设 8.5 节） |

## 3. 优先级与路线

排序依据三个乘数：**与导师方向的相关性 × 本机可行性 × 新颖性空间**。

| 优先级 | 方向 | 相关性 | 可行性 | 新颖性空间 | 建议 |
| --- | --- | --- | --- | --- | --- |
| 1 | **D2 对比式步骤标签** | 高（直接治 No-Go 的病因） | 高（复用现有管线） | 高（无人做过功能正确性版本） | 主线，先做 |
| 2 | **D1 约束解码的候选池代价** | 中高（解释候选池上限） | 高（Ollama 直接支持） | 高（三篇论文都没做） | 主线，可与 D2 并行 |
| 3 | D3 自适应粒度 | 高（现有假设的升级） | 高 | 中 | 紧随 D2，共用数据 |
| 4 | D7 小模型约束代价测量 | 中 | 高 | 中 | 作为 D1 的副产品，2 天 |
| 5 | D4 监督来源比较 | 中高 | 中 | 中高 | 挂在 D2 之后 |
| 6 | D6 局部重写的可补全性 | 中 | 中 | 高 | GVR 分析做完再上 |
| 7 | D5 双目标选择 | 中 | 中 | 中 | 先看危险样本比例再决定 |
| 8 | D8 标签范式三方对照 | 高 | 中 | 中 | 成本最高，放最后 |

### 两条互不冲突的路线

**路线 A（过程奖励主线，接导师方向）**：D2 → D3 → D4 → D8。
核心问题从"要不要带执行反馈"换成"**步骤标签是怎么来的、方差多大**"。这条路的立论点是：在 3B 小模型 + 50 题规模上，模态带来的信息增量已经被执行反馈提供的粗信号吃掉了，剩下的增量只能来自更干净的步骤标签。

**路线 B（候选池质量，接约束解码三篇）**：D7 → D1 → D5。
核心问题从"怎么排序候选"换成"**候选池里到底有没有好东西、约束解码把它压成什么样了**"。这条路的立论点是：排序方法的上限由候选池决定，而候选池正被约束解码悄悄改变。

两条路线共用同一批数据和执行器，**D2 与 D1 可以同时开**，D3 的数据能直接被 D8 复用。若只允许选一条，选路线 A。

## 4. 明确不要做的

1. **重复当前 No-Go 的配置**。0.514 对 0.533 对 0.683 这个结果已经稳定，重跑只是消耗时间。要动的是标签、粒度、候选池这些上游变量。
2. **追大算力复现**。SecCodePRM 的 4×80GB、PSC 的 255 GiB 预处理、LAVE 的 dLLM 推理，都不在能力范围内；把它们当作"知道存在即可"的文献。
3. **把 public 选择器和 PRM 混为一谈**。这条约定已在仓库记忆里记着，继续遵守。
4. **在没有 hold-out 题目级切分的情况下报告粒度规则的效果**。50 题规模下过拟合几乎是必然的。
5. **把候选池太小（4 个）导致的天花板问题归因给评分器**。12/50 题目在候选池里没有正确答案，这是候选池的限制，任何排序器都无法弥补，报告时必须单列。

## 6. 一页速记

1. 四篇论文给出的最有价值的东西，集中在它们的**局限性章节**：作者自己说没做的地方，就是最省力的切入点。
2. 我们的 No-Go 结果与这些空白有一条共同的解释链：**候选池质量 → 步骤标签质量 → 排序器上限**，上游决定下游。
3. 本机最该先做的两件事：用差异集合重造步骤标签（D2），以及量化约束解码对候选池的代价（D1）。
4. 三篇约束解码论文都停在"大模型 + 大算力"这一侧，**消费级小模型这一侧的代价曲线是空白**，而这些论文的技术恰好在小模型区间收益最大。
5. 判断一个方向值不值得做，先问它需不需要训练：D1、D3、D7 的大部分工作不需要 GPU，先做完再决定要不要训。
