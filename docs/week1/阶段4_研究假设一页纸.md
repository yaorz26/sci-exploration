# 研究假设一页纸（阶段 4）

生成日期：2026-09-10
数据基础：`apps-train-introductory 50 题 × 4 候选`（Qwen2.5-Coder 3B，seed 42，固定候选池）
证据来源：`阶段2_手工观察素材.md`、`reports/neural_codeprm_train50_seed42_diagnostic_2026-09-05.json`

---

## 一句话

> 在函数式代码生成任务上，"函数"不是有效的 subtask 单位：绝大多数候选只有一个顶层函数，
> 过程奖励因此退化为结果奖励；真正有区分度的是**思路步骤**，而现有代码 PRM 的步骤定义
> 与任务形态不匹配。

## 1. 观察到的现象（可复核）

| 编号 | 现象 | 数值 | 复核方式 |
| --- | --- | --- | --- |
| O1 | 候选代码绝大多数只有 1 个顶层函数 | **183 / 200**（另 2 条 3 个函数，15 条语法错误） | `tmp/observation_stats.py` §A |
| O2 | 同一批候选的模型思路步数分布 | 1 – 16 步，中位数 5 步，均值 5.61 | `tmp/observation_stats.py` §A |
| O3 | 公开测试反馈与私有测试结果的排序一致性 | Spearman = 0.825 | `tmp/observation_stats.py` §B |
| O4 | 公开测试"全过但私有全败"的候选 | 5 / 200 | 同上 |
| O5 | 公开测试"全败但私有全过"的候选 | 2 / 200 | 同上 |
| O6 | 直接用 public 通过率选择后仍不能完全通过 private 的题目 | 27 / 50（生成顺序口径；同分取序号小者） | `阶段2_手工观察素材.md` §0.2 |
| O7 | 候选池里根本没有正确答案的题目 | 12 / 50 | 同上 |
| O8 | 学习到的神经过程评分器未超过 public 选择 | 0.514（神经） vs 0.533（首候选） vs 0.683（public），后 13 题 | 诊断报告 `fixed_baselines` |

## 2. 对现象的解释

- **O1 + O2 放在一起**说明：在这类任务上，“函数”与“思路步骤”是两种数量级不同的划分（1 个 vs 最多 16 个、中位数 5 个）。按 FunPRM 的定义，183/200 个候选只有 **1 个步骤**，步骤级过程监督没有可评的东西。
- **O3–O6** 说明：执行反馈并不像论文假设的那样总能定位错误。它给出的是"程序级"通过率，而错误可能集中在某一个思路步骤或某一个分支上；当公开测试覆盖不足时（O4），反馈甚至会把定位引向错误方向。
- **O8** 说明：当步骤定义不可靠、候选池又小时，学习到的过程分数很难提供超出执行反馈的额外信息。这与 CodePRM 论文的关键分析（"不给代码和执行反馈的传统 PRM 接近随机"）方向一致，但原因是**步骤划分**而不是**输入模态**。

## 3. 最小方法改动（一次只改一个变量）

> 把步骤定义从"函数"改为"**任务自适应的语义步骤**"：
> 在函数式单函数任务上以思路步骤为步骤单位；在模块化多函数任务上保留函数级步骤；
> 由候选代码的结构复杂度（顶层函数数、分支/循环数）自动选择，而不是全局固定。

对照实现（同一候选池、同一划分、同一随机种子）：

| 代号 | 步骤定义 | 说明 |
| --- | --- | --- |
| S0 | 单步（整段代码） | 退化的过程奖励 = 结果奖励，作为下界 |
| S1 | 函数级 | 等价于 FunPRM 设定 |
| S2 | 思路步骤级 | 等价于 CodePRM 设定 |
| S3 | 结构自适应（本假设） | 按 O1/O2 的分布自动落档 |

## 5. 实验设计（最小版）

| 项目 | 内容 |
| --- | --- |
| 研究问题 | 步骤定义与任务形态不匹配时，过程奖励是否还有效？自适应粒度能否恢复其收益？ |
| 基线 | 首候选、public 通过率选择、private oracle（上限，仅分析）；S0/S1/S2 |
| 自变量 | 步骤定义（4 档） |
| 控制变量 | 题目集合、生成模型、候选数（4）、划分（前 37 / 后 13）、随机种子 |
| 指标 | private pass rate、pass@1、步骤排序 Spearman、错误定位准确率、修正成功率与退化率 |
| 消融 | 去掉结构自适应 → 退回固定粒度；去掉结构化反馈 |
| 失败分析 | 按错误类型（`wrong_answer 109 / runtime_error 25 / syntax_error 15 / timeout 2`）与题目难度分层 |
| 明确不做 | 7B 训练、Codeforces、OS 级沙箱、官方 APPS test（当前条件不允许 B 级目标） |

## 6. 可能的反例与风险（先想清楚，避免被问倒）

1. **O1 是 APPS 特有的**：APPS 的 starter code 本身就是单函数骨架，所以模型自然只写一个函数。FunPRM 用的 LiveCodeBench/BigCodeBench 是开放式生成，函数组织由提示词决定。**结论必须限定表述**："在 starter-code 约束下的函数式任务上"。
2. **只有 50 题、4 候选、3B 模型**：所有数值只作探索性证据，不能外推。
3. **12/50 无解题目**说明生成器弱，收益可能来自"选择"而非"步骤评分"，需要分开报告。
4. 若 O1 在你复核的 5 题里不成立（例如你发现语义 subtask 与函数确实一一对应），**该假设应被推翻**，此时转向假设 C（结构化反馈）。

## 8. 边界与升级路线（当最终目标是大模型 + 复杂项目时）

### 8.1 先说清楚上文的边界

第 1–7 节的结论只在“APPS 函数式入门题”上成立。**它不能被说成“函数不能当步骤”。**
它真正给出的是粒度的**下界端点**：当函数数 = 1 时，函数级步骤退化为单步，过程奖励没有可评的东西。
换言之：我们要证明的是“**粒度存在有效区间**”，而不是“函数这个定义错了”。

### 8.2 大项目上问题会反过来变成“函数太多”

| | APPS 入门题（当前数据） | 真实项目（最终目标） |
| --- | --- | --- |
| 函数个数 | 绝大多数 1 个 | 几十到几百个，跳文件/跳类 |
| 失败模式 | 粒度**过粗**：函数=整体，无信息 | 粒度**过细**：成本爆炸、语义碎裂、奖励噪声大 |
| 结构 | 单个函数内部就是一条链 | 函数之间是**调用图**（有向图）：互相调用、循环、递归、回调 |

### 8.3 统一假设（U 形粒度）

> 步骤粒度过粗会失去定位力，过细会失去语义与稳定性；
> 存在一个**随代码结构自适应的有效粒度区间**。

这不是两个假设，而是同一个假设的两端。当前数据占了左端点，下一步实验要去测右半段。

### 8.4 链 vs 图：一个比“粒度”更硬的问题

所有现有代码 PRM（CodePRM、FunPRM）都默认步骤是**一条链**：步骤 1 → 步骤 2 → …，
奖励可以沿链回传或聚合。但真实项目的函数构成**有向图**：

- 拓扑顺序不唯一，哪一步算“第 3 步”没有定义；
- 同一个函数可能在多个位置被调用，局部正确 ≠ 整体正确；
- 递归/回调会让“步骤”无法线性排列；
- 错误可能出现在**调用关系的缺漏**上，而不是某个函数内部。

→ 这是一个可以在**不训练任何模型**的前提下验证的结构性问题：先看函数之间的调用图是不是链。

### 8.5 下一步要采集的三个统计量（不需要 GPU）

1. 目标数据集里每个样本的**顶层函数数 / 类数 / 方法数**分布；
2. **调用图的形状**：最长链长度 vs 图直径、分支数、是否有递归；
3. 模型生成的**思路步数**与函数个数的比值（衡量两种步骤定义的错位程度）。

数据集候选（按贴近“复杂项目”程度排序）：

| 数据集 | 特点 | 能否本地执行 |
| --- | --- | --- |
| **ClassEval** | 类级任务，天然多方法、有测试 | 可以 |
| **BigCodeBench** | 需调用多个库函数，多函数倾向强 | 可以 |
| **LiveCodeBench** | FunPRM 主实验数据集，便于对比 | 可以 |
| **RepoBench / SWE-bench** | 真实仓库、跨文件，最接近最终目标 | 需 Docker 与依赖环境，单机不现实，先只做静态分析 |

### 8.6 必须提前写清的风险

1. **模型越强，这条路越难**：候选之间的差距变小，public/private 冲突变少，
   过程奖励可提供的额外信息也变少（信号冗余风险在强模型上更严重）。
2. **评测成本**：真实仓库的测试需要容器与依赖，不是单机能完成的，可能需要换成
   静态分析 + 少量可执行样本的混合方案。
3. **功劳归属**：大项目上的收益可能来自“选择”而不是“过程评分”，必须分开报告。
