# 对《科研执行清单（一天版）》的反驳与修订要求

审查日期：2026-09-10  
审查对象：`docs/科研执行清单.md` 及其引用的阶段材料、原始记录和实验报告

## 结论

该清单可以作为一天的**科研审计与假设生成**安排，但不能被当作已经验证研究假设的计划，更不能据此得出“函数不适合作为过程步骤”或“自适应粒度能超过 public 选择”的结论。

当前可靠的研究切入点是：

> 在 APPS starter-code 约束下，基础生成器常不产生 FunPRM 所需的模块化函数结构；应研究函数级步骤的适用边界，以及 Chain-of-Function（CoF）提示或其他粒度策略能否提供超出 public 执行反馈的增量信息。

这与“FunPRM 的函数步骤无效”是两件不同的事。

## 1. 对论文对应关系的反驳

### 1.1 不能把本地函数计数当作对 FunPRM 的直接检验

FunPRM 不是“拿任意生成代码数一数函数”的方法。它先通过 Chain-of-Function 提示要求模型：在逻辑可独立或可隔离时拆出顶层函数、以高层函数在前的方式组织代码、并为函数写 docstring；之后才将函数作为 PRM 步骤。

本地 200 个候选来自 APPS 函数式 starter-code 任务，且未采用该 CoF 提示。观察到 `183/200` 个可解析候选只有一个顶层函数，说明的是：**当前生成协议没有产生 FunPRM 预期的函数化轨迹**。这构成迁移边界的线索，不构成对 FunPRM 本身的否定。

因此，以下表述不成立：

> 函数不是有效的 subtask 单位。

应改为：

> 在当前 APPS starter-code 与基础生成提示下，函数级划分常退化为单步；是否可通过 CoF 或自适应划分恢复有效的过程监督，仍需实验检验。

### 1.2 “函数数少于 thought 数”不是语义不一致的直接证据

本地 thought 列表包含大量格式性或重复性内容，例如“Steps:”“Implementation”“Here is the Python function…”。它们未必是独立、可验证的语义 subtask。

所以“一个函数 vs 五个 thought 条目”只能说明**两种原始文本的切分数不同**，尚不能证明函数边界与语义子任务边界不一致。要证明后者，必须先写出人工标注规范，至少明确：

- 什么算独立语义操作；
- 格式性、复述性 thought 是否剔除；
- 一个 subtask 是否允许跨函数；
- 错误位置如何由代码、题意和测试证据共同判定。

未完成这些定义之前，`183/200` 应被称为“筛查信号”，而不是“第一手证据”。

## 2. 对 public-feedback 论证的反驳

### 2.1 “12/50 无正确答案”混淆了两个定义

当前材料中的 `12/50` 是“该题四个候选的 private pass rate 都为 0”，而非“候选池没有完全正确解”。在固定 seed 42、按生成顺序同分取先的口径下，应同时报告：

| 事件 | 题目数 |
| --- | ---: |
| 四个候选的 private pass rate 都为 0 | 12 / 50 |
| 候选池没有完全正确候选 | 26 / 50 |
| 候选池存在完全正确候选 | 24 / 50 |
| public 选择得到完全正确候选 | 23 / 50 |

因此，public 选择只在 **1/50** 道“候选池本有完全正确解”的题上错过了完全正确候选。将 `12/50` 直接称作“候选池里根本没有正确答案”，并据此界定选择方法的天花板，是不准确的。

### 2.2 “27/50 未完全通过”不是 public 选择失效的证据

`27/50` 表示 public 选中的候选没有 private 全过；其中大部分是候选池本身没有完全正确解，而非 public 从可选的正确答案中选错。

固定候选池上的可观测事实是：

| 指标 | 数值 |
| --- | ---: |
| public 选择 private pass rate | 0.609 |
| private oracle private pass rate | 0.625 |
| 二者差距 | 0.016 |
| public 选择低于该题池内最优 pass rate | 4 / 50 |

这说明当前候选池中，任何试图超越 public 选择的方法可获得的上限极小。它不适合用来证明 S2/S3 的最终选择收益；更适合作为“public 信号很强、但存在大量并列”的诊断数据。

### 2.3 pooled Spearman 不能支持“public 常误导”

清单引用的 `Spearman(public, private)=0.825` 是跨 50 道题、200 个候选的汇总相关性，会混入题目难度差异；它不是候选选择问题的充分指标。按同一题内的候选两两比较：

| 指标 | 数值 |
| --- | ---: |
| 题内候选对数 | 300 |
| public 并列的候选对 | 191 |
| public/private 均不并列的候选对 | 86 |
| 其中排序一致 | 81 / 86（94.2%） |

所以应将结论改为：public feedback 在当前数据上有强排序信号，但粒度粗且经常并列；少数反例可做失败案例，不能概括为 public feedback 普遍误导。

## 3. 数据与可复现性问题

### 3.1 同分规则在两个统计脚本中不一致

`tmp/observation_stats.py` 对每题候选先按代码文本排序；`tmp/build_observation_material_v2.py` 保留 JSONL 中的生成顺序。两者对同分 public pass rate 会选到不同候选，因而分别得到不同的“public 选后未全过/选错”计数。

必须冻结以下协议：

1. 在原始反馈记录中写入不可变的 `candidate_index`；
2. 明确同分规则，例如“最小生成序号优先”；
3. 所有统计、训练、汇报共用同一个选择函数；
4. 同时报告 public 并列率，避免把任意 tie-break 当成方法能力。

### 3.2 错误类型的来源混用

阶段 2 的 private 错误类型统计为 `wrong_answer=102, none=56`；阶段 4 使用 `wrong_answer=109, none=49`。后者来自“private 错误类型为空时回退到 public 错误类型”的混合口径，不能称为 private 错误类型分布。

后续表格必须明确标注为以下之一：

- private error type；
- public error type；
- public/private fallback error type。

### 3.3 素材生成脚本不能直接重建当前文件

`tmp/build_observation_material_v2.py` 的输出位置仍是 `D:\\yaorz\\research\\阶段2_手工观察素材.md`，而当前正式材料在 `D:\\yaorz\\research\\docs\\阶段2_手工观察素材.md`。直接重跑会产生另一份文件。清单不应声称当前 `docs` 内材料可以由该脚本直接复现，除非先统一路径和产物哈希。

## 4. 对人工观察实验的反驳

从按异常程度挑出的 5 道题中再只人工标注 3 道，不能估计“函数与语义 subtask 不一致率”，也不能估计“public 反馈定位率”。这属于**目的性案例研究**，不是随机样本统计。

正确做法是把目标拆开：

| 目标 | 可接受做法 |
| --- | --- |
| 展示失败模式 | 保留当前 5 道目的性案例，明确称为 illustrative cases |
| 估计发生比例 | 另抽取随机或按错误类型分层的候选样本 |
| 评估错误定位 | 定义“直接定位 / 缩小范围 / 无法定位”，记录证据来源 |
| 支持人工结论可信度 | 预先给标注指南；有条件时由第二位标注者复标并报告一致性 |

特别是 `wrong_answer: output mismatch` 通常并不能仅靠执行反馈定位到代码中的某个 subtask。人工阅读题目和代码后得到的判断可以用于案例分析，但必须与“反馈本身能够定位”的结论分开。

## 5. 对 S0--S3 实验设计的反驳

S0--S3 目前只有名称，没有可比较的操作定义：

- S1 只应称作“函数级局部基线”，不能称“等价于 FunPRM”；FunPRM 还包含 CoF 生成、Monte-Carlo 部分奖励、元奖励校正和生成式 PRM。
- S2 的 thought 是原始 LLM 列表还是清洗后的语义步骤？步骤如何合并、剔除、对齐？
- S3 的“按结构自动落档”没有给出分界阈值、切分算法、评分聚合函数或推理时成本。
- “Spearman 提升 >= 0.10”“相关 < 0.7”等阈值没有统计依据；50 题、尤其 13 道 held-out 题下不应采用机械阈值决定假设成败。

在实际运行前，S0--S3 至少需要预注册：输入、步骤生成规则、标签构造、评分聚合、同分规则、成本预算、主指标和按题目 cluster bootstrap 的置信区间。

## 6. 对“标签方差或信号冗余”二分法的反驳

将 continuation 从 2 条补到 4 条是合理的诊断，但“test-retest 相关性低即标签方差、高即信号冗余”并不成立。相关性还受标签取值范围、题目难度混合、同一题内节点依赖和生成器随机性影响。

应分成两个独立检验：

1. **标签稳定性**：对同一节点比较两组独立 continuation 均值，例如 `(C1,C2)` 对 `(C3,C4)`，报告 Spearman、RMSE 或 ICC，并按 problem cluster bootstrap 给区间。
2. **增量信息**：在严格 held-out problems 上比较 public-only、PRM-only、public+PRM 的排序和选择结果；报告相对 public 的配对差异及置信区间。

若标签稳定而 PRM 对 public 没有增量，才能称为“当前特征/目标相对 public 冗余”；仍不能推广成过程奖励整体无效。

## 7. 最低修订要求

在开展新训练或向导师汇报前，应完成以下修改：

- [ ] 将研究定位改为“APPS starter-code 约束下 CoF/函数步骤的迁移边界”，不再反驳 FunPRM 本体；
- [ ] 修正 `12/50`、`26/50`、`24/50`、`23/50` 四类候选池统计及其文字定义；
- [ ] 将 public 的主分析改为题内、显式 tie-break 的选择分析；
- [ ] 统一候选编号、同分规则、错误类型来源和脚本输出路径；
- [ ] 将 5 题观察称为目的性案例研究，不报告为总体不一致率；
- [ ] 为语义 subtask 与错误定位提供人工标注代码本；
- [ ] 将 S0--S3 写成可执行的实验协议；
- [ ] 将“标签方差/信号冗余”改为稳定性检验与增量信息检验。

## 8. 修订后的可汇报口径

> 我在 APPS starter-code 任务的固定候选池中发现，基础生成器很少产生 CoF 所要求的多函数结构，因此函数级过程监督可能退化。这个现象尚不构成对 FunPRM 的反证。当前 public 选择已接近候选池 oracle，我会先冻结选择协议、核对候选池上限，并检验 CoF 或可操作的语义步骤定义能否在 held-out 题目中提供超出 public feedback 的增量信息。
