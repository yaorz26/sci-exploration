## 结论

1. 该反驳文档的**数字主张全部复核通过**（12 条里 12 条），可以据此修订清单。
2. 有 **1 处推论偏强**：第 2.2 节用「public 选择与 oracle 只差 0.016」论证"上限极小"，而这个 0.016 是四种同分规则里最乐观的一个；另外三种规则给出的差距是 0.041 / 0.058 / 0.077，有解题目命中率从 23/24 降到 20–22/24。规则本身带来的波动大于被当作 headroom 的那个数字。这是本次审查发现的最重要问题。
3. 有 **2 处论据不准确或与数据不符**：第 1.2 节举的 thought 格式性例子在本数据集里几乎不存在；第 5 节说 S0–S3"只有名称"低估了 `阶段4` 已有的内容。论点方向不变，论据需要替换。
4. 有 **1 处遗漏**：候选题按可用性分三层（12 题全 0 / 14 题只有部分正确 / 24 题含完全正确解），文档只用了前两层的合并口径，漏掉了中间那层——而它恰好是步骤级信号唯一有名义作用空间的子集。

总体判断：**采纳该文档作为修订依据**，但第 2.2 节、第 1.2 节、第 5 节需要按本文档第 2 节改写后再进入正式材料。

## 2. 需要修正的地方

### 2.1 最重要：`0.016` 是最乐观的同分规则下的数字

被审查文档第 2.2 节用"public 选择 0.609 对 oracle 0.625"得出"任何试图超越 public 选择的方法可获得的上限极小"。同一批数据，把同分规则换成另外三种同样合理的写法：

| 候选顺序 | 同分规则 | public 选择均值 | 与 oracle 之差 | private<1.0 | 有解题命中 | 低于池内最优 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 生成顺序 | 取序号小 | **0.609** | **0.016** | 27/50 | 23/24 | 4/50 |
| 生成顺序 | 取序号大 | 0.548 | 0.077 | 30/50 | 20/24 | 8/50 |
| 代码排序 | 取序号小 | 0.567 | 0.058 | 30/50 | 20/24 | 7/50 |
| 代码排序 | 取序号大 | 0.584 | 0.041 | 28/50 | 22/24 | 4/50 |

（oracle 恒为 0.625，池内含完全正确解的题数恒为 24。复核脚本：`tmp/audit_tiebreak_rules.py`）

三种替代规则把差距从 `0.016` 推到 `0.041`、`0.058`、`0.077`，"有解题目命中率"从 23/24 降到 20/22/20。也就是说：**同分规则本身带来的波动（约 0.06）比被当作 headroom 的那个 0.016 大好几倍**。叠加题内 300 对候选里有 **191 对**在 public pass rate 上并列这一事实，可以说在这批数据上"选择"这个动作大部分时候由同分规则执行，public 信号只负责划出一批难以区分的候选。

**结论改写建议**：

> 不能说 headroom 很小。准确的说法是：`0.016` 是四种同分规则里最乐观的一个；同一 public 信号在四种规则下给出的 private pass rate 落在 0.548–0.609 之间，规则变化带来的波动量级与 headroom 相当甚至更大。因此同分规则不是实现细节，它本身就是要被研究与被报告的对象。

这一改写反而给 S0–S3 找到了一个干净的实验位：把过程评分器当作 **tie-breaker**，与"最小生成序号""代码字典序"这类任意规则比。这个对照不需要模型就能先跑一遍上界分析。

### 2.2 第 1.2 节的论据与数据不符

被审查文档写 thought 列表"包含大量格式性或重复性内容，例如 `Steps:`、`Implementation`、`Here is the Python function…`"。实际统计（1122 条 thought 条目）：

| 模式 | 命中数 |
| --- | ---: |
| `Here is the Python function` | **0** / 1122 |
| `Steps:` | 7 / 1122 |
| `Implementation` | 9 / 1122 |
| 长度 < 25 字符 | 97 / 1122（8.6%） |

`Here is the Python function` 这条例子来自 `collect_step_continuations.py` 里的续写提示词模板，本地 200 个候选的 thought 里一条都没有。用"大量"形容 7–9 次命中也不成立。

**可替换的、经得起追问的证据**：**28 / 200 个候选（14%）的 thought 就是流水线硬编码的兜底列表** —— 逐字相同的 `["Parse the input", "Apply the requested operation", "Print the result"]`（`src/generator.py` 第 74 行的默认值）。这类"步骤"由代码生成，与模型推理无关，因此把它们当作语义步骤直接失去意义。再加上 8.6% 的过短条目，足以支撑原结论，而且每一条都能当场重算。

### 2.3 第 1.1 节的证据应当加强

被审查文档的表述是"当前生成协议没有产生 FunPRM 预期的函数化轨迹"。这个说法偏保守。生成提示词原文要求"exactly one Python 3 program"，且 function 模式下要求"exactly the signature in the starter code"。

在这套协议下，`183/200 个候选只有一个顶层函数`接近**定义使然**：提示词已经把输出限定成单程序单签名，模型即使有能力拆函数，也没有被要求这么做。建议改成：

> 该统计在当前生成协议下近似于同义反复（提示词明确要求一个程序、一个签名），它描述的是协议与 FunPRM 设定的不匹配，不能作为关于粒度假设的证据。可作为研究动机，不可作为发现。

这样写虽然更弱，但它挡住了所有可能的"这统计根本说明不了什么"的追问，比现在这版更耐用。

### 2.4 第 5 节对 S0–S3 的描述不准确

被审查文档写"S0--S3 目前只有名称，没有可比较的操作定义"。实际 `docs/阶段4_研究假设一页纸.md` 第 5 节已经给出了研究问题、基线、自变量、控制变量（题目集合、生成模型、候选数、划分、随机种子）、指标、消融与三条可证伪预测。

缺的是 S1/S2/S3 的**操作定义**：切分算法、边界判定、标签构造、评分聚合函数、推理成本。建议改成"缺可执行的操作定义"，并把要求具体化为预注册清单（这一点被审查文档已经列了，保留即可）。

### 2.5 遗漏：候选池应当分三层

被审查文档只用了 `12/50` 与 `26/50` 两个口径。按"池内是否存在能拿到的最高分"分三层更清楚：

| 层 | 定义 | 题目数 | 对方法研究的意义 |
| --- | --- | ---: | --- |
| L0 | 池内最高 private pass rate = 0 | 12 | 任何选择方法都无法改善，是天花板为 0 的死区 |
| L1 | 0 < 池内最高 private pass rate < 1 | 14 | **步骤级/部分奖励唯一有名义作用空间的子集** |
| L2 | 池内存在 private 全过的候选 | 24 | 考验的是"能不能挑对"，也就是排序与同分规则 |

L1 那一层的池内最高分分布为：0.04、0.17、0.31、0.33、0.36、0.5（2 题）、0.67（4 题）、0.75、0.8（2 题）。这一层适合验证"部分奖励能否避免选到最差的候选"。

另外 L0 内部还要再分：12 道里有 **10 道**连 public 也全 0（生成彻底失败），只有 `apps-train-2653` 与 `apps-train-2684` 是"public 有通过、private 全败"。这两道才是 public 反馈误导的干净样本，样本量是 2，报告时必须按案例写，不能当作比例。

## 5. 一页速记

1. 被审查文档的 12 条数字主张全部复核通过，可以采纳。
2. `12/50` 与 `26/50` 是两个不同事件，前者是"四个候选一个私有测试都没过"，后者是"池内没有完全正确解"。文档的更正成立。
3. `0.016` 是四种同分规则里最乐观的一个：另外三种规则下差距变成 0.041 / 0.058 / 0.077，有解题目命中率从 23/24 降到 22/24、20/24。规则带来的波动大于 headroom 本身。
4. 191/300 的题内并列率说明：在这批数据上，"选择"这个动作多数时候在做同分裁决。清单里同时出现的 27/50 与 30/50 就是两种同分规则的结果（30 对应 `tmp/observation_stats.py` 的代码排序口径）。
5. thought 噪声的论据要换成"28/200 硬编码兜底 + 8.6% 过短条目"，`Here is the Python function` 这类例子在本数据集里不存在。
6. 候选池分三层报告（死区 12 / 部分正确 14 / 有解 24），L1 那层才是部分奖励的名义空间。
7. 生成提示词要求"exactly one program + exactly the starter signature"，所以 `183/200` 是协议使然，不是发现。
