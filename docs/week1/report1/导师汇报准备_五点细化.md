## 1. 先讲论文理解：六篇论文放在同一张地图里

### 先说结论：我读了哪六篇，以及它们怎样相关

除核心复现依据 **CodePRM** 和 **FunPRM** 外，我还阅读了 **AdapTrack、PSC、LAVE、SecCodePRM** 四篇论文，共六篇。它们不是都在做同一件事；若不先分清问题，极易把“生成的代码语法合法”“程序功能正确”“程序没有安全漏洞”误当成一个指标。

| 要回答的问题 | 最直白的说法 | 对应论文 | 一个反例 |
| --- | --- | --- | --- |
| 代码能否写成合法形式？ | 括号、关键字、JSON/SQL/编程语言语法是否符合规则；API 名称是否存在 | AdapTrack、PSC、LAVE | 一段 Python 没有语法错误，仍可能把排序方向写反 |
| 程序能否完成题目？ | 对看得见和看不见的输入，输出是否都对 | CodePRM、FunPRM | 程序通过样例，不代表能通过隐藏边界情况 |
| 程序是否安全？ | 会不会引入已知漏洞、危险调用或可被利用的实现 | SecCodePRM | 功能完全正确的 C 程序也可能有缓冲区溢出 |

可以把它想成造桥：约束解码保证“图纸用的是合规符号”；过程奖励模型尝试判断“这座桥最终能不能承重”；安全过程奖励模型再检查“即使能承重，会不会有会伤人的结构隐患”。三者有联系，但不能互相替代。

### 先记住的五个词

| 词 | 零基础解释 |
| --- | --- |
| 候选程序 | 同一道题让模型写出多份答案；每一份都是一个候选。 |
| Best-of-N | 一次生成 N 份候选，再挑一份最可能好的交出去。它不会凭空提高候选池的上限，只能提高挑对的概率。 |
| PRM（过程奖励模型） | 像给解题草稿每一步打分的助教，而不只在整份卷子写完后判“对/错”。 |
| public / private 测试 | public 是方法在生成或修正时可看到的样例；private 是藏起来、只用来做标签或最终验收的样例。后者若被偷看，结果就不可信。 |
| 约束解码 | 模型每写一个 token（可近似理解为一个词或代码片段）时，规则系统把必定违法的下一步挡掉。它保证合法，不自动保证解题正确。 |

### 六篇论文的一句话全景

| 论文（全称见括号） | 先背这一句 | 在整条链中的位置 |
| --- | --- | --- |
| CodePRM（执行反馈增强的代码生成过程奖励模型） | 用“思路 + 已写代码 + 样例运行反馈”评估哪个思路更可能导向正确程序，并尝试修正低分思路。 | 功能正确性：选择与修正 |
| FunPRM（函数即步骤的过程奖励模型） | 把模块化代码中的函数当作步骤，用过程分数从多份程序里挑更好的答案，并校正中间标签的噪声。 | 功能正确性：选择 |
| AdapTrack（不扭曲 LLM 输出意图的约束解码） | 规则挡住某条路后，必要时回退到更早的选择，避免被迫补成违背模型原意的合法代码。 | 约束合法性：质量不被扭曲 |
| PSC（通过解析器栈分类的高效语法约束解码） | 预先把“什么解析器状态允许什么 token”编成可快速查询的表，使严格语法约束不必逐 token 暴力检查。 | 约束合法性：速度 |
| LAVE（Lookahead-Then-Verify） | 为并行填空式的扩散语言模型做语法约束：先向前试探，再确认当前位置不会把未来堵死。 | 约束合法性：可完成性 |
| SecCodePRM（面向代码安全的过程奖励模型） | 给代码片段的安全性打过程分，既可找漏洞，也可在多份功能可用的代码中偏向更安全的一份。 | 安全性：选择 |

### 1.1 CodePRM：为什么要给“思路”打分

**背景与问题。** 数学推理中，一条中间推导常能单独判断对错；但代码生成不一样。模型说“用动态规划”，这句话听起来没问题，最终代码却可能把状态转移、边界或输入输出写错。因此，只读自然语言思路不能可靠判断它有没有用；只等程序写完再判分，又错过了中途修正的机会。

**目的与意义。** CodePRM 想训练一个“代码过程助教”：它不问“这句 thought 在逻辑课上真不真”，而问“从当前 thought 继续走下去，最后产出正确程序的机会有多大”。若能找到真正拖后腿的思路，就有机会让生成器只改那里，而不是整份代码推倒重写。

**研究方式，按步骤理解。**

1. 对一道题，生成多个 thought 和对应代码，形成一棵树；树中的一个节点保存当前思路、代码、public 测试是否通过以及运行反馈。
2. 方法不让模型偷看 private 测试。研究者只在离线标注时，用某 thought 节点下所有后续代码的 **private 通过率均值**，作为该 thought 的分数。可以理解为“从这条思路出发，多次往下写，平均有多大机会成功”。
3. 用这些样本训练 PRM。它的输入不是 thought 单独一行，而是“题目 + 已有 thought 链 + 当前代码 + public 运行反馈”。这样模型能看到计划与实际程序行为是否矛盾。
4. 推理时使用 GVR（Generate–Verify–Refine）：先生成；若 public 未通过，则由 PRM 找低分 thought，再把题目、代码和报错反馈交给生成器修改，并重新生成代码。

**结论该怎样读。** 作者实验表明：去掉代码和执行反馈后，过程评分接近随机；使用 private pass rate 这样的连续标签通常比粗糙的二元标签更有信息；但修正次数越多不必然越好，因为生成器可能把原本可用部分也改坏。真正的结论是“代码与可见反馈让过程监督更有依据”，不是“只要训练 PRM 就必定修好代码”。

**它没解决什么，以及与我的关系。** 它依赖可执行的 public 测试和大量后续展开来构造标签，成本不低；PRM 即使找对问题，生成器也未必改得对。我当前项目复现的是这一类机制的缩小版本：检验过程信号能否在小候选池中帮助选择/修正，不能声称等价复现了论文的大规模树搜索或效果。

### 1.2 FunPRM：为什么把“函数”当作代码步骤

**背景与问题。** 代码不像数学证明那样天然有清晰的步骤。按行评分，几百行程序就有几百个零碎步骤，既贵又难懂；随意按函数切分也不行，因为模型可能把全部逻辑塞进一个函数，或写出没有实际职责的空壳函数。另一个难题是：如果某段半成品代码还没有写完，怎样知道它好不好？常见做法是从它继续补全多次并跑测试（Monte-Carlo），但次数有限时，得到的中间分数会很吵。

**目的与意义。** FunPRM 希望得到较自然、较少的代码步骤，并降低“半成品评分不可靠”带来的误导。它的价值是把过程监督从抽象思路推进到可读的程序结构：哪一个函数更可能已经把任务带到正确方向上。

**研究方式，按步骤理解。**

1. 先用 CoF（Chain-of-Function）提示要求模型模块化编程：把反复出现或复杂的操作抽成函数，先给高层函数，再写辅助函数和文档字符串。这里的函数不是事后硬切，而是生成时就被提示组织成步骤。
2. 每写到一个函数前缀，研究者从这里继续补全 K 次；每个补全程序跑单元测试。通过得多，说明这个函数前缀暂时看起来更有希望，这就是嘈杂的 Monte-Carlo 部分奖励。
3. 完整程序最终能否通过测试，是较干净的结果信号。论文用这个干净信号去学习如何校正前面嘈杂的部分奖励，再训练过程评分器。
4. 推理时为同一道题生成 N 份模块化候选，对每份候选的函数分数做聚合，然后采用 Best-of-N 选择。重点是**挑选**，不是 CodePRM 式逐个 thought 的 GVR 修正。

**结论该怎样读。** 作者报告函数级过程奖励在代码选择中优于只看最终答案的奖励模型，尤其在复杂任务中模块数量会增加。这个结果支持“在合适的模块化生成协议下，函数可以成为有用的过程单位”。它不等于“函数越多越好”，也不等于“普通的一段单函数竞赛代码已具备函数级过程”。

**它没解决什么，以及与我的关系。** CoF 是前提而非装饰；如果提示词要求“只交一个程序、严格保持给定函数签名”，模型很可能只写一个顶层函数，此时根本没有足够的函数步骤可评分。我的初步审计中，候选常只有一个顶层函数，因此当前协议并不适合宣称复现 FunPRM；这首先是**步骤边界/生成协议不匹配**，不是对 FunPRM 的反驳。

### 1.3 AdapTrack：合法代码为何也可能“被规则逼歪”

**背景与问题。** 普通约束解码的做法是：下一步不符合语法或 API 规则的 token 一律遮住，只从剩下的 token 里选。这像输入法禁止错别字，表面很合理。但模型的一个早期选择也许后来才发现走不通；若不回退，系统只能在狭窄的剩余选项中硬选一个合法词，结果虽然合法，却偏离了模型原先最想表达的完整程序。

**一个具体例子。** 模型本来想调用某版本 API 中存在的 `linalg.matrix_rank`，却先高概率写下与 `matrix_` 有关的前缀；当规则发现这个版本没有 `rank` 时，普通贪心约束可能强迫它补成另一个低概率但合法的 `matrix_power`。程序没有“违规”，却可能完全不是原来要做的事。

**目的与意义。** AdapTrack 的目标是：输出一定满足约束，同时尽量保留原模型在“所有合法完整输出”之间的偏好。用数学话说，它希望接近“原模型分布在合法集合上的条件分布”；用人话说，就是“只能走合规道路，但别因为临时封路而把导航强行带到荒唐目的地”。

**研究方式与结论。** 它维护每条分支还可能走到合法终点的估计；新信息显示早期选择没有希望时，方法会拒绝或回退并重采样更早的位置，而不是只修改最后一个 token。论文在 TensorFlow API 版本约束及通用代码基准上报告了比普通约束解码更高的有效准确率；核心贡献是校正约束解码造成的意图扭曲，且无需重新训练语言模型。

**边界与我的关系。** 代价是额外模型调用（论文的不同设定中约增加约 20% 到 60%），并且约束规则本身必须正确。它保证的是“在合法候选中更忠于原模型偏好”，不保证题目功能正确。它可作为未来提高候选池质量的互补工具，但不应替代我当前的 CodePRM 式功能评价。

### 1.4 PSC：怎样让严格语法约束跑得动

**背景与问题。** 严格的语法约束需要知道“当前已写代码的语法状态下，词表中哪些 token 可接”。最直接的方法是每一步拿整个词表逐一送进解析器试验。模型词表可以有十几万个 token，这会把生成时间耗在检查上，而不是模型推理上。

**目的与意义。** PSC（Parser Stack Classification）不改变“哪些 token 合法”的规则，想做的是把得到这张合法 token 掩码的时间大幅压缩。它解决的是工程可行性：如果约束本身慢到无法使用，再完美的语法保证也难落地。

**研究方式，按直觉理解。** 离线预处理阶段，论文分析每个 token 在什么解析器栈条件下能被接受，把大量“试一下这个 token 行不行”的条件合并为一个可查询的自动机/分类器；运行时只观察当前解析器栈，就直接取回完整的合法 token 掩码。对确定性上下文无关语法，论文证明这种加速与原先逐 token 检查在合法集合上等价。

**结论该怎样读。** 作者在 Java、Go、SQL 和 JSON Schema 等语法上报告复杂编程语法的掩码计算最高约 700 倍加速、JSON 约 30 倍，并使端到端吞吐接近不加约束的生成。这里的“快”指规则检查快，不代表程序逻辑更聪明、测试通过率自然更高。

**边界与我的关系。** 它只适用于确定性 CFG，且依赖具体语法和 tokenizer 的离线预处理；预处理内存可能非常大（论文中部分编程语法达到数十至数百 GiB）。所以 PSC 很适合有基础设施的系统研究，而不适合作为当前 8GB 级本地复现的主线。概念上它可与 AdapTrack 结合：PSC 快速给出“哪些选择合法”，AdapTrack 决定“发现走不通时如何回退”。

### 1.5 LAVE：并行填代码时，怎样避免把未来堵死

**背景与问题。** 上面两篇约束工作默认自回归模型从左到右一个 token 一个 token 地写。扩散语言模型（dLLM）更像先把整段代码全放成 `[MASK]`，再并行填不同位置；中间可能出现“开头已填、结尾已填、中间还有洞”的状态。传统解析器只擅长检查连续前缀，无法直接回答这种带洞片段还能否补成合法程序。

**目的与意义。** LAVE 要在上下文无关语法（CFG）下约束 dLLM，并要求一个更强的性质：当前接受的 token 不仅眼前不违法，未来也至少存在一条路能把所有洞补成合法字符串。这叫可扩展性/可完成性。

**研究方式，按步骤理解。** 当模型要在某个空位填 token 时，LAVE 先用模型对其余空位的预测做若干次向前试探（Lookahead），得到可能的完整前缀/补全；随后用解析器验证（Verify）至少有一个试探结果仍可延展成符合 CFG 的代码。若都走不通，就拒绝当前 token 并重采样。它比“只看此刻局部语法”多问了一句：**我现在这样填，会不会把以后的合法完成全部堵死？**

**结论该怎样读。** 论文在多种 dLLM 和基准上报告了比已有扩散模型约束方法更可靠的合法输出与更好的质量/开销平衡。贡献在于解决“中间有洞”的约束问题；不要把它误说成一般自回归模型的万能语法器。

**边界与我的关系。** 试探数量有限、最大输出长度有限时，仍可能有漏判或无法完成的情形；效果也依赖模型给出的试探质量。我的当前生成器是自回归 Qwen 代码模型，并不是 dLLM，因此 LAVE 暂时是理解研究版图和未来可迁移思想的材料，不是当前应直接实现的模块。

### 1.6 SecCodePRM：功能正确之外，代码还要没有已知风险

**背景与问题。** 只看最终整段程序的“安全/不安全”标签太粗：它不能告诉模型危险最早在哪一步出现，也不适合在代码尚未写完时提醒。传统静态分析虽能找一些问题，却不等于一个可在候选之间排序的语言模型过程分数。并且漏洞往往跨函数、跨调用关系，不能只看孤立的一行。

**目的与意义。** SecCodePRM 训练一个安全过程评分器：给完整或部分代码一个从不安全到安全的连续分数。这样同一个信号可用于漏洞检测、对未完成代码的早期预警，以及从多份候选中偏向既能用又更安全的一份。

**研究方式，按步骤理解。**

1. 将代码按空行、函数头和返回结构等规则切成步骤；这只是便于建模的近似步骤边界。
2. 从“含漏洞版本—修复版本”的代码对中找差异，再结合 AST 调用图把风险传播到相关调用者，并辅以专家/静态分析标签，构造步骤级安全标注。
3. 模型输出该步骤安全与脆弱的概率差，得到约在 -1 到 1 之间的过程分数；聚合整段代码时，让低分步骤占更大权重，因为一个严重漏洞就足以让整段程序不可接受。
4. 用这个分数做完整代码漏洞检测、部分代码检测或 Best-of-N 安全引导生成。

**结论该怎样读。** 作者在多个漏洞数据集和安全代码生成评测上报告了有竞争力的检测/生成功能，并显示安全过程分数能改善“功能能跑但有风险”的候选选择。它提示了一个重要事实：**功能测试通过率不是唯一奖励信号。**

**边界与我的关系。** 标注依赖已有漏洞—修复对、规则切分、静态分析和已知 CWE 类型，面对新型漏洞、新语言或跨环境行为会受限；训练与数据管线也远超当前资源。它不是要求我现在把研究方向改为安全，而是提供一个后续可检验的扩展：若未来研究多目标代码选择，安全性应作为与功能性分开的目标和评价集。

### 六篇论文合起来，我现在真正理解的研究链条

```text
语言模型原始生成
        │
        ├─ AdapTrack / PSC / LAVE：先保证“能否合法地生成”，并控制代价或避免走死路
        │
        ▼
形成多个语法/API 合法的候选程序
        │
        ├─ CodePRM / FunPRM：再判断“哪一份更可能把题做对”，选择或修正
        │
        ▼
功能更可信的候选程序
        │
        └─ SecCodePRM：若任务要求，还要判断“其中哪份更安全”
```

我的当前科研任务应留在中间一段：在明确隔离 private 测试的小规模设置中，研究**过程信息是否能在 public 同分或难以区分的候选之间，提供对功能正确性有增益的排序信号**。前端三篇约束论文和后端安全论文用于说明边界、准备追问与规划后续方向，不能被包装成我已完成的实验。

### 明天怎样用这六篇，不让汇报失焦

主汇报只用约 60--90 秒讲六篇的地图，重点展开 CodePRM、FunPRM 和本地复现；其余四篇用来证明我已看清相关方向及其适用条件。可这样口述：

> 我围绕代码生成的过程监督与受约束生成，共读了六篇论文。CodePRM 和 FunPRM 直接回答“如何用过程信号提升功能正确性”，是我复现的核心依据；AdapTrack、PSC、LAVE 分别说明约束解码的质量、速度和扩散模型可完成性问题；SecCodePRM 说明安全是独立于功能正确性的另一条评价轴。因此我没有把六篇方法混做一个系统，而是将当前问题收束为：在小规模、无 private 泄漏的协议下，过程信号是否能改善功能候选的选择。

### 必须避免的说法

- 不说“语法约束保证程序正确”。它只保证规则合法，不能保证算法对。
- 不说“public pass rate 就是 PRM”。它只是直接执行反馈选择器；PRM 是学习到的过程评分器。
- 不说“private 测试能用于推理”。当前协议中 private 只用于标签和最终评价。
- 不说“FunPRM 就是把任意代码按函数切开评分”。它依赖 CoF 先让函数成为有意义的生成步骤。
- 不说“我复现了六篇论文”。我阅读并比较了六篇；当前只在缩小设置中实现/审计 CodePRM 相邻的过程监督闭环。

### 导师可能追问与回答

**问：为什么 CodePRM 要输入代码和执行反馈？**  
答：代码中的 thought 往往只是算法设想，光看它无法决定最终实现是否正确；代码和 public 反馈把这个设想与实际程序行为连起来。它的标签是“从这里继续生成成功的预期质量”，不是给 thought 判逻辑真伪。

**问：FunPRM 为什么不直接按行作为步骤？**  
答：逐行会产生太多零碎步骤、成本高且语义割裂；CoF 试图让相对独立的函数成为可读、可评分的步骤。但如果生成协议只产生一个顶层函数，这个假设便不成立。

**问：既然有约束解码，为什么还要 PRM？**  
答：约束解码回答“这段代码是否符合语言/API 规则”，PRM 回答“它更可能是否做对题”。一段完全合法的代码仍可能算法错误；两者应串联或比较，不能相互替代。

**问：SecCodePRM 是否意味着现在必须把安全加入实验？**  
答：不必。它证明安全是重要但独立的质量轴。当前数据、算力和评价协议都围绕功能正确性，贸然加入安全会改变研究问题；更合理的是先把功能过程信号的协议做干净，再把安全作为后续多目标扩展。

## 3. 诚实汇报结果：已确认的事实与未成功的尝试

### 目的

展示你能区分“稳健事实”“探索性结果”“尚未能解释的负结果”。

### 建议展示：主结果表

固定 APPS train-50、每题 4 候选、3 个生成 seed；下表均用 private 测试评价。

| 方法 | private pass rate | pass@1 | 可以支持的结论 |
| --- | ---: | ---: | --- |
| 首候选 | `0.445 ± 0.028` | `0.333 ± 0.023` | 小模型首个候选稳定有限 |
| 随机候选 | `0.373 ± 0.036` | `0.280 ± 0.035` | 候选池中存在可被选择的质量差异 |
| public pass-rate 选择 | `0.572 ± 0.032` | `0.440 ± 0.020` | public 执行反馈在此协议下具有稳定选择价值 |
| private oracle（仅事后上限） | `0.617 ± 0.007` | `0.473 ± 0.012` | 候选池仍有未被直接 public 选择取到的空间 |

### 对主结果的建议口述

> 首先，一个稳健结论是：在这个固定的小候选池中，直接用 public pass rate 选候选，稳定优于首候选和随机候选。它说明执行反馈有价值，但它不是过程奖励模型。

> 第二，public 选择和 private oracle 仍有差距，但这个差距会受到 public 分数并列以及同分规则的明显影响。因此我不会把单个 tie-break 的结果直接解释成评分器能力，而会把并列组单独作为下一步研究对象。

### 神经 CodePRM 的负结果：应主动讲，但只占 20--30 秒

| 设置 | 结果 |
| --- | --- |
| 数据与划分 | train-50 seed 42；前 37 题训练，后 13 题测试；每节点 2 条 continuation 标签 |
| 最佳神经过程评分器 | 原始候选选择 private pass rate `0.514` |
| 同一测试题的首候选 | `0.533` |
| 同一测试题的 public 选择 | `0.683` |
| 决策 | 当前配置标记为 No-Go，不直接扩展到更多 seed |

建议口述：

> 我的神经 CodePRM pilot 没有超过 public 选择，甚至没有超过首候选。因此我停止了同配置的大规模重复。这个结果不能推出“CodePRM 无效”，因为每个节点目前只有两条 continuation、训练题少、测试仅 13 题，而且过程标签与候选选择目标未必完全对齐；但它已经说明，现有设置没有提取出比直接执行反馈更强的增量信息。

### 简化 GVR：作为补充，不要抢主线

三 seed 的模型驱动 GVR 将 private pass rate 从 `0.445` 提至 `0.477`，pass@1 从 `0.333` 提至 `0.353`；平均每 50 题接受约 3.67 次修正。这个结果可说明“受控重写有小幅净收益”，但规模小、收益远小于 public 候选选择，不能作为主要贡献。

### 必须主动承认的审计发现

不要回避这些问题；它们是你展现科研严谨性的机会。

- public 分数经常并列，不同同分规则会改变结果；原有脚本曾混用“生成顺序”和“代码排序”两种规则；
- `12/50` 是四个候选 private 都为零，不等于没有完全正确候选；真正没有完全正确候选的是 `26/50`；
- 5 道人工案例是目的性抽样，只能说明失败模式，不能估计总体比例；
- 当前单函数比例高，主要是 APPS starter-code 和生成提示造成的协议现象，不能当作 FunPRM 被反驳的证据。

一句总结：

> 我认为这些审计问题不是实验失败，而是帮助我确定“哪些数能报告、哪些数必须重新定义”的必要步骤。

## 4. 提出一个新方向：只给一个、给出可证伪设计

### 推荐题目

> **APPS starter-code 任务中，过程信息能否作为 public-feedback tie-breaker？**

### 研究问题

当多个候选拥有同样最高的 public pass rate 时，public feedback 无法再给出排序。此时，thought、代码结构和 public 执行信息能否在不接触 private 测试的前提下，选出 private 表现更好的候选？

### 为什么不是凭空想法

已有三 seed 的静态审计显示：

| 现象 | seed 42 | seed 43 | seed 44 |
| --- | ---: | ---: | ---: |
| 最高 public 分出现并列的题目 | 37 / 50 | 35 / 50 | 33 / 50 |
| 并列组内 private 质量不同的题目 | 12 / 50 | 12 / 50 | 11 / 50 |
| 最高 public 并列组的 oracle 相对组内均匀随机的 private pass-rate 增量 | 0.051 | 0.049 | 0.049 |

这只证明“存在可选择的残余空间”，**不证明过程评分器一定能利用它**。正因为如此，它是可检验的研究问题。

### 最小实验设计

```text
第 1 层：public pass rate 选出最高分候选组
第 2 层：仅在最高分并列时，过程评分器选择一个候选
第 3 层：private 测试只用于最终评价
```

| 项目 | 规定 |
| --- | --- |
| 比较对象 | 最小生成序号、最大生成序号、代码字典序、组内随机、过程 tie-breaker、组内 private oracle |
| 候选分层 | L0：全 private=0；L1：仅部分正确；L2：存在完全正确候选 |
| 主要指标 | L1 的 private pass rate、L2 的 pass@1、全体题目的总体影响 |
| 可靠性要求 | 以 problem 为单位划分训练/测试；按 problem 做 cluster bootstrap；报告并列率和同分规则敏感性 |
| 输入边界 | 题目、thought、代码、public feedback；不输入 private 内容 |

### 建议口述

> 我目前不把“动态粒度一定有效”作为结论。先收束为一个更小的问题：过程评分器是否能只在 public 反馈无法区分候选时，承担 tie-breaker 的角色。它能把过程模型与直接执行反馈从“互相竞争”改成“分层协作”，同时避免把任意的同分规则误当作方法效果。

> 如果过程 tie-breaker 在严格 held-out 题目上仍不能超过预注册的固定规则，我会把它作为负结果：在当前 APPS starter-code 条件下，残余过程信号不足以支持学习型选择器。只有这个基线确认后，才引入 CoF 或结构化程序特征。

### 不要在本次汇报主张的方向

- “函数一定不适合作为步骤”；
- “S3 自适应粒度一定会提升 pass@1”；
- “已经验证结构化 feedback 有效”；
- “用当前 APPS 入门题结果能够推广到复杂项目”。

CoF / 函数粒度仍可作为**条件性后续路线**：若 tie-breaker 需要更有意义的过程结构，才在相同模型、候选数、测试预算下比较“原提示 vs CoF 提示”。这属于改变候选生成结构的实验，应与评分器实验分开归因。
