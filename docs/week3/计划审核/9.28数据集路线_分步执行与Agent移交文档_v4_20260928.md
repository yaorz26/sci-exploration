## 一、一句话目标

先确认我们到底要用什么样的题、这些题能不能可靠判对错，再决定使用公开数据还是自行建设；数据和评测没有站稳之前，不继续训练、强化学习或大规模生成实验。

## 二、当前背景与结论边界

### 2.1 已经确认的事实

1. 当前 APPS 自定义切分主要是竞赛题，其中不少题的难点集中在一个算法想法上；在生成侧，函数拆分和 top-down 路线没有稳定超过直接生成。
2. 在选择侧，helper-first FunPRM 合并确认取得 `12/60`，高于首候选 `7/60`，净增 5 题；题目级为 6 胜 1 负，双侧精确符号检验 `p=0.125`。这是有限的选择侧正信号，不能写成强统计显著，也不能外推为拆分生成或 top-down 成功。
3. 同一候选池的事后上限为 `14/60`，评分器已取得其中 `12/14` 个全通过题；在这一冻结设置下，主要瓶颈已从“评分器明显漏选”转向候选池质量，但同族生成器/评分器等结论边界仍然存在。
4. 既有生成侧实验已排除“只是组合采样太少”这一主要解释，也确认接口不一致会给拆分方法带来额外损失。
5. 项目代码中的后端、命令行工具、数据处理管线等任务，通常更容易形成多个自然阶段，可能更适合检验拆分方法；这仍是待验证假设，不是既有结论。
6. 导师给出的数据路线是：先查 AI、软件工程顶会论文的公开数据集；公开数据不合适时，再从 GitHub 项目构建 `<requirement, code>` 数据。
7. 当前实验状态仍为暂停。不得擅自生成新候选、训练模型、调用付费模型或启动强化学习。

### 2.2 已决定与尚未决定的事项

**用户 2026-09-28 已确认（以下为已生效的决定，不再当作待决项）：**

2. **数据用途**：第一轮只做评测，不训练代码生成器、拆分器或评分器。
3. **数据集成果归属**：本路线优先采用已有的顶会公开数据集，**采用别人的数据集不算本项目成果**；“数据集是否作为成果”只在走到自建分支（WP4B）时才成立，届时再定（见 §2.4 末段、§5.3 第 16--17 条）。
4. **结论标签**：等 G1 选定具体数据集后再定；在此之前只允许中性表述（“新数据候选的工程审计”或“项目式代码探索性试跑”）。
5. **候选池探针 P0**：不预先授权，等到该步骤前再确认（先完成 FAST-0 与 WP1--WP3）。

### 2.3 本文建议的默认工作假设

在导师或用户进一步修改前，先按下面的研究问题准备数据：

> 在本地 7B 代码模型与有限计算预算下，对于本来就包含多个自然阶段、接口清楚、能够自动测试的项目式代码任务，“先拆分、分别实现、再组合”是否比直接生成完整代码更可靠？

第一轮把新数据当作**评测材料**，暂不用于训练。这样可以先分清“换了更合适的题是否有效”和“训练是否有效”，避免两个原因混在一起。

### 2.4 研究定位、文献缺口与可交付价值

这条路线不是单纯“换一个数据集再跑一次”。它要回答的是一个有边界条件的问题：

> 竞赛题上的负结果，究竟来自“拆分本身没有价值”，还是来自“任务的难点无法拆开”；当任务天然由多个有清楚接口的阶段组成时，拆分能否减少原先量到的接口与协调损失，并抵消它自身带来的额外成本？

需要检验的核心假设不是“项目代码一定适合拆分”，而是下面这个可以被数据推翻的假设：

> 与难度集中在单一算法想法上的任务相比，项目式任务会降低拆分后的接口断裂和全局协调损失；这种下降幅度足以抵消额外格式、重复调用、组合稀疏以及没有训练补偿带来的代价，从而使 M2 相对 M0 的题目级差异翻为非负或正向。

该假设可能以两种方式失败：一是项目式任务并没有降低接口错误；二是接口错误虽然下降，但其余成本仍然更大。两者必须分开报告。

WP1 必须核查这个问题是否已经被现有论文直接回答，尤其检查“项目级或仓库级任务上，模块化/分解生成与直接生成的等预算比较”。若已有高质量工作回答同一问题，本项目必须说明新的增量是本地 7B 条件、不同任务边界、不同组合机制，还是仅做复核；若没有可辨认增量，应在数据建设前停止扩张。

不同结果最多能支持以下表述：

- **正结果**：只能说在冻结的新数据、模型、预算和选择规则下，项目式任务出现探索性正信号；20--30 题不能直接推出一般规律。
- **负结果**：可以说明“仅换成更有自然接口的任务仍不足以抵消拆分成本”，但不能推出所有项目代码都不适合拆分。
- **差异不清楚**：如区间同时覆盖有意义的正负差异，应直接写“现有题量无法判断”，不得包装成“基本持平”或继续临时加题直到得到想要的方向。
- **即使全负仍成立的交付**：可复跑的数据审计、许可证与来源记录、本机评测管线、公开/私有测试隔离、仓库级切分，以及“哪些公开数据在本机能稳定判分”的工程事实。

导师提出“数据集本身也可作为成果”。按用户 2026-09-28 的更正，这条**只在自建分支（WP4B）才成立**：本路线优先采用已有的顶会公开数据集，**采用别人的数据集不算本项目成果**。若走公开数据分支（WP4A），本项目自己的产出只能是**派生物**——数据转换、公开/私有测试切分、可拆分性分层标注、评测适配与说明；这些可以署名发布，但必须写明来源数据集与原作者、遵守原许可证对再分发与衍生作品的规定，**不得宣称是新数据集**。因此该决定**推迟到 G1 选定分支之后再定**，不在 WP0 强问。

### 2.5 现实产出上限

在当前 8GB GPU、单机、本地 7B 和有限磁盘条件下，本路线最可靠的产出是“数据与评测基础设施是否可用”的工程事实；其次是 20--30 题上的探索性方向信号。统计上可靠地证明“拆分在项目式任务上有效或无效”，很可能需要远高于当前预算的题量与多 seed 运行，不能预先承诺。

配对结果的已有锚点是：6 胜 1 负的双侧精确检验为 `p=0.125`；6 胜 0 负才约为 `p=0.031`，5 胜 0 负仍约为 `p=0.063`。这些数字说明小样本只有接近一边倒时才可能达到常用显著性阈值。但本文不把 `p<0.05` 当作唯一成功标准：还必须预先冻结最低有意义提升、题目级效应与区间口径，并保留“不确定”结论。

### 2.6 对审阅意见的采纳边界

本版直接采纳：问题线补全、统计与预算前置、环境/落盘核查、既有初筛承接、分层负对照、双 seed 要求、候选池前置探针、目录与交叉引用修正。

本版改写后采纳三点：

1. `p<0.05` 只作为证据之一，不替代效应大小、区间和最低有意义提升。
2. “M0 + 公开测试选择”不是新的生成方法，而是作用在 M0 候选池上的选择规则；生成方式与选择方式分开报告，并尽可能把同一选择规则应用到可比较的候选池。
3. BigCodeBench、SWE-bench、DevBench 等只作为既有初筛线索；“适合”或“本机不可行”必须由 WP1--WP3 重新核实，不能把旧印象当成最新事实。

审阅中的“项目式任务成本约为旧实验十倍”“最终确认可能需要 150--300 题”等仅保留为数量级风险，不写成已验证预算。实际预算必须由 WP3 和前置探针的实测决定。

## 三、不可违反的执行规则

所有接手 Agent 必须遵守以下规则：

1. 开始工作前读取根目录 `AGENTS.md`、`PROJECT_MEMORY.md`、本文件和自己工作包列出的输入文件。
2. 只执行被分配的工作包，不得跳过前置门槛直接做后续实验。
3. 不得覆盖冻结数据、旧报告或机器输出；协议变化必须生成带版本号的新文件。每次修订主文档前，先保存带版本号和日期的只读快照，记录 SHA-256；旧版缺失时只能如实标注“不可恢复”，不得凭记忆重建。
4. 私有测试不得进入提示词、候选生成、候选选择、调参或训练输入。
5. 调研结论优先依据论文原文、官方数据集页面、官方仓库和许可证文件；博客只能作为找线索的入口，不能作为关键结论的唯一证据。
6. 下载大体积数据前先记录预计大小、许可证和用途；调用付费 API 或大规模模型前必须获得用户明确同意。
7. 任何失败都要记录，包括下载失败、环境装不上、测试不稳定、许可证不清楚和候选数据不适合；不得只保留成功项。
8. 所有自然语言文档使用中文；模型名、数据集名、字段名和命令可保留原文。
9. 每个工作包结束时更新项目规定的记忆文件，并使用本文第十六节的移交格式。
10. 新增的大文件、模型、缓存、虚拟环境和容器镜像不得默认落到 C 盘；必须事前写明 D 盘绝对路径、预计体积和清理办法。**特别地：pip / conda 缓存目录与新建的 Python 虚拟环境默认在 `C:\Users\...\AppData\Local\`，属本机当前最可能往 C 盘写的部分，必须在建环境时用环境变量（如 `PIP_CACHE_DIR`、`UV_CACHE_DIR`、虚拟环境路径）显式指到 D 盘**（已查明 WSL 虚拟磁盘与 Docker 数据盘实体均在 D 盘，此项无需例外）。任何 C 盘例外必须由用户明确决定。

### 5.3 具体动作

1. 研究任务的可能目标有三个，**主目标已由用户 2026-09-28 确认为第一个**，不需要再问：
   - **只评测拆分是否有效（已确认，第一阶段唯一目标）**：新数据只用于比较直接生成和拆分生成。
   - 训练拆分器（暂不做）：让模型学会把需求转成子任务和接口。
   - 训练代码生成器或评分器（暂不做）：分别需要参考代码，或多候选及结果标签。
2. 与上述决定一致：**第一轮不训练，只做评测**。原因不变——当前还不知道项目式任务上是否存在拆分正信号，直接训练会把任务适配和训练收益混在一起。若将来要改用后两个目标，必须重新走 WP0 并生成新的数据契约版本。
3. 冻结任务粒度。建议第一阶段只做：
   - Python；
   - 后端逻辑、命令行工具、数据处理或小型库功能；
   - 单个函数到小型模块级修改；
   - 不依赖浏览器、手机模拟器、真实数据库、外部网络服务或人工看界面。
4. 冻结每道题的最低字段，至少包括：
   - 稳定的 `task_id`；
   - 自然语言需求 `requirement`；
   - 可提供给模型的项目上下文和 starter 文件；
   - 不提供给模型的参考实现或参考补丁；
   - 公开测试与私有测试；
   - 运行环境和依赖；
   - 来源仓库、固定提交版本、许可证和文件哈希；
   - 任务规模与可拆分性标注。
5. 若目标包含训练拆分器，额外要求：子任务列表、每个子任务的输入输出、依赖关系、共享状态说明和推荐执行顺序。
6. 若目标包含训练评分器，额外要求：同题多份候选、函数边界、测试结果、运行错误和候选来源。
7. 冻结待验证的“可拆分性量表”：
   - 至少两个自然处理阶段；
   - 阶段之间输入输出清楚；
   - 至少一部分子功能可独立测试；
   - 测试能够区分不同实现，而不是所有候选都并列；
   - 正确性不完全依赖一个无法拆开的算法洞察。
8. 明确这五项判据是本项目根据既有失败归因形成的**待验证量表**，不是公认真理。WP1 需要查找 DecompRL、MoT 及相关论文中的模块化、条件独立或任务结构定义，建立对应关系；找不到对应依据时，必须把五项判据标成项目自定义。
9. 冻结判据的证伪条件。建议至少包括：高判据组并未比低判据组减少接口错误，或 M2 相对 M0 的差异没有随判据层级改善。小样本只作描述，不能把未显著误写为“判据无效”。
10. 冻结最低有意义提升。不得直接照抄“10 个百分点”；应结合任务成本、旧结果和导师目标，写出一个题目级全通过率差值，以及为什么低于该值即使为正也不值得投入。
11. 冻结统计口径：题目级成对差异、效应大小与区间为主；配对精确检验为补充。预先估计可能出现的 M0=M2=0 双零题比例，因为这类题越多，真正提供方法差异信息的题越少。
12. 预注册“不确定”分支：若区间同时覆盖有意义的正向和负向差异，结论为“题量不足，无法判断”。默认不追加题、不训练；只交付数据与评测基础设施。任何扩大都必须另立预算、新确认集和资源来源说明。
13. 冻结 seed 规则：单 seed 只允许工程试跑或探索；若进入确认，至少两个预先固定 seed，并按“同一题在不同 seed 下的重复测量”分析，不能把 task×seed 全部当成互相独立的题来虚增样本量。
14. 冻结预算与停止条件，至少包括：总请求数、每方法请求数、总墙钟、单方法墙钟、单题测试超时、磁盘上限、最大输出和超预算后的部分报告方法。可参考旧协议“单方法 2.5 小时停止”的先例，但不得未经实测原样搬到更长的项目任务。
15. 明确所有大文件的落盘位置。默认 D 盘；记录数据、模型、虚拟环境、pip/conda 缓存、WSL VHDX 和 Docker 镜像的路径与预计体积。C 盘例外由用户决定。
16. 结论标签上限**已由用户 2026-09-28 决定：等 G1 选定具体数据集后再定**。在选定之前，只能使用“新数据候选的工程审计”或“项目式代码探索性试跑”这类中性表述；旧标签“本地 APPS 自定义切分缩小规模机制研究”不能自动沿用，也不得在此阶段声称任何一般性结论。G1 决策文档需同时提交建议的新标签，交用户或导师确认。
17. 数据集是否作为正式交付物**按分支处理（用户 2026-09-28 更正）**：本路线优先采用已有公开数据集，采用别人的数据集不算本项目成果；只有在 G1 判定转入自建（WP4B）时，才需要决定数据集是否作为独立成果，届时必须补齐数据卡、版本策略、标注一致性、发布许可和维护计划。走公开数据（WP4A）时，本项目产出的是**派生物**（转换、公开/私有切分、拆分层标注、评测适配），可署名发布但须写明来源与作者、遵守原许可对衍生作品与再分发的限制，不得宣称是新数据集。
18. 把 WP0 交付设计成“一页决策请求单 + 数据字段契约草案”。请求单列出每个待决定项、推荐选项、替代选项、成本、最迟决定时间和未决定时的默认动作。默认动作必须是暂停有成本的后续工作，而不是 Agent 自行代替用户选择。
19. 提前登记扩大确认可能使用的资源来源：本机延长运行、外部算力、API 额度、导师或课题组资源；每一项都写明是否已获授权、负责人和可用期限。无法确认资源时允许写“未知”，但 G2 不得把“需要更多资源”永久保留为开放待办。

## 七、WP2：候选数据集静态审计

### 7.1 目的

不运行大规模任务，只通过论文、字段样本、仓库结构和许可证判断候选是否值得进入本机试运行。

### 7.2 并行方式

WP1 形成短名单后，可以把每个候选数据集分给不同 Agent 并行审计。每个 Agent 只审计一个数据集，使用同一模板，避免各自改变标准。

### 7.3 硬性否决条件

出现任意一项，原则上直接排除；若保留，必须由用户明确接受风险：

1. 数据或参考代码许可证不允许当前使用或再分发。
2. 没有可执行测试，也无法合理补建测试。
3. 任务依赖人工主观评分，无法形成稳定的自动判定。
4. 绝大多数任务需要浏览器、移动端、外部网络、真实云服务或大型数据库。
5. 单题上下文明显超出本地模型可设定的输入上限，且无法在不改变任务的情况下裁剪。
6. 数据无法下载、关键文件缺失，或官方仓库已经无法复现。
7. 输入中直接包含参考答案、私有测试或等价实现，存在无法修复的答案泄漏。
8. 评测只能在无法控制的外部服务上运行，因而不能冻结环境和复现结果。
9. 必须使用 Docker / WSL2，但无法给出符合用户约束的 D 盘落盘方案、预计体积和清理办法。
10. 绝大多数题不包含两个以上自然阶段，或无法对任何阶段做独立验证。此时它可能仍是代码生成数据，但不适合回答当前拆分问题。

### 7.4 统一评分维度

在看到各候选最终总分前固定评分规则，每项记 `0/1/2`：

- 来源和许可证清晰度；
- 需求描述完整度；
- 项目上下文真实性；
- 可执行测试完整度；
- 公开/私有测试可分离性；
- 五项可拆分判据匹配度；
- 本地运行可行性；
- Python 子集可用规模；
- 按仓库隔离切分的可行性；
- 污染与重复代码风险的可审计性。
- Windows / WSL2 / Docker 环境依赖与稳定性；
- 镜像、数据、环境和缓存的体积及 D 盘落盘可控性；
- GitHub、pip、Hugging Face 等网络可达性；
- 是否确有至少两个自然阶段且能够分阶段测试；
- 可拆分判据与既有文献定义的对应程度。

总分只用于排序，不能覆盖硬性否决条件。

## 八、WP3：每个候选抽 10 题做可运行性试验

### 8.1 目的

这里不是测模型效果，而是检查这批题能不能在本机稳定判分。就像买实验仪器前先通电，不能等生成几百份代码后才发现测试环境根本跑不起来。

### 8.2 选题规则

1. 先固定抽样规则和随机种子，再读取具体结果。
2. 每个候选抽 10 题，覆盖不同项目和不同规模；不能只挑 README 中的成功示例。工程试验采用预先分层的初始配额：高可拆分目标层 4 题、低可拆分负对照层 3 题、边界层 3 题。若候选本身凑不出某层，记录结构覆盖不足，不得用其他层的成功题静默补齐。
3. 负对照优先从同一数据集或相近仓库分布中抽取，并尽量匹配语言、上下文长度、测试成本和许可证条件，以减少“任务域不同”带来的混杂。
4. 尽量按仓库分散抽样，避免 10 题都来自同一个项目。
5. 除实际运行的 10 题外，静态核查该候选能否为 WP5 提供每层至少 8 个潜在任务 ID；这些储备题在 WP3 不必全部安装运行，但必须能追溯来源、任务结构和初步入层理由。
6. 记录任务 ID、仓库、提交版本、抽样种子和文件哈希。
7. 五项可拆分判据至少由两名独立标注者或两个独立 Agent 判断；记录逐项一致率和全部分歧。样本很小时不强求使用单一统计量掩盖分歧；若计算 Cohen's kappa，必须同时报告原始一致数。

### 8.3 具体动作

1. 环境预检：记录 Windows / WSL2 / Docker 模式、绝对落盘路径、预计新增体积、当前剩余空间、网络前置条件和清理办法；路径不合规时停止，不先安装再补记录。
2. 建立隔离环境，安装依赖并记录准确命令、版本、缓存目录和环境目录。
3. 运行官方参考实现或金标准补丁，确认原始测试能够通过。
4. 每题至少重复运行 3 次，检查结果是否稳定、是否依赖网络、时间或随机状态。
5. 测量安装时间、单题测试时间、内存、磁盘占用和输出大小。
6. 检查公开测试和私有测试能否物理隔离；若官方只有一套测试，记录可否在不泄漏的前提下预先切分。
7. 统计输入上下文长度，确认能够放进 WP0 冻结的模型输入预算。
8. 按五项可拆分判据给每题打 `是/否/不确定`，并写一句依据。
9. 本阶段原则上只跑参考实现和测试，不调用代码生成模型。

当前已知环境事实只能作为预警，Agent 仍需在开工时复核：2026-09-28 审阅时 Docker CLI 已安装但守护进程未运行；WSL2 为 Ubuntu-22.04；WSL 内 Hugging Face 访问曾被阻断，需要主机下载后从 `/mnt/d` 载入；C 盘仅余约 38.8 GiB，D 盘约 120.3 GiB；既有 `wsl_root_free_gib=939` 与物理盘容量不一致，WSL VHDX 位置仍未知。在核实 Docker/WSL 落盘前，不得启动大量镜像拉取或环境安装。

### 8.4 建议的初始通过门槛

这些门槛应在 WP0 中正式冻结；如果 WP0 采用其他值，以 WP0 为准：

- 10 题中至少 8 题能够在干净环境完成安装和测试；
- 至少 8 题的参考实现连续 3 次结果一致；
- 至少 8 题不依赖外部网络、人工交互或真实云服务；
- 预注册的 4 题目标层、3 题负对照层、3 题边界层配额均有明确入层理由；若某层缺失，不能把该候选宣传为可支持三层交互检验；
- 静态储备清单中每层至少有 8 个潜在任务 ID；未达到时只能条件采用，并在 G1 明确研究结论将收缩；
- 至少 8 题能放入冻结的输入长度预算；
- 能建立严格的公开/私有测试隔离方案；
- 许可证和来源信息覆盖全部 10 题。
- 所有新增数据、环境和缓存均按 WP0 约束落盘，且未未经授权占用 C 盘。

门槛失败时不得通过删除失败题来凑够比例。可以另立 v2 抽样协议，但必须保留 v1 的失败记录和修改原因。

## 九、G1：公开数据还是自建数据的决策门槛

### 9.1 输出选项

只能给出以下四种结论之一：

1. **采用公开数据**：至少一个候选通过 WP3，且只需有限格式转换。
2. **有条件采用公开数据**：核心数据合适，但需要可控的测试适配或 Python 子集过滤；必须列出工作量和剩余风险。
3. **公开主集 + 自建补充集**：公开数据覆盖一般项目任务，但缺少拆分标注；自建小规模补充只用于接口和拆分监督。
4. **转入自建**：公开候选在许可证、测试、任务结构或本机可运行性上均不满足门槛。

### 9.2 决策规则

- 不能因为已经花时间适配某个数据集就降低门槛。
- 公开数据只要能回答主问题，优先于从零自建，因为来源和外部可比性更强。
- 若公开数据只缺拆分标注，不应立刻抛弃整个数据集；可以考虑在其上增加经过审计的拆分层。
- 若公开数据没有可靠测试，不能因为需求文本看起来真实就采用。
- 决策文档必须显式回答一个现实问题：候选数据同时满足“至少两个自然阶段、能分阶段测试、许可证清楚、本机稳定运行”的比例是多少。若好运行的数据普遍只有单点函数任务，而真正多阶段的数据普遍依赖重型容器，就应把这一矛盾作为路线结论，而不是继续降低门槛。
- 若 WP1 表明同一科学问题已被高质量研究直接回答，且本项目没有清楚增量，即使数据可用，也可以给出“工程可用、研究立项 No-Go”。
- 数据集定位必须**按分支说明**：走公开数据（WP4A）时，本项目产出的是基于他人数据集的派生物（转换、公开/私有切分、拆分层标注、评测适配），**不得宣称是新数据集**，也不得把他人数据集算作本项目成果；只有在 G1 判定转入自建（WP4B）时，才需要决定数据集是否作为独立成果，届时两种路线的质量与发布要求不同。这部分已由用户 2026-09-28 更正。

### 9.3 产物

`DOC_ROUTE_ROOT/04_dataset_route_decision.md`

文档必须列出：通过/失败门槛、证据、成本、风险、推荐选项，以及需要用户或导师拍板的事项。

## 十、WP4A：采用公开数据时的转换与清洗

只有 G1 选择公开数据后执行。

### 10.1 具体动作

1. 下载并保存官方版本号、发布日期、原始文件哈希和许可证副本。
2. 原始数据只读保存，转换结果写入新目录；不得直接修改原始文件。
3. 只保留 WP0 允许的语言、任务粒度和运行环境。
4. 把数据转换到统一字段，但保留原始 ID 和来源映射。
5. 去除完全重复和近似重复任务；记录去重算法、阈值和被删除 ID。
6. 按仓库而不是按单题切分，避免同一项目的相似代码同时进入训练和测试。
7. 将测试分为公开与私有两部分；私有部分单独保存，不进入模型输入目录。
8. 运行参考答案回归测试和环境审计。
9. 对可拆分性做双人或双 Agent 标注；分歧项单独记录，不能强行统一。
10. 保留低可拆分或明确“不应拆分”的负对照任务，不得只留下高判据任务后再证明拆分有效。
11. 根据 WP1 核实的模型训练时间边界制定污染降低方案；边界未知时不得把时间过滤写成无污染保证。

## 十一、WP4B：自行构建 GitHub 数据集

只有 G1 判定公开数据不满足要求，或明确需要小规模拆分补充集后执行。

### 11.1 推荐的第一版任务范围

先做 20--30 题的最小可用版本，不直接追求大规模：

- Python 项目；
- 许可证清楚；
- 原仓库已有自动化测试；
- 功能位于单函数或小模块，能在本机独立运行；
- 无浏览器、移动端、GPU 服务、真实数据库和外部网络依赖；
- 上下文能在本地模型输入预算内表达；
- 优先后端业务逻辑、命令行工具、解析器、格式转换、数据验证和小型库功能。

star 数只能作为项目成熟度的辅助信号，不能作为唯一标准。高 star 项目更可能被模型在预训练时见过，必须单独记录污染风险。

### 11.2 构建步骤

#### 步骤 A：仓库入选审计

记录仓库地址、许可证、star 数、主语言、最后提交时间、固定提交哈希、测试框架、依赖和本机运行结果。许可证未知或禁止当前用途的仓库直接排除。

#### 步骤 B：选择任务单元

从仓库中选择一个完整功能，而不是任意截取几行代码。记录目标函数/模块、依赖文件、调用方和原始测试。任务应满足五项可拆分判据的大部分条件。

#### 步骤 C：制作 starter 状态

删除或遮蔽目标实现，但保留完成任务所必需的接口、类型、相关上下文和依赖。确认 starter 在未实现目标功能时测试会失败，填回参考实现后测试会通过。

#### 步骤 D：大模型反推需求

大模型可以读取参考实现、调用方、文档和测试，生成第一版需求，但必须保存：模型名、版本、提示词、参数、调用时间和原始回答。需求生成不是最终真值，只是草稿。

如仓库存在 issue、用户文档、变更说明或提交消息，应另生成一份**不读取参考实现**的需求草稿，与“读取实现反推”的草稿对照。没有这些材料时不强造第二路，但必须标记“只有实现反推来源”，并相应降低需求真实性证据。

#### 步骤 E：需求泄漏审查

人工或独立 Agent 检查两类泄漏：

1. **实现细节泄漏**：内部变量名、完整控制流程、答案特有常量或逐行算法。
2. **解法形状泄漏**：把参考实现的阶段数量、先后顺序、关键数据结构或天然拆分直接写进需求，使研究要比较的拆分过程提前被答案告知。

需求应说明“要实现什么、输入输出是什么、边界行为是什么”，不应变成参考代码的中文翻译。至少两名独立标注者或两个独立 Agent 审查，保留逐项一致数、分歧和最终处理；不能只给一个无分歧记录的“已通过”标签。

#### 步骤 F：测试构建与隔离

保留一部分可见测试帮助理解接口；另外建立模型不可见的私有测试，覆盖正常、边界、异常和规模情况。私有测试不得由参与生成候选的模型看到。若新增测试来自大模型，也必须人工验证并记录生成来源。

#### 步骤 G：拆分标注

若数据要支持拆分研究，为每题记录 2--5 个自然子任务、输入输出、依赖边、共享状态和是否可单独测试。允许标注“不应拆分”，它是合法负样本，不能强迫所有题都拆。

#### 步骤 H：难度与结构标注

优先使用可复核指标：上下文 token 数、修改行数、涉及函数数、依赖深度、测试数、分支数、运行时间。模型成功率只能作为开发集上的辅助观察，不能在确认集看完结果后倒过来定义难度。

#### 步骤 I：重复与污染检查

检查同仓库重复、跨仓库复制、近似代码和相同测试。根据 WP1 核实的官方训练时间边界记录目标代码发布日期与当前模型可能见过它的风险；边界未披露时写明未知。优先选择模型发布时间之后的提交可以降低风险，但不能证明代码未出现在其他来源或后续训练中。无法证明“模型从未见过”时，不得声称完全无污染。

#### 步骤 J：按仓库切分

训练、开发、探索性试跑和最终确认必须使用不同仓库。不得把同一仓库的不同函数分到不同集合，因为它们可能共享代码风格、工具函数和实现模板。

### 11.3 建议统一数据结构

```json
{
  "task_id": "stable-id",
  "source": {
    "repository": "owner/repo",
    "commit": "full-commit-hash",
    "license": "SPDX-or-unknown",
    "source_files": ["path/to/file.py"],
    "content_hashes": {}
  },
  "requirement": "给模型看的需求",
```

### 11.4 自建数据质量门槛

- 100% 任务有许可证、仓库、固定提交和哈希记录；
- 100% starter 会触发预期失败，参考实现会通过目标测试；

- 需求泄漏审查同时覆盖实现细节和解法形状，并报告独立审查的一致与分歧；
- 训练、开发、试跑和确认按仓库隔离；
- 公开测试和私有测试物理隔离；
- 删除和失败任务保留审计记录，不静默消失。

## 十二、WP5：数据切分、冻结与最终审计

### 12.1 数据用途分层

建议至少分为：

1. **工程开发集**：用于修评测器、安装环境和提示格式，可以反复看结果。
2. **探索性试跑集**：用于估计直接生成和拆分生成的大致差异，结果不能作为最终确认。
3. **最终确认集**：题目、预算、提示、随机种子和选择规则冻结后才运行私有测试。
4. **训练集**：只有 G2 决定训练时才启用，并与最终确认仓库完全隔离。

探索性试跑集应预先分为三层，每层建议 8--10 题，总计 24--30 题：

- **低可拆分负对照层**：单阶段或接口价值很低的任务，用来检查 M2 是否因额外流程受损。
- **高可拆分目标层**：有两个以上自然阶段、接口清楚且部分阶段可独立测试，是核心检验对象。
- **边界层**：表面有多个函数，但关键难度集中在一个洞察、性能架构或全局状态上，用来检查五项判据是否真能预测方法差异。

低可拆分负对照的首选来源是**同一公开数据集或相近仓库分布中的单阶段/低接口价值任务**，并尽量与目标层匹配语言、上下文长度、测试成本和仓库活跃度。既有 APPS 冻结题可以作为外部描述性 sanity check，但它已经揭盲且任务域不同，不得作为主要负对照、调参依据或确认性“任务结构 × 方法”证据。

若公开数据无法同时提供三层，不得静默删掉负对照，也不得直接用 APPS 替代内部负对照；应在 G1 明确说明只能做目标层探索或检验方法主效应，无法可靠检验“任务结构 × 方法”的交互关系。

### 12.2 重要统计说明

20--30 题只适合探索性试跑，不足以自动承担最终确认。此前 60 题比较仍得到 `p=0.125`，说明最终题量不能凭感觉决定。还要把 M0=M2=0 的双零题比例纳入判断：若大量题两种方法都无法解决，名义题量并不等于真正能区分方法的题量。WP6 结束后应根据观察到的题目级差异、最低有意义提升、双零比例和可接受误差，做样本量与预算估计，再冻结最终确认规模。

### 12.3 冻结内容

- 任务 ID 和仓库集合；
- 每个文件的哈希；
- 公开/私有测试边界；
- 模型、量化方式和上下文上限；
- 方法提示词；
- 每题候选数、调用数和 token 上限；
- 探索阶段的固定随机种子；进入确认时至少两个固定 seed，以及重复测量的分析方式；
- 超时、内存和输出上限；
- 无效候选处理；
- 选择规则与并列处理；
- 主要指标、次要指标和停止条件。
- 最低有意义提升、区间口径、配对检验口径和“不确定”分支；
- 三层任务的入层规则与判据无预测力的证伪条件；
- 总请求、总墙钟、单方法墙钟和磁盘上限。

### 12.6 P0：候选池 headroom 前置探针

P0 是一个独立工作包；这里只使用 §12.6 编号，是为了保持主章节和既有引用稳定，不表示它属于 WP5 的常规步骤。本探针位于 WP5 与 WP6 之间，涉及生成新候选，必须先获得用户明确许可；许可只覆盖探针，不自动解除后续 WP6、训练或 RL 的暂停。

目的不是比较 M0 与 M2，而是先回答：当前 7B 在这些任务上是否至少偶尔能生成全过答案。如果候选池几乎全为零，后面的多方法比较主要会测到共同能力天花板。

建议设计：

1. 从高可拆分目标层与边界层共抽 10--20 题；抽样规则、题目、seed 和测试边界先冻结。
2. 每题生成 1--3 个 M0 直接生成候选；总调用保持在几十次量级，具体上限由 WP0 冻结。
3. 候选生成结束后冻结清单，再运行私有测试并计算首候选成绩、M0 候选池上限、有效候选率、双零风险与成本。
4. 不在本探针上修改提示词；若发现评测器错误，保留 v1 并另立 v2。
5. 默认解释：若 20 题中仅 0--3 题存在全过候选，应把“7B 共同地板”列为严重风险，原则上不直接进入完整 WP6；若达到 4 题及以上，也只说明存在最低可测空间，不代表拆分会有效。该 `4/20` 是操作性筛查线，不是统计结论；WP0 可在运行前改为其他有依据的门槛。

- `DOC_ROUTE_ROOT/06a_headroom_probe_report.md`
- 候选、评测和预算清单

若用户不授权本探针，文档应写“未测”，不得假设候选池有空间。

## 十三、WP6：20--30 题探索性对照试跑

本阶段必须等用户明确解除“暂停实验”后才能运行。

### 13.1 首要问题

项目式、接口清楚的任务上，拆分生成能否至少不低于等预算直接生成，并产生直接生成没有覆盖到的正确候选；而且这种差异是否主要出现在高可拆分层，而不是低可拆分负对照层？

### 13.2 生成方法与选择规则必须分开

- `M0`：直接生成完整代码，主对照。
- `M1`：先写自然语言计划，再生成完整代码，作为次要对照。
- `M2`：先形成带接口的分解，再分别实现和组合，实验方法。

第一主要比较为 `M2 vs M0`。M1 用于判断收益来自一般性“先计划”，还是来自真正的函数分解。

“首候选”和“公开测试选择”是**选择规则**，不是新的生成方法。至少报告：

1. `M0-first`：M0 的固定首候选，作为最自然的单次生成基线。
2. `M0-public`：在 M0 候选池中按公开测试选最好者，使用预先冻结的并列规则。
3. `M1-first` 与在预算允许时的 `M1-public`。
4. `M2-first`、`M2-public`，以及预先冻结的 M2 组合/选择规则。

如果某数据集没有合法、不会泄漏私有信息的公开测试，`public` 选择规则应标为不可用，不能临时从私有测试拆出一部分再称“公开”。为了区分生成质量与选择质量，优先比较同一选择规则下的不同生成方法，同时单独报告各方法的候选池上限。

### 13.3 预算原则

不能只让三种方法各生成相同份数，因为 M2 每份答案需要多次调用。至少同时报告：模型调用数、输入 token、输出 token、墙钟时间和测试执行数。主比较应使用预先冻结的等预算口径，并与 P5c 的既有口径尽量一致；若项目任务需要调整，必须写清差异。保留原始调用明细。

WP0/WP5 冻结的请求数、墙钟和磁盘上限是硬停止条件。超过上限时停止新增生成，按已完成题目报告，不删除超时或未完成题，也不把部分结果包装成完整试跑。

### 13.4 指标

主要指标：

- 私有测试全部通过的题目数；
- M2 与 M0 的题目级成对差异。
- 高可拆分层与低可拆分层中 `M2-M0` 差异的方向；小样本只作探索性交互描述。

次要指标：

- 候选池上限，即同一批候选中假设能提前知道正确答案时最多可解多少题；
- 部分测试通过率；
- 有效候选率；
- 接口类错误率；
- 公开测试并列率；
- 独特程序数量；
- 调用、token、时间和测试成本。
- M0=M2=0 的双零题数量和比例；
- 各层、各 seed 的结果，及方向是否一致；
- 选择规则带来的提升与生成方法带来的候选池提升分别是多少。

候选池上限只能在选择冻结后作诊断，不能反过来挑候选或改提示词。

### 13.5 试跑结果的解释门槛

- 若 M2 的候选池上限和选择后成绩都不高于 M0，且成本更高：停止扩大，不训练拆分器。
- 若 M2 候选池上限高于 M0，但选择后成绩没有提高：问题主要在选择，应先研究选择器或评分器。
- 若 M2 候选池上限与选择后成绩都高于 M0：获得继续扩大确认的依据，但 20--30 题仍只能称探索性正信号。
- 若两者池上限都很低：优先判断模型能力或任务上下文是否成为共同天花板，不把失败强行归因给拆分。
- 若收益只来自更多 token 或调用：不能称拆分机制有效。
- 若题目级差异的区间同时覆盖 WP0 冻结的有意义正向和负向差异，或不同 seed/分层方向冲突：结论为“当前题量下无法判断”。默认不扩大、不训练，交付数据与评测基础设施；如要扩大，另立新协议、预算和 §14.2 规定的资源计划。
- 若高可拆分层与负对照层没有出现预期的差异方向，五项判据的预测力未得到支持；不能只汇总总分后继续声称选对了任务域。
- 若单 seed 为正，第二 seed 反向或接近零：只能报告 seed 敏感，不得合并后掩盖方向冲突。

### 13.6 产物

- `codeprm-reproduction/experiments/<new_experiment>/preregistration.md`
- 预算和运行 manifest
- 原始生成、测试和审计文件
- `DOC_ROUTE_ROOT/07_project_code_pilot_report.md`

### 13.7 验收标准

- 所有冻结题和所有方法均报告，不删除失败题。
- 私有测试只在候选与选择规则冻结后运行。
- 同时报告正确率、候选池上限与成本。
- 结果明确标记为探索性试跑，不能写成最终确认。
- 同时报告三层任务、生成方法、选择规则和 seed，不把它们混成一个总分。
- 公开测试选择、首候选和候选池上限的关系可复核；私有测试未进入选择。

## 十四、G2：是否扩大确认、是否进入训练

### 14.1 决策表

| 观察结果 | 下一步 | 不应做什么 |
| --- | --- | --- |
| M2 候选池与选择后成绩都不优于 M0 | 记录项目式任务上的负结果，检查是否需要收束 | 不训练拆分器，不启动 RL |
| M2 候选池更好，但选不出来 | 研究评分与选择；可考虑函数级评分器 | 不把选择失败说成生成失败 |
| M2 选择后更好，但池上限不变 | 检查收益是否只是候选排序或偶然波动 | 不声称拆分提高了生成能力 |
| M2 池上限和选择后成绩都提高 | 做样本量估计，并同时提交扩大确认资源计划 | 不在同一试跑集继续调参后称为确认 |
| 所有方法都接近 0 | 检查任务太难、上下文太长或 7B 能力不足 | 不直接归因于接口设计 |
| 所有方法都接近满分 | 提高任务区分度或扩展规模 | 不用天花板数据比较方法 |
| 效应区间覆盖有意义的正负差异 | 结论为“现有题量无法判断”，默认交付数据与评测基础设施 | 不把未显著写成“基本持平”，不临时续跑直到显著 |
| 高/低可拆分层方向相同或混乱 | 记录五项判据没有显示预测力，重新审查研究构念 | 不只汇总总分后宣称找到适用域 |
| 两个 seed 方向冲突 | 记录 seed 敏感，停止提高结论强度 | 不把 task×seed 当独立题扩大分母 |

### 14.2 扩大确认的资源闭环

若 G2 给出“探索性正信号，需要更大确认”，必须同时产出 `DOC_ROUTE_ROOT/07_confirmation_resource_plan.md`，至少写明：

1. 预计需要的任务数、seed 数、请求数、输入/输出 token、墙钟时间、测试执行数和新增磁盘；
2. 资源来源：本机延长运行、外部算力、API 额度、导师或课题组资源；不得只写“后续再申请”；
3. 资源负责人、审批人、最迟确认日期和授权边界；
4. 若资源未获确认，如何在不追加运行的情况下收束结论。

没有具体资源来源、预算和负责人时，G2 必须正式选择“不扩大确认”，把本阶段目标收敛为“边界刻画 + 数据与评测基础设施交付”，不得把“需要更多题量”长期挂成无主待办。

### 14.3 只有满足以下条件才讨论训练

1. 数据和评测器已经稳定，不再频繁改变标签定义。
2. 探索性试跑显示存在可利用的候选池空间。
3. 已明确训练对象：拆分器、实现器或评分器。
4. 训练、开发和最终确认按仓库隔离。
5. 训练前写出独立协议、预算、成功门槛和停止条件。
6. 强化学习仍需单独授权；本路线的正信号不自动开放 RL。
7. 探索性信号不只来自单一 seed、单一任务层或额外 token；若当前预算不足以验证这一点，应先写“不确定”，不是先训练后补解释。

## 十五、适合多 Agent 的派单方式

### 15.1 推荐分工

- **Agent A：WP0**。负责研究问题与数据字段契约。完成前，其他 Agent 不开始大规模检索。
- **Agent A0：FAST-0**。WP0 请求单形成后，对一个既有候选做半天内的 5--10 题参考测试抽查；不运行生成模型，可在等待用户决定时执行。
- **Agent B：WP1**。负责顶会论文和公开数据集全景检索。
- **Agent C1--C5：WP2**。短名单形成后，每个 Agent 独立审计一个候选数据集，可并行。
- **Agent D：WP3**。负责统一抽样、环境安装与 10 题可运行性试验。
- **Agent E：G1**。只基于前述产物做路线决策，不重新定义门槛。
- **Agent F：WP4A 或 WP4B**。根据 G1 结果执行公开数据转换或自建数据。
- **Agent G：WP5**。负责去重、仓库级切分、私有测试隔离和冻结审计。
- **Agent H0：P0**。只有用户明确授权少量生成后，执行候选池 headroom 探针；该授权不自动覆盖 WP6。
- **Agent H：WP6**。只有用户明确解除对应实验暂停后，执行探索性对照试跑。
- **Agent I：G2**。只基于冻结试跑结果作扩大确认/训练决策；若建议扩大，必须同时提交资源计划，不能只留下“需要更多题”的待办。

### 15.2 不应并行的工作

- WP0 未完成时，不应让多个 Agent 各自收集不同结构的数据。
- WP0 请求单形成前不做 FAST-0；请求单形成后，FAST-0 可与等待人类决策并行，但不得扩展成完整 WP3。
- WP1 未形成统一候选表时，不应各自凭印象选择数据集。
- WP3 未完成时，不应同时大规模下载或转换数据。
- G1 未决策时，不应同时建设完整公开数据管线和完整自建数据管线。
- WP5 未冻结时，不应运行正式模型比较。
- P0 未获明确授权时，不应以“只是几十次调用”为理由自行生成候选。

## 十六、每个 Agent 的统一移交格式

每个工作包结束时必须给出：

1. **一句话结果**：完成、部分完成、失败或等待决定。
2. **实际做了什么**：列出检索、下载、运行或修改动作。
3. **产物路径**：列出新建或更新文件。
4. **可核查事实**：数字、样本量、版本、哈希、命令和来源。
5. **失败与限制**：包括不能运行、许可证未知、测试不稳定等。
6. **观察与推断分离**：先写观察到的事实，再写由此作出的判断。
7. **门槛结论**：通过、不通过或条件通过，以及对应条款。
8. **准确下一步**：下一工作包是什么；若需用户决定，给出具体选项与代价。

## 十七、整个数据路线的最终完成标准

只有同时满足以下条件，才能说“数据阶段完成，可以进入正式实验设计”：

- 研究问题的定位已经导师认可，且第一阶段用途**已确认只做评测、不训练**（用户 2026-09-28）；
- 可证伪假设、最低有意义提升、“不确定”出口已确认；结论标签按 2026-09-28 的决定处理（等 G1 选定数据集后定，在此之前只用中性表述）；
- 数据来源、许可证和固定版本完整；
- 任务能够在本机稳定自动判分；
- 需求、starter、参考答案和测试边界清楚；
- 公开测试与私有测试严格隔离；
- 按仓库完成训练/开发/试跑/确认切分；
- 重复、答案泄漏和污染风险已有审计；
- 环境、网络、磁盘预算和 D 盘落盘方案已有审计；
- 低可拆分负对照、高可拆分目标层和边界层的入层规则已冻结；
- 20--30 题探索性试跑协议已预先写好；
- 若提出扩大确认，题量、预算、资源来源、负责人和期限已经形成可执行计划；没有资源时已正式收束；
- 用户明确解除实验暂停后，才允许真正运行生成实验。
