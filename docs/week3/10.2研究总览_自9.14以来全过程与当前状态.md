## 一、一句话现状

**两条路都走到了明确的负结果，而且第二条（数据路线）是在把评测装置做到"干净、可复跑、可判分"之后才得出负结果的。** 当前手上最硬的资产不是"拆分有效的证据"，而是一套**可稳定判分的类级评测装置**（ClassEval 派生物，91/100 题可判分）和几条**可复用的工程事实**。唯一卡在外部输入上的事：研究问题的正式表述仍需导师认可。

## 二、可以说 / 不能说（结论边界）

**可以说**（都有落盘证据）：
1. 在本地 7B、自建切分、helper-first 评分器条件下，**选择侧有跨两个确认切分的稳定正向信号**：`12/60` 对首候选 `7/60`，bootstrap 95% 区间 `[0.0267, 0.1433]`，下界 > 0；逐题 6 胜 1 负（`p=0.125`）。
2. 在 API 给定的类级任务上，**"逐方法实现 + 组装"（M2）不比"一次性整体生成"（M0）更好，成本还高出数倍**（v1、v2 两次独立抽样一致）。
3. 这批类级任务对本地 7B 而言**明显偏难**：三臂在 66.7%--70.8% 的题上**全部失败**（"双零题"）。
4. 本项目自定义的"可拆分性五项判据"**当前措辞无法可靠标注**（κ=0.436，"可独立验证"零方差）。
5. 公开测试**不足以做候选选择**（多题出现"公开全过、私有不过"）。

**不能说**：
- 不能说 top-down/分解机制"有效"或"论文复现成功"；
- 不能声称取得官方 APPS 成绩、也不能说已具备 RL 条件；
- 不能用 ClassEval 的结果谈"该怎么拆"——它的 API 必须给定，**只能检验给定分解后的实现策略**；
- 不能声称"任务结构 × 方法"的交互检验做过（分层用的是机械代理，判据量表不可靠）。

### 阶段三：G1 / G2 决策（2026-09-29）

- **G1**：公开候选中同时满足"多阶段 + 分阶段可测 + 许可清楚 + 本机可跑"的**只有 1/5**（ClassEval）→ 决定**只采用 ClassEval**；排除 EvoCodeBench（上游含 AGPL×2/GPL×1/无许可×2）、DevEval（仓库无 LICENSE）、Commit0（需 Docker/Modal）、LCA（六个任务全无执行型判定）。
- **G2**：命中预注册门槛"**M2 的池上限与选择后成绩都不高于 M0 且成本更高 → 停止扩大、不训练拆分器**"，同时命中"两臂都低 → 优先判断模型共同天花板"。**决定：不扩大确认、不训练、不启动 RL**；因无外部资源来源，按 §14.2 **正式收束为"边界刻画 + 数据与评测基础设施交付"**。v2 复核后结论不变。

## 五、可复用的工程性事实（换任何方向都能用）

1. **ClassEval 派生物 v1**：91 题、字段统一、公开/私有**按方法切分**、含两种输入变体（`decompose_free` / `decompose_given`）、数据卡与 README；许可证 MIT（一手核实）。
2. **91/100 题能在本机稳定自动判分**：单题中位 0.29 秒，无需容器；9 题排除原因**逐条归档**（含 3 题非确定性，必须剔除）。
3. **公开测试不足以选择**：多题出现"公开全过、私有不过"（M0 至多 4 例）→ 选择规则必须与私有判定分开报告。
4. **双环境跑法**：Windows py3.13 + NumPy 2.x 为主，**NumPy 1.x 语义题用 WSL py3.10 + numpy 1.26.4**（已验证 1 例）。
5. **本机可承受的实验规模（实测）**：M0 单次生成 14--22 秒；WP6 v2 的 351 次调用约 49 分钟生成墙钟。
6. **"逐方法独立实现"的固有失败模式**：会**重复定义骨架里已有的辅助方法并覆盖签名**（`_to_camel_case`、`_select`），即使提示词明令禁止也照样发生；逐方法输出还可能在组装时才暴露语法不完整。

## 七、限制与风险（必须一直带着）

1. **污染风险未知**：Qwen2.5-Coder 训练数据边界官方未披露，且全部候选数据都早于该模型发布——"用晚于模型的提交降低污染"这条手段失效。

3. **分层是机械代理**（方法数量），判据量表经双标注不可靠 → "任务结构 × 方法"的交互**尚未真正检验**。

5. 之前阶段的老限制仍在：官方 APPS evaluator/test split 未取得；生成器与评分器同属 7B 家族；`max_length=768` 截断可能带来偏差。
