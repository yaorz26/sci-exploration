## 二、数据结构（HF 上的只有 0.02 MiB 元数据）

字段：`instance_id`、`repo`、`original_repo`、`base_commit`、`reference_commit`、`setup`、`test`、`src_dir`。样例：

- `instance_id` = `commit-0/minitorch`；`original_repo` = `minitorch/minitorch`
- `base_commit` / `reference_commit`：完整的 40 位提交哈希
- `setup` = `{'install': 'pip install -e .', 'packages': ['requirements.txt', 'requirements.extra.txt'], 'pip_packages': [...]}`
- `test` = `{'test_cmd': 'pytest', 'test_dir': 'tests/'}`
- `src_dir` = `minitorch/`

**含义：HF 上只有"任务清单"，真正的代码在 GitHub 的 `commit-0/<库名>` starter 仓库里**（每库一个仓库，含单元测试与待填空的函数体）。54 个 Python 库。

## 三、结构与规模（这是它最贴合我们问题、也最扛不住的地方）

- **任务单元是整个库**：多文件、多函数、相互依赖，需要"实现整库并通过全部单元测试"——**五项可拆分判据全部满足**，是短名单里结构最贴的一个；
- 但代价：
  1. 单题需要理解 **整套规格文档 + 多个源码文件 + 多个测试文件**，`【推断】` 上下文远超我们冻结的 **8192 token** 输入上限；
  2. 任务量级远超 20--30 题的探索性尺度（一个库就是一道大题）；
  3. 官方 README 明确写到：**跑测试需要先配置 Docker 或 Modal**（"You need to set up `docker` or `modal` before running tests"）。

## 七、结论

**结论：排除。** 排除理由本身是 G1 需要的证据：**"结构上最贴合研究问题的公开数据，恰好是本机最跑不动的那一个"**——这正是执行文档 §9.2 要求 G1 正面回答的"好跑的都不够可拆分、够可拆分的都不好跑"矛盾的具体实例。

**保留可能**：若将来外部算力或容器额度到位，可重新评估；或退一步只用它的**任务结构作为自建数据的模板**（从同一批库里挑单个模块做小规模任务），但这已属于 WP4B 自建分支。
