## 一、要核查的问题

> 是否已有工作，在**项目式 / 仓库级任务**上，做过"**模块化（分解）生成 vs 直接生成**"的**等预算**比较？它们的结论是什么？本项目还能主张什么增量？

## 二、找到的同类工作（按"是否补偿了分解的代价"分组）

### 第一组：分解 + 训练补偿

| 工作 | 做法 | 报告结果 | 证据强度 |
| --- | --- | --- | --- |
| **DecompRL** | 分解 + 分别实现 + 重组，**用 RL 训练**分解与实现两个策略 | 本项目本地已精读：收益要到**每题 5 万 token 以上**才出现（本机约 3.3k，差 15 倍以上）；原文 Table 4 记录"无 RL 的层级推理 11.0% **低于**标准生成 14.0%" | 本项目自有 PDF 精读记录（一手） |
| **MoTCoder / MoT** | 模块化指令微调（**SFT**），先出模块头，再实现，再组合 | APPS pass@1 **+5.8%**、CodeContests **+5.9%** | 论文摘要 + 项目已有的 MoT 阅读记录（`articles/extra/09_MoT.pdf`） |

**读法**：这两条都说明"分解**加上训练**可以有用"，但**都不能证明"只靠提示词分解"本身有用**。DecompRL 恰恰提供了"没有 RL 时层级生成反而更差"的对照。

### 第二组：分解作为"智能体脚手架"（换了一个问题）

| 工作 | 做法 | 报告结果 | 证据强度 |
| --- | --- | --- | --- |
| **MASAI**（arXiv 2406.11638） | 把 SWE 任务拆成 5 个子智能体（测试模板生成、问题复现、编辑定位、修复、排序） | SWE-bench Lite 解决率 **28.33%**（当时最高）；定位准确率 75%；每 issue 约 $1.96 | 摘要 + 多个二手页面（**未通读**） |
| **Agentless**（arXiv 2407.01489） | **非模块化**的两阶段简单流程 | SWE-bench Lite **27.33%**，成本约 $0.34/issue | 二手（未通读） |

**读法**：MASAI 是"模块化的智能体架构更好"，但它比较的是**不同脚手架**，不是"同一模型在等预算下拆分生成 vs 直接生成"；而 Agentless 用更简单的**非模块化**流程拿到几乎相同的分数、成本低一个量级——这对"模块化一定更好"是一个**反向提示**。

### 第三组：不训练的"模块化价值"直接测量（与本项目最接近）

| 工作 | 做法 | 报告结果 | 证据强度 |
| --- | --- | --- | --- |
| **Revisiting the Impact of Pursuing Modularity for Code Generation**（arXiv 2407.11406） | 提出模块化度量，比较"模块化代码 vs 非模块化代码"作为输入对生成性能的影响 | **模块化不是提升代码生成性能的核心因素** | 摘要（**未通读**；其设置是给模型看模块化/非模块化示例，不等于"分解—实现—组合"流程） |
| **GenSE-Scheduler**（IEEE Access 2026，并行机调度代码） | 单体生成 vs **四阶段模块化流水线 + 类型化契约**，本地部署的开源权重模型，**预注册等价准则** | 模块化显著提升行为多样性（Cliff's δ=+0.799 / +1.000），但**未通过预注册的 regret 等价准则**（Δ=+0.565 > ε=0.05）；可修复性是"契约层面"的 | 二手页面引述摘要（**未通读**） |

**读法**：这两条是本项目最需要认真对待的邻居——它们在**不同设定下**都指向"模块化本身不带来性能收益"。GenSE-Scheduler 尤其接近本项目的问题形式（单体 vs 多阶段模块化、本地小模型、预注册准则），只是**领域是调度优化代码、且要求类型化契约**。

## 三、与本项目配置的逐项对照

| 维度 | 本项目 M2 配置 | 已有工作是否覆盖 |
| --- | --- | --- |
| 是否训练 | **不训练**（纯提示词） | DecompRL/MoT 都训练；Revisiting/GenSE 不训练 ✔ |
| 是否跨候选重组 | **重组**（k 个实现的组合） | DecompRL 重组；MoT 不重组；Revisiting/GenSE 不重组 |
| 等预算口径 | **等预算比较** | DecompRL 报告 token 曲线；GenSE 报告 regret 准则；其余未见严格等预算 |
| 任务域 | **通用 Python 项目式任务**（后端/CLI/小型库） | GenSE 是调度优化代码；其余是竞赛题或 SWE issue |
| 任务结构分层 | **高可拆分层 + 低可拆分负对照层 + 边界层** | **未见**任何工作按"可拆分性"分层做交互检验 |
| 模型规模 | **本地 7B、8GB 单机** | GenSE 用本地开源权重；其余多为大模型/闭源 API |

## 四、结论（研究缺口）

**判断：本项目的问题没有被直接回答，但被大量"邻居"包围，且邻居的结论大多偏负。**

- **没有**任何一项工作同时满足：不训练 + 跨候选重组 + 等预算 + 通用项目式任务 + 按可拆分性分层的交互检验 + 本地 7B。这个格子是空的。
- 但空的格子不等于有价值：三组证据（DecompRL 的无 RL 对照、Revisiting Modularity、GenSE-Scheduler）都独立指向"**只靠分解、不给训练补偿时，收益难以出现**"。这**显著下调**了本路线得到正结果的先验概率。
- 因此本项目的**可主张增量**只能是下面这种强度的表述，不能更高：
  1. **边界刻画**：用高/低可拆分两层，回答"分解的收益是否随任务结构变化"，而这是既有工作没做的部分；
  2. **本地小模型 + 零训练**条件下的复现性证据（DecompRL 的"无 RL 结论"在通用项目代码上的外部效度检验）；
  3. 工程交付：一套可复跑的项目式任务评测管线与数据审计。

**同时必须写明两条限制**：

- 上述"邻居偏负"的结论**多数来自摘要与二手页面**，本项目尚未通读 Revisiting (2407.11406) 与 GenSE-Scheduler 原文，"摘要可能有选择性"这一风险未排除；
- 本轮**没有逐会议检索**，可能漏掉更贴合的近两年工作（见 `01_public_dataset_search_log.md` 第五节）。
