# WP1-2：公开数据集全景（第一轮，按任务单元排序）

日期：2026-09-28 ｜ 状态：第一轮，召回完整性未验证（见 `01_public_dataset_search_log.md` 第五节）
读法：本文件只做"分类与结构判断"，**许可证、可运行性、污染风险的一手核实属 WP2**。凡标 `【推断】` 者均未实测。

## 一、一句话全景

现有公开代码基准可以按**任务单元**排成一条轴：越靠左越便宜好跑、但越不满足本项目的"多自然阶段 + 接口清楚"；越靠右越接近项目式任务、但越依赖重型容器与长上下文，在本机 8GB 条件下越难跑。**这条轴正是复审预告、FAST-0 已部分实证的那个矛盾。**

```text
函数级（单点）                                  →  仓库/项目级
HumanEval / MBPP / DS-1000 / BigCodeBench         SWE-bench 家族
ClassEval（类级）                                  Commit0（整库生成）
EvoCodeBench / DevEval（带仓库上下文的函数体）        DevBench（分环节 repo 任务）
APPS / CodeContests / LiveCodeBench（竞赛题）        Long Code Arena（多任务）
   便宜、快、测试自带                                     贵、慢、Docker/长上下文
   可拆分性弱                                             可拆分性强但难跑
```

## 二、按任务单元分五类

### 2.1 竞赛/算法题（本项目已用过）

APPS（自定义切分）、CodeContests、LiveCodeBench（含 contamination 控制、持续更新）。
**结构判断**：难度常集中在一个算法洞察上——正是本项目负结果最可能的来源之一。已被上一阶段使用并揭盲，不能拿回来当新证据。

### 2.2 函数级单点题

HumanEval(164) / MBPP(974) / DS-1000(1000, cc-by-sa-4.0) / **BigCodeBench(1140, apache-2.0)**。
**结构判断**：任务单元是"一个函数写对没有"，题内**没有函数间接口**。BigCodeBench 的题虽是"用若干库函数完成一段数据处理流程"（139 个库、7 个领域），函数内部可能确有多个步骤，但**步骤之间没有可独立验证的接口**——按五项判据第 1--3 条，`【推断】` 不满足。
**本机可行性**：BigCodeBench 已实测可跑（FAST-0：5/5 稳定通过，单题约 1 秒；但只限"仅依赖标准库"的 324/1140 = 28.4%，其余 71.6% 含 tensorflow/django/cv2 等重依赖，未测）。

### 2.3 类级题

**ClassEval**（100 题，Python，MIT，手工构造，类内多个**相互依赖的方法**）。
**结构判断**：`【推断】` 这是"函数级"与"仓库级"之间最便宜的一档——一个类里有多个有依赖关系的方法，天然存在"先实现哪个、接口如何定义"的结构问题，同时仍是单文件、无需容器。
**本机可行性**：`【推断】` 高（纯 Python、单文件、测试自带），但**未实测**。
**风险**：100 题规模偏小；题目为手工构造，可能带有"教学式"风格，与真实项目分布有差距。

### 2.4 带仓库上下文的函数体生成

**EvoCodeBench-2403**（275 题 / 25 仓库，字段含 requirement、tests、跨文件依赖，HF 页显示总文件 1.2 GB）、**DevEval**（1874 题 / 117 仓库 / 10 领域，三种上下文设置：无上下文 / 同文件上文 / 同上文+下文）、CoderEval（460 题，Docker 评测）。
**结构判断**：任务单元仍是**单个函数体**，但必须理解跨文件依赖——比 2.2/2.3 更接近真实项目，同时仍以"函数"为交付单位。按五项判据，第 1 条（多自然阶段）依旧勉强。
**本机可行性**：官方都建议 **Ubuntu + conda**，需要准备原始仓库与依赖数据；本机 Docker 守护进程未运行、WSL 内 HF 被阻断，`【推断】` 成本明显高于 BigCodeBench，**未实测**。

### 2.5 仓库级 / 项目级任务

- **SWE-bench 家族**（2294 条真实 issue，12 个 Python 仓库；Lite/Verified/Multilingual/Multimodal/Live 变体）：输入是 issue，输出是补丁，用 FAIL_TO_PASS / PASS_TO_PASS 测试判定。结构最接近"多阶段 + 接口清楚 + 可自动测试"，但**评测依赖每个仓库专属的容器环境**，且有 agent 交互（长轨迹）成本。**HF 元数据未标注许可证**（WP2 硬性核查项）。
- **Commit0**（54 个 Python 库，从零实现整个库；给 spec + 含单元测试的 starter 仓库；只看单元测试通过率）：任务单元是**整个库**，多文件、多函数、相互依赖——**五项判据符合度最高**；代价是任务规模远超 20--30 题探索性试跑的尺度，单题上下文可能大幅超出本地 7B 的输入预算。
- **DevBench**：注意**存在两个同名不同物的工作**——较早的 DevBench（Li et al., 2024，分环节 repo 级：代码设计/代码生成/单元测试合成）与本轮检索到的 DevBench（2026，telemetry 驱动的 1800 题、多语言、合成实例、人工复核）。两者必须分别核实，不得混写。
- **Long Code Arena**：6 个不同任务（含 bug fixing、commit message 等）；HF 元数据查询返回 401。

## 三、对本项目研究问题的适配判断（`【推断】`，非实测）

| 数据集 | 多自然阶段 | 阶段间接口清楚 | 子功能可独立验证 | 可自动判分 | 本机可运行 | 综合 |
| --- | --- | --- | --- | --- | --- | --- |
| APPS 自定义切分 | 弱 | 弱 | 弱 | 是（已建管线） | 是 | 已揭盲，只能作外部参考 |
| BigCodeBench | 弱 | 弱 | 弱 | 是（已实测） | **是（已实测）** | **工程可用、研究适配弱** |
| ClassEval | 中 | 中 | 中 | 待核实 | `【推断】`高 | 便宜的多方法结构，值得审计 |
| EvoCodeBench-2403 | 中 | 中 | 中 | 是（替换 body 跑测试） | `【推断】`中偏难 | 仓库上下文试验场 |
| DevEval | 中 | 中 | 中 | 是 | `【推断】`中偏难 | 规模最大（1874） |
| Commit0 | **强** | **强** | **强** | 是 | `【推断】`低（整库、上下文长） | 结构最贴，代价最高 |
| SWE-bench 家族 | **强** | 中（补丁边界模糊） | 中 | 是（需容器） | `【推断】`低 | 许可证缺失需先解决 |
| DevBench（两个版本） | 强--中 | 待核实 | 待核实 | 是（需容器） | `【推断】`低 | 需先分清版本 |

**结论（供 G1 参考，不代替 G1 决策）**：目前**没有**找到一个"既满足五项判据、又能在本机 8GB 条件下稳定跑"的公开数据集。最可能的现实是：**只能选"结构中等 + 可运行"的一档（ClassEval / EvoCodeBench / DevEval 量级），并把结论收缩为方法主效应描述**；或者走"公开数据 + 自建小规模补充集"的混合分支（G1 选项 3）。

## 四、短名单（进入 WP2 静态审计）

按"工程可运行性 × 研究适配性 × 成本"综合，建议以下 **4 个**进入 WP2（WP1 验收要求 3--5 个）：

1. **ClassEval** —— 最便宜的多方法结构；许可证 MIT 已确认。
2. **EvoCodeBench-2403** —— 带仓库上下文，规模适中（275），测试与依赖字段齐全。
3. **DevEval** —— 同类型但规模更大（1874）、领域覆盖更广，可作 EvoCodeBench 的替代/补充。
4. **Commit0** —— 结构最贴合研究问题（多阶段、多模块、有测试）；即使最终因成本被排除，**排除理由本身也是 G1 需要的证据**。

**保留但不进短名单**：BigCodeBench（已完成 FAST-0，作为"可运行对照"保留在案）；SWE-bench 家族、DevBench、Long Code Arena、CoderEval（暂按 `【推断】` 本机高成本，若第 1--4 项全部不合格，再回头评估）。

> **2026-09-28 补充**：用户开启本机代理后 GitHub 与 Hugging Face 均已直达，许可证已改为一手核实，全部链接与许可证据见 `docs/week3/公开数据集与论文链接清单.md`。同批核实新增两项事实：
> 1. **`seketeam/DevEval` 仓库没有 LICENSE 文件**（GitHub API `spdx=None`），而其 HF 数据集标 `cc-by-4.0` —— 这是短名单里**唯一的硬性许可证风险项**，WP2 必须先解决；
> 2. **Long Code Arena 的 6 个任务已定位到具体 HF 数据集**，其中 `lca-library-based-code-generation` 与 `lca-codegen-{small,medium,large,huge}` 是"项目级上下文 + 多模块"结构，**建议按第二轮候选一并纳入 WP2 评估**（尤其当"如何拆分"成为主攻方向后，它比单函数基准更贴近要回答的问题）。

## 五、必查但本轮未查的硬项（WP2 承接）

1. SWE-bench 家族**许可证缺失**问题（HF 元数据为空）；
2. Commit0 / DevEval / EvoCodeBench 的 **LICENSE 原文**与再分发条款；
3. 各候选**是否 Linux-only / 是否必须 Docker**、WSL2 能否替代；
4. 各候选**数据与依赖的实际体积**及 D 盘落盘方案；
5. **Qwen2.5-Coder 训练数据截止时间**（决定污染判据）；
6. 各候选**公开/私有测试能否切分**（BigCodeBench 每题只有一套测试，这一点尤需设计）。
