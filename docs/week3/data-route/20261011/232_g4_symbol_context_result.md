这是原 G4 的局部执行批次，不修改宏观总计划。三项已有研究池候选各执行一个 seed：

- PR126：confuse 源文件相对路径；
- PR142：confuse 环境配置叠加；
- PR440：more-itertools 组生命周期。

模型为本机 `qwen2.5-coder:7b`，seed `20261011`，`num_ctx=8192`，每臂总预算 6500
（输入加输出）。父源码上下文从 AST 按公开 API 提取完整定义、import、必要常量和真实
行号；不读 feature、正确补丁、评价器或上游测试。模型身份和 tokenizer 哈希保存在
实验目录；本地 tokenizer 的 ChatML 计数与 Ollama 每次 `prompt_eval_count` 一致。

原始实验目录：

`decomposition-bench/experiments/d1_G4_symbol_context_pair_v1_20261011/`

冻结计划与三轮事前审查：该目录 `PLAN.md`、`REVIEWS.md`。

6500 臂预算内，预算不足的后续请求在发出前被拒绝。逐臂结果如下：

| 任务 | 方法 | 请求 | 已耗 token | 结果 |

M2 的计划和组件回复全部保留；组装没有在预算不足时发送。没有任何完整候选工作区
被创建，行为评价器没有运行，不能把这批结果写成 0/6 行为准确率，也不能计算主问题
A 的 `Δ`。

## 这批结果区分了什么

前一批固定行段确实遗漏 PR126 的 `Configuration.set_file` 并截断函数，本批已经用
完整 AST API 上下文修复。因此，固定行段遗漏不能再解释本批的失败。完整上下文后，
M0 仍分别出现 hunk 坐标错误和包路径错误，M2 仍受重复上下文预算约束；当前可支持
的判断是：**失败已从“上下文构造缺陷”转为“模型补丁协议不合规或 M2 预算不足”**。

这仍不能分离模型能力、提示格式、预算大小和严格补丁协议各自的比例；尤其不能推出
更大预算一定成功。它只说明在当前冻结的输入、模型、提示、入口和总预算组合下没有
可评价候选。
