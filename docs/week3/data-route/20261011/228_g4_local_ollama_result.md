# G4 本地 Ollama 配对运行结果

## 问题和口径

本阶段只问一个可见问题：在既定 M0/M2 补丁协议、每臂 6500 个服务端输入加输出 token、同一 seed 下，本机 `qwen2.5-coder:7b` 能否为真实项目候选生成可应用的完整补丁。它属于原 G4 的资源条件分支；不回答主问题 A 的收益关联。

实验输入是 PR126 和 PR142 两个 `research_pool_only` 候选，每题一个 seed `20261011`。模型只看到父源码选定片段、需求和公开案例；没有看到 feature、alternative、遗漏控制、正确补丁、评价脚本或上游测试。原始输出和失败均保存在：

`decomposition-bench/experiments/d1_G4_local_ollama_real_project_pair_v1_20261011/`

以及第二次适配尝试：

`decomposition-bench/experiments/d1_G4_local_ollama_real_project_pair_v2_20261011/`

## 实际请求和失败

| 版本 | 题目 | M0 | M2 | 解释 |

v1 共 6 次 Ollama 请求，v2 共 6 次 Ollama 请求；服务端每次响应都保存了 `prompt_eval_count`、`eval_count` 和原始回答。两次运行没有云端付费、训练或强化学习。

## 格式故障隔离

v2 两份 M0 回答都以一个前导空格加 ` ```diff` 开始。对原回答做一次不调用模型的格式剥离后，严格补丁解析继续在原行内容处失败：

- PR126：`PatchFailure: 原行内容不匹配，拒绝模糊应用`；
- PR142：`PatchFailure: 原行内容不匹配，拒绝模糊应用`。

因此，失败不是只由代码围栏造成；模型生成的 hunk 与父源码也不一致。格式诊断的原始结果在 `v2/format_repair_diagnostic_summary.json`，不计作严格 M0 候选。

## 阶段结论

四个题目×方法臂都没有形成可应用的完整候选，行为评价没有可定义的分子，不能把 0/4 写成行为准确率，也不能计算主问题 A 的 Δ。当前配置给出的实证边界是：

1. 6500 总 token 在完整项目上下文和 M2 重复上下文下不足以稳定完成协议；
2. 即使压缩到预算内，模型回答仍可能违反严格 unified diff 坐标，导致补丁入口失败；
3. 仅把前导格式剥掉不能修复 hunk 错位，不能把后处理候选冒充原方法输出。

这排除了“旧 DLL 是唯一阻碍”的解释，但没有区分模型能力、上下文裁剪方式和预算大小各自的比例。由于任务仍无真实人工双审、`formal_labels=null`、`split=null`，本阶段没有模型效果或主 A 结论。

## 阶段审查

目标已达到：取得真实服务端计量、原始生成和可复查失败。预算超限、计划解析、补丁坐标三类失败均有原始响应和分母；没有覆盖旧输出。阶段状态为 **complete with boundary**，不是方法成功。

## 方向审查

否决继续缩小提示、反复剥格式或重复同一模型请求：两次实质适配已显示预算和补丁协议的不同失败，第三次同支路预计只产生包装性信息。也否决把格式修复后的半补丁当作行为分数。按原计划转 G5，交付“当前资源条件不可取得主 A 实证”的适用边界，并保留未来若要改变预算、模型身份或补丁协议时的资源缺口；这需要新的明确计划，不在本阶段暗开。
