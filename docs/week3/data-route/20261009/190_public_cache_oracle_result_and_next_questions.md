## 三轮新问题深挖与审核

第一轮：N1新oracle是否仍会接受读取时才清理的实现：来自P94公开len/items可能触发expire的真实代码路径，且需求禁止读取补做清理；N2完整代理的全部API回归无法用有限小样本保证且偏离当前功能，否决；N3再跑模型缺少校准身份与预算依据，否决。N1与评价可识别范围、内部自由直接相关，不是无故扩输入。

第二轮：N1具体机制是expire先计算报告并记pending时间，首次公开读取才调用完整清理；读取后全部报告/状态可以与即时版相同。仅比较外部返回无法证明内部事件时点。需要一个实现级见证（诊断用底层状态或控制实现自己的清理事件账，而非把诊断反过来当通用oracle），同时证明公开观察接受它。若存在，就应区分“可观察的操作后状态”与“不可直接观察的物理清理时点”；不简单回退到固定Cache基类存储，也不宣称黑盒能证明所有内部义务。

第三轮：最低成本先定向读原父/feature公开迭代/len/currsize调用路径，构造一种read-repair控制的可行性计划；正式实验最多一个原mixed输入，两程序，模型0，不能再扩随机格。结果若成立会决定删/改未来候选的不可观察物理条款，具有否定价值；若不成立则保留具体失败，不无限做伪装实现。最终选择N1为P95，先有限源接口调查，详尽计划需再三审。原任务/需求不追溯修改，任何规范变化另存并说明理由。
