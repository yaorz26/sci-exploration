## 新问题与可见目标

**具体未知**：PR126 这个真实跨组件功能，能否在同一个父版本、同一功能需求和同一个行为 oracle 下，形成一对“整体实现任务”和“阶段分解任务”候选；如果不能，主问题 A 的任务构造会继续被项目上下文差异或泄漏混淆。

**竞争解释**：

- H1：可以建立成对候选；两种任务只改变任务组织方式，仍共享同一父快照、功能需求、行为例和总 token 计量入口。
- H2：跨组件接口和对象状态使阶段任务无法保持与整体任务相同的功能义务；强行拆分会改变题目，成对设计不成立。
- H3：表面上能配对，但合并补丁、内部参考或阶段答案会泄漏到任务输入，或整体/阶段输入成本不可公平比较。

**最终可见结果**：一个 `paired_task_blueprint.json`，包含整体视图、阶段视图、共同父快照、共同需求与行为 oracle、拆分字段、输入泄漏检查、token 计量待办和明确的可用/否决结论。它是数据集构造证据，不是模型效果。

## 详尽计划

1. 从已保存的 PR126 父/合并快照和 `task_spec.json` 固定共同任务需求；不再下载文件、不读取上游测试、不调用模型。
2. 整体视图只描述“在父快照上实现该功能并保持旧行为”；阶段视图拆成源元数据、模板解析、文件载入传递三个有明确输入输出的阶段。两视图共用行为例与合并参考，但合并补丁只在研究侧保存。
3. 对两视图执行静态一致性检查：共同父提交、需求语义、行为例、依赖组件、oracle 关系、私有参考隔离、formal labels/split/model/human 状态。
4. 若阶段视图必须改变功能义务、无法定义公共 oracle或暴露参考答案，输出否决结论并保留失败；若通过，只登记一个研究池成对候选，不修改 initial20。

## 计划执行前的三轮严苛审查

### 第一轮：可行性与替代路线

**审查**：所需父/合并源码、需求、诊断和参考已在本地保存；不需要模型、人工或新下载，能在一次脚本中生成候选。

**风险**：阶段任务可能需要暴露前一阶段的真实中间对象，且 token 预算尚未测量。

**修订**：目标降为“任务构造可行性”而不是“生成效果”；阶段输入输出只写行为契约，不放参考代码；token 只登记为待测量字段，不假装已公平。**结论：通过，可执行。**

### 第二轮：意义与重心

**审查**：单个成对候选不能估计 A 的关联，但它能检验数据集是否具备同题不同组织方式的基本单元，直接补 P40 暴露的“无对照”缺口。

**风险**：若继续增加更多 PR 或更多例子，会再次变成候选数量和覆盖率竞赛。

**修订**：只允许一个 PR126 成对蓝图；通过或否决都算结果；禁止同 PR 扩格、静态门和重复参考。**结论：通过，贡献边界明确。**

### 第三轮：区分力、泄漏与可信度

**审查**：公共 oracle 可由已保存父/合并 API 诊断复查；合并补丁、上游测试和隐藏数据不进入任务输入；两个视图必须共用父提交和行为例。

**风险**：阶段拆分天然引入中间接口，可能让题目义务不同；没有模型调用和人工审查，不能声称效果或正式标签。

**修订**：蓝图增加“共同义务/新增阶段义务/不可比较点”字段；任何不能保持共同义务的设计直接标为 `rejected_for_A`。正式三轴、split、人工和模型字段继续为 `null/0`。**结论：通过，但只作为研究池构造结果。**

三轮审查后的执行范围冻结为：一次蓝图构造、一次一致性检查，不扩展候选、不运行模型、不发布数据集。

## 完成后的下一问题挖掘要求

本循环完成后，从蓝图结果出发进行三轮问题挖掘：第一轮找出蓝图中实际暴露的机制缺口；第二轮追问该缺口是否来自任务本身、拆分方式还是 oracle；第三轮比较最低成本的下一验证与否决理由。只有审核后才能选下一循环，不以“继续增加候选”为默认方向。
