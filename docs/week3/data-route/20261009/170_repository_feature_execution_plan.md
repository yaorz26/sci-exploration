# P83：把真实功能候选变成可运行的项目任务

169号中的“整体—阶段成对蓝图”未执行，已撤回：按已知补丁指定源元数据、模板、载入三个阶段可能向方法泄漏答案结构；主问题A应允许合法内部拆法。该文中的旧总结保留，正式下一步以本计划为准。

## 问题、竞争解释和可见结果

问题：基于PR126的公开功能需求，是否能构建一个可运行项目任务，让同一行为测试识别“接口存在但语义没接上”和“解析正确但文件载入入口未传参”的不完整实现？这是数据集实质缺口：可运行源码和演示例尚不等于能评价候选项目代码。

H1：完整功能与两种不完整实现能被同一需求的行为测试区分，项目任务可用。H2：测试只查新参数是否接受，接错组件仍可通过。H3：测试要求补丁的内部结构，合法替代实现被误拒。行为期望来自外部路径规则，不要求具体源码行或helper结构；H3仅能局部检查，不能穷尽所有合法实现。

最终产物：一个研究池项目任务目录，含真实父版本包源码、中文功能需求、公开行为测试、可对任意修改后工作区运行的评价脚本；研究侧保存完整合并版本、父版本和两个有明确遗漏的控制版本的实际测试输出。结果必须明确哪种遗漏被哪条测试发现、仍欠缺哪些验证，不能用总通过数代替解释。

## 执行计划草案

1. 固定已有父版本与公开功能需求，把PR来源及合并答案保留在研究侧；不下载、不读上游测试、不碰initial20隐藏数据。
2. 将路径例改为运行时临时目录，写一个只调用公开API的测试模块。只覆盖功能链关键义务和保持旧行为所需的控制，不扩同PR输入格。
3. 做可对任意工作区运行的评价入口，收集每项实际结果；所有输出独立落盘，不覆盖P80—P82数据。
4. 一次性执行父版本、完整合并版本、仅更新sources版本、source/template更新但core仍旧版四个固定工作区。后两者模拟特定接口遗漏，不是模型结果；不能据此估计模型错误率。
5. 根据逐项结果保留或否决此任务，记录行为测试与任务适用边界。没有模型生成、人工标签、正式储备切分或发布。

预算：25分钟/最多两次有实质修订的实验；四工作区一批执行；模型0、人工0、下载0、付费/训练/RL/发布0。首批若失败只允许因明确代码/规范缺陷修订一批，保留旧输出。不要再跑P80/P81参考或静态门。

## 第一轮审查：可行性（对上述草案）

实际资源：两个历史版本七个Python模块和许可已保存；本机Python3.13.7已成功导入该历史包和PyYAML。无需恢复README或安装元数据即可通过显式sys.path运行。四个独立工作区可以复制已保存非测试源码，禁止合并前后在同一Python进程导入后串库。

发现：原下载并不是完整Git工作树，不能称完整仓库恢复；临时目录、应用配置目录发现和机器环境可能让结果漂移。

修订：产物标为“真实项目包源码任务”，不称完整仓库集成；评价器每工作区独立子进程，禁用自动配置读取，把应用目录与cwd固定到TemporaryDirectory；只使用已验证依赖，并保存Python/PyYAML版本。缺依赖或导入失败报告环境错误，不计功能失败。

结论：第一轮通过。修订后的计划具备实际执行资源；后续意义审查须审查此收窄版本。

## 第二轮审查：意义（对第一轮修订后的计划）

已有P80诊断能区别旧版拒参数与新版接受参数，P81四例已复核；单纯再跑这些例没有新增判断。真正未知是评价能否在参数已接受时识别跨组件遗漏，并且能用于任意修改后的项目代码。

发现：若本次只有更多路径例或成对文本，仍是过度评测；自制控制也不是真实模型缺陷分布。

修订：取消成对蓝图和预给阶段拆法；任务给一个共同外部需求和父源码，各方法自行组织。主结果限定为“评价入口是否拒绝两个具体不完整实现，并给出失败位置”，同时交付该可执行任务；已有默认/绝对路径只作为必要回归控制，不称新增发现。若两个遗漏不能被区分则否决测试设计，而不继续加输入数量。正式标签、模型收益及泛化结论保持未知。

结论：第二轮通过。与旧例的差别是新增不完整实现辨别和可用于项目候选的执行入口，具有数据集实质价值；第三轮继续检查是否把参考答案当任务义务。

## 第三轮审查：区分力与可信度（对第二轮修订后的计划）

两种遗漏有不同预测：仅sources更新能接受源标志，但Filename仍按应用目录解析；sources/templates更新且core旧版能正确解析源标志与模板标志，但set_file新增入口仍拒参数。逐项外部行为可以区分它们，不需检查源码结构。

发现：P81需求“应用目录选项应覆盖源目录”表述过宽。公开功能中in_app_dir覆盖源级base_for_paths，而显式模板in_source_dir具有自己的优先级；任务必须写清，不能沿用模糊语句。旧脚本曾覆盖重跑输出、把占位符字符串误当绝对路径，本次应杜绝这两个缺陷。

修订：功能需求明确cwd优先、in_source_dir对有filename的源显式启用源目录、in_app_dir只覆盖源级base_for_paths、无filename时源级标志无效并保持cwd行为；测试用os.path.join生成绝对期望，不复制参考输出。评价器输出用独占新建；四版本各独立子进程；所有测试均为研究公开诊断，不假称隐藏/未见确认。完整合并版本作为正控制，另外两个固定遗漏作为负控制，不声称穷尽错误或合法方案。

结论：第三轮通过。冻结执行范围为一个项目包源码候选、一个行为评价器、四个工作区一批对照。H1/H2能区分；H3只能靠行为约束降低结构偏好，合法替代方案完整性未知，必须保留此边界。

状态：三轮审查完成，可按修订后计划执行。三轮均为助手自审，没有人工独立审查。
