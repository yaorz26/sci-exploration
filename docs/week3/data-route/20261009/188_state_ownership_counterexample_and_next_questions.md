# P93：状态所有权误拒与时点漏收

同一个原boundary_mixed输入，timer固定2、显式expire4，a/b期限4/6。四种项目组织独立运行，先观察调用后、再消费返回。所有预测符合。

| 项目组织 | 返回a正确 | 消费前公开剩b/len1/size2 | 消费后旧Cache基类剩b/size2 |
|---|---|---|---|
| 完整feature | 是 | 是 | 是 |
| 内部委托完整feature | 是 | 是 | 否：外层存储空/size0 |
| 仅报告不删除底层 | 是 | 否：len2/size4 | 否 |
| 延迟生成器 | 是 | 否：调用后a仍在 | 是 |

反例含两种不同错误：旧底层观察会误拒本输入公开行为相容的委托组织；消费后观测会漏收本输入的延迟清理。timer2早于a到期4，公开len/currsize自动expire2不能补做显式expire4，因而这一具体公开观察可以保留区分力。没有回退timer或强制列表返回。

这是单输入、有限API的控制证据，不是整库代理等价证明。新独特输入0、四组织运行、模型/API/人工0；源码与freeze/raw在`experiments/d1_delegated_state_oracle_v2_20261009/`。v1因-I无法导入研究侧工具而四进程未进入项目行为，stderr与失败审查保留，一次修复后v2完成；不能把v1报为四个功能失败。

阶段审查：H1得到本输入反例支持，H2在本输入所查API未出现；H3不能泛化否定全部公开观察，具体future-expire设计拒绝两错误控制。Cache基类是公开类型，但对其显式非虚调用额外固定了状态存储所有权；任务没有要求这一组织。

方向审查：结果直接影响内部自由与数据集评价有效性，值得修订一个任务评价器；停止更多代理/随机输入格，原定义、oracle和分数不追溯改。P92DLL问题仍未解决，不再调用模型。

## 三轮新问题挖掘与严审

第一轮：N1把这个反例正式纳入可运行任务评价，是现有候选缺口；N2继续证明所有缓存API等价无有限低成本保证且超出题目，否决；N3修DLL是资源侧支撑，保留后置。N1必须回查原五输入需求覆盖，不能只有单反例报告而不落到实际评价入口。

第二轮：N1收窄为“原五公开场景能否改用调用后、消费前公开状态观察，既接受两种组织，又保留对仅报告/延迟控制的拒绝”。timer不回退：原五的explicit expire均不早于插入时钟；关键区分案例mixed的显式4>timer2，repeat/same-deadline显式4>timer0。插入时钟6可能已有自动清理，公开len可能不能证明所有潜在物理残留；这是观察范围限制，不能宣称完全代替底层一切真值。
