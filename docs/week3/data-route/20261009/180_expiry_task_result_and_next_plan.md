## 三轮下一问题挖掘与审核

第一轮：N1立即扩第三真实任务会重复未解决测量漏洞，后置；N2模型收益受约98/100预算限制；N3“可迭代返回允许生成器时，清理的时点是否被评价延后观察掩盖”由评价代码先消耗返回再看状态的真实顺序引出，与阶段依赖/共享状态直接关联。优先N3。

第二轮：追问expire调用完成、迭代结果和后续状态观察三个阶段是否混淆。一次性生成器可以只延迟返回枚举，也可以延迟实际清理，二者不同；当前任务措辞没有显式写明调用返回时完成删除。必须先判断评价能否区分，而不是直接把所有生成器拒绝。若两种都通过，暴露的是测试和需求时点缺口；不得把事后新增条件追溯写成已冻结真值。

第三轮：最低成本构造两个真实项目工作区：及时清理+生成器报告，延迟清理+生成器报告。用同一新fresh场景同时观察调用后/消费后的基类存储，旧五场景不得重复整批。若旧评价只消费后观察，它们可能无法区分；结果会决定需求是否必须显式规定调用时点及未来测试增量。选定N3，预算15分钟/两尝试，模型0、人工0、新输入1个，不扩功能领域。

## P89详尽执行计划与审查

目标为两种生成器实现的实际时点记录，明确是否存在测试/需求不足。共享完整feature源码，通过追加包装expire分别及时/延迟调用原清理；对同一个a在ttl4、expire(4)场景观察调用返回后的原始存储、消费返回的pairs、消费后的原始存储。期望及时版调用后空、延迟版调用后保留a、消费后两者均空和返回a。先保存程序/预测，再一次独立进程执行。禁止改P88原始定义/测试/输出；若需新规范另存增量。
