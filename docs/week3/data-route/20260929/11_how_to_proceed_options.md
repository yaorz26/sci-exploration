# 接下来怎么办：可选路线、代价与我的建议

日期：2026-09-29 ｜ 性质：**选项分析**（研究方向的结论性判断属用户/导师；本文件只给证据、代价与推荐顺序）
触发：用户提问"有什么解决办法"。背景＝WP6 结果：M0 6/24、M1 7/24、M2 6/24（更正后），双零题 70.8%，M2 成本约 M0 的 4.7 倍，G2 已正式收束。

## 一、先把"要解决的是什么问题"分清（三件事被混在一起了）

| 编号 | 真正的问题 | 我们的实测证据 |
| --- | --- | --- |
| **P1** | **7B 能力天花板**：题太难，模型根本写不出来 | **双零题 70.8%**（M0 与 M2 都不过）；P0 探针池上限仅 25% |
| **P2** | **我的实验装置有两个可修缺陷**，使 M2 被低估 | ① 组装器初版吞掉方法（已修）；② M2 提示词未禁"重定义已有辅助方法"（`_to_camel_case`、`_select` 各被定义两次）+ 未做语法校验重试（`ClassEval_5` 三引号未闭合） |
| **P3** | **任务域结构与研究问题错位**：ClassEval 的 API 必须给定 → 检验不了"拆分方案的选择" | 冻结清单 v1.1 的 `structural_constraint`；公开测试不足（4/24 出现"公开过、私有不过"） |

**P1 是主因，P2 是自家装置的瑕疵，P3 是选题边界问题。** 下面按"先修正自己的装置 → 再判断有没有可测空间 → 再决定是否换域/要资源"排序。

## 二、解决办法清单（按性价比排序）

### 方案 1（**最便宜、必须先做**）：做一次 v2 公平试验——修 P2 + 加候选

**做什么**：
1. 三臂**统一**加"语法校验 + 不合格重试一次"（同一规则，不许只给 M2）；
2. M2 的逐方法提示词加两条硬约束：**禁止定义骨架里已存在的方法名**（除正在实现的那个）、必须闭合三引号；
3. 每题候选数从 **1 提到 2**（能区分"首候选成绩"与"候选池上限"）；
4. 全部结果写成 v2，保留 v1 不动。

**代价**：约 **344 次调用、1.5--2 小时**本机算力（生成），无需新资源。
**能回答**：M2 修好后是否仍 ≤ M0？**候选池上限**比首候选高多少（这决定"选择"这一半有没有空间）。
**风险**：这是看到结果后改装置，**必须按协议变更处理**（新版本 + 保留 v1 + 报告两版），否则等于调参凑方向。我已按此规则执行。

### 方案 2（便宜，与方案 1 同时可得）：把"选择"这一半补上

项目此前唯一的正结果来自**选择侧**（helper-first FunPRM：`12/60` 对首候选 `7/60`，池上限 `14/60`）。
当前 M0 首候选 6/24，**池上限未知**——如果池上限明显更高（例如 10/24），说明瓶颈在"选不出来"，那么做评分器/选择器实验才有意义；如果池上限也就 6--7，说明**根本没有可选的候选**，选择侧这条路在本题域上直接死掉。
**这一步的信息量最大，且完全包含在方案 1 里。**

### 方案 3（中等成本，1--2 天评估）：换任务域，走自建小数据集（WP4B）

**为什么**：公开数据里"多阶段 + 接口清楚 + 能自动判分 + 本机可跑 + 许可干净"的**只有 ClassEval 一个**（我们审了 5 个候选，G1 已给出 1/5 的结论）。要检验"拆分方案的选择"，必须换到**API 不由数据给死**的任务形态。
**具体路径**：从 GitHub 小库挑**模块级**任务（如 Commit0 那种"实现一个模块/一组函数"的结构，但规模缩到本机可承受），自己写 starter + 公开/私有测试 + 需求反推审查。
**代价**：20--30 题约数天（人工审需求泄漏 + 测试隔离 + 许可证记录）；按你的规则**只有自建分支才有"数据集算成果"的可能**。
**风险**：GitHub 项目代码可能被模型见过（污染风险仍不可控）；小规模 → 仍只能称探索性。

### 方案 4（性价比最高的"升级"，需要资源）：强模型分解 + 本地 7B 实现的隔离实验

**做什么**：用强模型（API）只负责"拆分"，7B 只负责"逐子任务实现"，把"分解策略质量"与"实现能力"彻底分开。
**为什么值得**：这一条能直接回答"瓶颈到底在分解还是在实现"——而 P1/P2 的证据都指向**实现能力**；如果强模型拆得更合理而 7B 仍写不出，就能把"拆分无用"的解释彻底排除掉。
**代价**：约 **80 次强模型请求**（已登记为候选方向②）+ 本机 7B 生成；需 API 额度或课题组资源。
**风险**：需要资源；结论仍是"本地 7B 条件下"的边界刻画。

### 方案 5（贵，本机不现实）：引入训练补偿

**证据**：文献里"分解有效"的正结果几乎都带训练补偿——MoT（SFT，APPS `+5.8%`）、DecompRL（RL，但要 **80×H100** 且收益到每题 **≥5 万 token** 才出现）。
**本机可做的最小版本**：QLoRA 做**分解式指令微调**（本机有 7B QLoRA 先例：75 题 140 节点、10 epochs、175 步）。
**代价**：先要造"分解式"训练数据（要么用强模型生成 MoT 格式数据＝花钱，要么人工写＝很慢）；必须另立协议、预算与稳定性门槛；**结论标签要改**（"训出一个会拆分的模型"≠"拆分机制有效"）。
**现实判断**：**不推荐现在做**，除非方案 1--4 都排除掉且导师愿意投入。

### 方案 6（零成本，纯立场调整）：把结论从"拆分是否有效"改成"何时不该拆 + 接口设计"

**已有证据足够支撑这条收束**（也都是可以发表的工程事实）：
- 接口类失败的具体形态：**各部分独立实现会重复定义辅助方法并覆盖签名**（`_to_camel_case`、`_select` 两例全错）；
- 逐方法输出**语法不完整**会在组装时才暴露（`ClassEval_5`）；
- 公开测试**不足以做选择**（4/24 误判）；
- 类级任务对 7B 而言**双零率 70.8%**，属"能跑但偏难"的档位。

### 方案 7（零成本）：把已建成的评测装置当作独立产出

**已经就绪、换任何方向都能复用**：ClassEval 派生物 v1（91/100 可稳定判分、公开/私有按方法切分、24/24 校验通过）、冻结清单、双环境跑法（Windows py3.13 + WSL py3.10/numpy1.x）、可复跑脚本与 10 个单测、以及"160 次调用/30 分钟"这类**本机可承受规模**的实测数字。
按你的规则，公开数据的**派生物可以署名发布**（须写明来源与原作者、遵守原许可），**不得称新数据集**。

## 三、我的建议（一句话版）

**先做方案 1（含方案 2 的信息），这一步便宜、且能把"是不是我们自己装置的问题"彻底排除；做完再决定是走方案 4（要资源）还是方案 3（自建换域）或者干脆用方案 6 收束。**

判断依据：如果 v2 后 M2 仍 ≤ M0、且池上限也没空间，那么**在这个任务域上，"拆分"这条路已经用本机能做到的最干净方式证伪了**——继续投入的边际收益很低，应该换域（方案 3）或换手段（方案 5/4）。反之，若池上限明显高于首候选，则问题转向"选择器"，方案 2 值得单独做一轮。

## 四、本文件不回答的事

- 不替用户/导师决定研究方向的取舍（换域、申请资源、是否训练）；
- 不承诺任何方案能得到"正结果"——按现有证据，**在不加训练补偿的前提下，得到正结果的先验概率偏低**，这一点必须写在前面。
