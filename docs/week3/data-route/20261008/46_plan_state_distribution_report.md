# P20结果：任务的操作状态不唯一决定实际方案的共享状态

C03在相同两个helper数下，存在三种通过有限外部检查、持久状态边界不同的手工实现：缓存和计数可以由入口持有，可以封装在一个helper，也可以由入口初始化后传给两个helper。任务级“有操作历史状态”因此不能替代生成方案级“哪些组件读写同一持久状态”的记录。这里证明的是三个具体实现的可行性，不是某种拆法更好、模型更容易生成，或所有有状态任务都能消除跨组件依赖。

## 冻结与行为检查

三份代码及候选状态描述先冻结，再运行原C03的2公开、9隐藏案例。3/3程序全部通过，即33次原案例求值；原案例没有增加。新代码是重评理由，未重跑无关任务或历史模型失败。

有限比较域为容量0/1/2、五种动作（两种位置参数调用、两种关键字调用、clear）、操作长度0—4。共有2343条不同输入序列、7029次程序求值，三结构输出均一致且输入未修改。这些序列只支撑声明的有限域，不是新增独立任务或原307用例。

| 方案 | 持久状态的位置 | helper之间共享持久可变状态 | 仍存在的依赖 |
| --- | --- | --- | --- |
| state_in_entry | solve持有缓存/计数 | 否 | 入口调用键与求和helper，按操作顺序维护缓存 |
| state_encapsulated_helper | _run_ops持有缓存/计数 | 否 | _run_ops调用纯_call_key；solve调用_run_ops |
| state_shared_between_helpers | solve初始化，_update更新，_render观察 | 是 | 两helper经参数取得同一内部state，先更新再输出 |

第三结构另保存一次三操作调用轨迹，六次update/render调用均收到同一state对象，计数1、2、2，观察输出与冻结的入口方案相同。该轨迹是具体程序的运行证据，不是任意程序状态分析器的可靠性验证。

## 第二遍质疑与研究影响

第一、前两结构并非“没有状态依赖”：状态只是留在入口或一个组件内部。helper读取同一输入args/kwargs，也不等于读取跨操作缓存。必须分别记录只读输入、符号调用、返回值数据流和持久可变状态；本表只回答最后一项。

第二、第三结构的state是新建内部对象，不是payload；共享内部状态与修改测试输入是两回事。输入未变检查没有否认内部对象会变化。

第三、候选状态表由助手在执行前编写，行为通过只能支持实现满足有限外部需求，不能自动证明表中语义分类是人工真值。helper数固定也没有控制代码量、接口复杂度或推理难度，不能据此做收益因果结论。

第四、后续主问题A若以任务属性解释收益，任务侧历史/实体耦合证据与生成后方案属性应分开报告。方案属性可能是方法产生的结果，不应事后当成随机前置分组，或只保留成功方案来计算关系。

阶段目标达到，模型/API/下载0、人工0，原20题、307记录与11/9切分保持。接续P21：检验错误固定输出是否也能通过有限隔离关系，从而明确结构关系证据用于诊断候选程序时的边界。原P12使用需求参考与另一结构实现，不能把新的退化例子倒推成原关系结果错误。
