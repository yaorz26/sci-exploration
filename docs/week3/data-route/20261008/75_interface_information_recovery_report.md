# P34：限定接口不足不等于任务无法拆分

M05的两输入columns=[[2,1],[a,b]]与[[1,2],[a,b]]经键排序helper都输出[1,2]，其非键列、共同长度也相同。但正确标签分别为[b,a]与[a,b]。若后段只能见这三项，相同输入必然给同样结果，至少一项无法正确；这是相对于明确裁剪边界的信息不足见证。

三个手工计划的六手算输入共18次完整程序求值。错误连接只排序键列、不重排行身份，通过3/6；helper返回行索引再收集、保留相同键值helper但入口读取原键列重新计算索引，两修复均通过6/6。六输入包括碰撞两输入、稳定同键、reverse稳定、短列导致空共同域、strict明确拒绝；不能称完整允许域覆盖。三个计划的排序helper局部求值18/18符合手算，错误与入口重计算计划的helper AST完全相同。

第一碰撞输入上，错误/索引/重计算计划的sorted调用分别1/1/2，后者调用来自helper和solve。只说明这个程序多做一次排序；没有计时对比、模型token或成本效果结论。六完整输入均保持，预期异常按ValueError符合性判断。旧640格/旧参考/隐藏新读取/模型/API均0。

结论改变了前一阶段解释的边界：信息碰撞否定的是某个限定中间接口的充分性。若完整原输入仍可访问，后段的可见信息已不同，重计算可修复；所以不能从接口反例推出任务不可拆分或实际M2必失败。任务侧联合判断机会、计划侧接口，以及实际方法允许的恢复操作需要分别记录。两个修复没有宣布谁更优，行为正确也不证明模型能生成该方案。

阶段审查：保存首手算未覆盖，代码与锚点先冻结，六手算及同helper对照区分竞争解释；未扩成原测试或未见确认。第二遍换问题回查完整payload差异与sorted调用，仍同助手而非独立人工。P31既有隐藏描述暴露限制保持。

方向审查：停止增加同类排序缺陷，转P35定向回查真实M2入口提示/门槛的可见信息及恢复限制。若实际入口可以访问原payload、重新计算甚至不用helper，则分解比较属于具体生成流程，不是严格受限的单向组件组合实验；必须依实际源码与保存请求区分已执行与仅模板。
