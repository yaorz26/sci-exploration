## 1. 对 DecompRL 的准确理解

### 1.1 论文真正做了什么

DecompRL 不是“让模型多写一个计划”的提示词技巧，而是一个面向高推理预算的层级搜索和 RL 训练框架：

```text
题目 x
  -> decomposition policy 生成 D = {函数签名 + docstring}
  -> implementation policy 为每个函数生成 k 个实现
  -> 从各函数实现中重组完整程序
  -> CPU 执行测试，得到完整程序 reward
  -> 用多样本目标和 leave-one-out advantage 更新策略
```

论文的关键建模假设是：给定分解 D 后，各函数实现近似条件独立：

```text
pi(D, I1, ..., In) = pi(D) * product_i pi(Ii | D)
```

若每个函数有 `k` 个实现、共有 `n` 个函数，则只生成 `n*k` 个实现，却最多得到 `k^n` 个完整程序组合。论文的收益主要来自：

- 生成成本在 GPU 侧近似线性；
- 组合数量和 CPU 执行评测量快速增加；
- 在高 `pass@k` 或高 token 预算下，组合可能找到普通整段采样没有找到的解。

论文还明确给出三个限制：

1. **无 RL 的层级推理有 format tax**。Qwen 2.5 7B 的 LiveCodeBench pass@1 从标准生成的 14.0% 降到无 RL 层级生成的 11.0%。
2. **低预算不一定受益**。层级结构损失单次精度，收益主要在高评测预算出现。
3. **训练可能发生拆分规模坍缩**。分解策略可能退化到只生成一个函数；论文用 logmeanexp、leave-one-out baseline 和交替训练缓解这一问题。

关键量化证据应按下面的口径理解：

| 证据 | 论文结果 | 对本计划的含义 |
| --- | --- | --- |
| Qwen 2.5 7B 的预算曲线 | 10k token 时 DecompRL 为 0.25，低于最佳基线 0.32；50k 时 0.40 略高于 0.39；100k/500k 时为 0.44/0.48，高于最佳基线 0.41/0.46 | 主要假设是高预算搜索收益，不能只看低预算 pass@1 |
| 512 次评测的成本分解 | DecompRL 约生成 4k token，标准 512 样本约 198k token；但两者执行时间相同，DecompRL 总时间仍约 99.6% 花在 CPU | 本机必须同时量 GPU token 与 CPU wall-clock，不能把组合写成“免费” |
| decomposition bottleneck | Appendix F 的实验显示去掉 implementation training 并未伤害 pass@10，作者据此认为 decomposition policy 是主要 RL 瓶颈 | 若进入 P6，先训练拆分器，implementation policy 放第二阶段 |
| reward tensor 近 rank-1 | 仅在 20 个“至少有一个正奖励”的分解中，17 个与 rank-1 近似完全一致；总体有 34 个 false positive | 模块独立性有初步证据，但样本小且经过正奖励筛选，本地必须单独测交互失败 |
| 无 RL 层级基线 | Qwen 2.5 7B 在约 4k token 的 pass@1 为 11.0%，标准生成是 14.0%，RL 后为 18.0% | M2a/M2b 失败并不意外；没有机制正信号时不能直接假定 RL 会补救 |

论文完整训练设置是 15,000 道题、两份模型副本、每个阶段 30k steps、`nmax=6`、`k=8`、每题最多抽样评测 512 个组合，并使用 80 张 H100。这个设置不属于本机可复现范围。

### 2.4 7B/8B 的实测边界

“8GB 显存跑不了 7B”这一说法过于绝对。2026-09-14 已用本机 Ollama 对 `qwen2.5-coder:7b` 和现有 `dolphin3:latest` 8B `Q4_K_M` 做短推理。

Qwen2.5-Coder 7B 的实测记录：

- `ollama show -v` 显示基础模型为 Qwen2.5-Coder 7B Instruct（7.6B 参数、`Q4_K_M`）；模型文件约 4.7GB，`ollama ps` 显示 `100% GPU`，4096 context 加载后整卡使用约 `6952/8188MiB`，仍有约 1006MiB 空闲；
- 同一段 Python 代码生成，冷启动（包含加载）总耗时约 24.3 秒，热调用总耗时约 0.62 秒；Ollama 统计 `eval_count=14`、`eval_duration=0.396s`，持续生成约 35 token/s；
- 以“区间合并”题做分解协议 smoke，要求 JSON 输出 `functions/name/signature/docstring/depends_on`，一次返回 5 个函数及有向依赖，JSON 可解析；这只能证明接口可用，不能外推分解正确率；
- 将上下文提高到 8192 后仍显示 `100% GPU`、约 `6941/8188MiB` 使用，没有发生 CPU offload；但同一“只输出代码”提示出现了额外解释文字，说明上下文容量与格式遵循是两个独立 gate；
- 返回结果可直接解析为 Python 函数。该测试证明的是 7B 4-bit 推理和服务调用可行，不代表 7B QLoRA 训练可行。

作为交叉检查，Dolphin3 8B 的实测记录：

- 模型文件约 4.92GB；加载后 Ollama 报告 `size_vram=5,271,726,325` bytes，即约 4.91GiB，完整放在 GPU；
- 加载后整卡使用约 7400/8188MiB，只剩约 558MiB；
- 4096 context、128 个输出 token 的代码生成实测总耗时约 7.7 秒，其中冷加载约 4.6 秒，持续生成约 43.5 token/s；输出因 `num_predict=128` 被截断，因此该测试只用于容量和吞吐，不评价代码正确性；
- 上述长测加载后整卡使用约 7275/8188MiB、余量约 683MiB，足以推理但几乎没有训练余量；
- 卸载后整卡使用约 2357MiB、空闲约 5601MiB，说明 Windows/桌面与其他进程已经占用约 2.3GB。

因此应区分三件事：

| 任务 | 判断 | 原因 |
| --- | --- | --- |
| 7B/8B GGUF 4-bit 推理 | **已证实可行** | Qwen2.5-Coder 7B 和 Dolphin3 8B 均已完整 GPU 加载并返回结果 |
| 7B 单策略 QLoRA | **可能可行，尚未实测** | 4-bit 权重能放下，但训练还需激活、梯度、LoRA optimizer 和 CUDA workspace；当前后台显存使余量很小 |
| 7B 原版 DecompRL | **本机不可行** | 问题不只是模型大小，还包括 15k 题、两策略、60k 总训练 steps、每题数百次执行和论文的分布式吞吐 |

7B QLoRA 的正确策略是先做显存 smoke，而不是直接排除：`batch_size=1`、sequence length 256 起步、gradient checkpointing、`use_cache=false`、4-bit NF4、LoRA rank 4/8、一次只激活一个 policy adapter。只有 forward/backward 峰值低于 7.5GB 且连续 20 steps 无 OOM，才把 sequence length 提到 512/1024。两策略应共享冻结的 7B base，通过两个 LoRA adapter 串行切换；不能同时放两份完整 7B 模型。

## 3. 研究问题、假设和反例

### RQ1：模型能否稳定产生可组合的分解

**H1**：在明确 schema、接口和依赖要求后，3B 模型能够生成可解析、可组合的函数分解；否则“让大模型调控大模型”的后续实验没有可靠输入。

**反例**：分解经常重复、漏掉主 API、依赖形成环、函数无法独立实现，或组合后的程序大部分不能解析。此时应先研究分解协议，而不是训练 RL。

### RQ2：层级生成的收益来自哪里

**H2**：在相同模型生成 token 预算下，层级方法在高 public 评测预算的 `solve@E` 可能优于整段生成；在 `selected pass@1` 或低预算下允许持平或下降。

**反例**：层级方法在所有预算上都不如文字计划或整段生成，或提高只来自更多 token/更多模型调用。此时不能声称“拆分提高正确率”，最多报告组合机制的成本与失败边界。

### RQ3：什么样的分解有用

**H3**：覆盖主要语义职责、接口输入输出一致、依赖图近似 DAG、各函数能够独立实现的分解，更容易产生高质量组合。

**反例**：人工评分高的分解与组合成功率无关，或函数拆得越多越差。这说明“拆分质量”不能用表面函数数代替，后续应转向任务自适应或不拆分。

### RQ4：小规模 RL 是否值得投入

**H4**：如果 prompt-only 层级方法在留出题目上已有正信号，DecompRL-lite 可以改善分解的组合效用或多样性；如果 prompt-only 没有正信号，RL 只会放大错误接口和 reward hacking。

**反例**：训练 reward 上升但留出题目无提升，或平均函数数坍缩到 1。此时停止 RL，保留机制层负结果。

## 4. 预注册的统一实验协议

### 4.1 数据和切分

1. 先使用现有 `apps_train_introductory50.json` 做机制 smoke，重新生成候选，不复用旧的“单程序 prompt”候选池作为主结果。
2. 在 Introductory-50 内固定题目级切分：20 题 engineering development、30 题 pipeline hold-out；具体 problem ID 写入新的 split manifest。prompt、schema 和阈值只能在 development 上调整。这 30 题只验证流程泛化，不能作为 DecompRL“解决更难问题”的主证据。
3. APPS 当前采用 `input_output` 前半为 public、后半为 private 的自定义划分。private 测试只能用于训练标签/环境 reward 和最终评估，不能出现在分解 prompt、实现 prompt、public 选择、阈值或人工评审材料中。
4. 每种方法使用相同题目、相同生成模型、相同温度、相同 seed 集合（首轮 `42`，确认轮 `42/43/44`）。任何参数变化写入新的 output suffix。
5. P5 科学性比较前，另行固定 30--60 道 APPS Interview/Competition 或 CodeContests 中等/困难题。按预先给定的 difficulty/source 分层纳入，不得根据某个方法的 private 成败逐题筛选。若整个分层上 M0 几乎全对或所有方法几乎全零，只能增加新的预注册难度层，不能删除不利题目。

### 4.2 方法对照

| 编号 | 方法 | 作用 |
| --- | --- | --- |
| M0 | monolithic | 题目 + starter code -> 完整程序，现有 baseline 的干净延续 |
| M1 | text-plan | 题目 -> 自然语言计划 -> 一次生成完整程序，控制“多一个计划”因素 |
| M2a | paper-prompt modular | 使用论文 Appendix I 的 one-shot 函数骨架 prompt，抽取签名/docstring 后独立实现和组合；最接近原始机制 |
| M2b | schema modular | 使用本计划的 JSON 接口/依赖 schema，再独立实现和组合；检验结构化控制是否改善 M2a |
| M3 | human modular | 人工给同一 schema 的分解，模型负责独立实现；用于估计“分解质量”上限，不是公平自动方法 |
| M4 | optional DecompRL-lite | 在 M2a/M2b 的记录上交替更新分解策略和实现策略，仅在前置 gate 通过后运行 |

M3 不能作为主要自动系统的竞争基线，它的用途是区分“模型不会拆”与“拆分本身无效”。M2a/M2b 也不能称为论文 DecompRL，因为没有论文规模的 RL 训练。M2a 与 M2b 必须分别报告；否则无法判断收益来自论文机制还是新增 schema 约束。

### 4.3 两种分解表示

M2a 直接使用论文 Appendix I 的 Python skeleton：函数签名、docstring 和 `pass` 函数体。解析器只做结构提取和错误标注，不擅自补语义、改接口或删除函数。其函数数由模型决定；相同总 token/执行预算耗尽后停止生成或组合，并把未完成原因记为 `budget_exhausted`。

M2b 不输出不可解析的散文，首版要求 JSON，字段如下：

```json
{
  "entrypoint": "solve",
  "functions": [
    {
      "id": "F1",
      "name": "parse_input",
      "signature": "def parse_input(raw):",
      "inputs": ["raw"],
      "outputs": ["data"],
      "depends_on": [],
      "responsibility": "将输入转换为后续计算所需的数据结构",
      "docstring": "..."
    }
  ]
}
```

硬约束：

- `entrypoint` 必须保留 starter code 要求的外部函数签名；
- `functions` 数量首轮限制为 2--4，超过上限直接标记 invalid，不在运行时默默截断；
- 每个函数有唯一 `id` 和可解析签名；
- `depends_on` 必须形成 DAG；
- 每个函数必须有输入、输出、职责和 docstring；
- 不允许在分解结果中写实现代码；
- 允许 helper 函数，但 helper 不能改变外部 API；
- 分解失败要保留原始响应、失败原因和 prompt 版本，不能只保留清洗后的结果。

### 4.4 组合和评测

对每个分解 `D`，为每个函数生成 `k` 个实现。M2b 首轮使用 `k=2`，确认轮使用 `k=3`，函数数上限 `nmax=4`；M2a 保留模型原始函数数，但同样受总生成 token 和执行预算约束。理论组合数为 `k^n`，超过预设执行预算时按固定随机种子采样，不临时按 private 结果挑选。

每个组合必须经过以下顺序：

```text
分解解析（Python skeleton / JSON schema）
  -> 签名与 AST 校验
  -> 确定性组合
  -> public 测试执行
  -> 按冻结 tie-break 选择
  -> 冻结选择结果和完整候选池
  -> 离线 private 评估 selected candidate，并为 solve@E/oracle 评估候选池
```

private 评估必须位于冻结边界之后，结果写入独立 evaluation trace，不能回流到 prompt、组合采样、public 排序或 tie-break。development 题的 private 结果若被用作 P6 训练 reward，也只能通过明确的训练字段进入；held-out private 结果不得用于调 prompt、阈值或预算。

主 tie-break 预注册为：

```text
public_pass_rate 降序，组合索引（D 索引 + 实现索引 tuple）升序
```

同时记录 public 并列率，并用其他固定规则做敏感性分析。不能用 private pass rate 参与排序。

### 4.5 两种公平预算

不能只报“组合后通过率更高”，因为那可能只是花了更多调用。每个方法同时报告两条曲线：

1. **固定生成预算**：总生成 token 约束在同一档，例如 2k、4k、8k；比较能得到多少有效候选和 `solve@E`。
2. **固定执行预算**：public 执行候选数固定为 `E=8/32/64`；比较模型 token、模型调用次数和 CPU 时间。

`selected pass@1` 单独报告，用于观察层级格式税；高预算使用 `solve@E`，不把相关的模块组合冒充独立同分布样本并套用标准 pass@k 估计式。所有指标按题目聚合，不把同一题的组合当成独立样本做普通置信区间。

## 5. 分阶段部署和可行性分析

### P0：冻结研究协议和 DecompRL 复现边界

**动作**

- 把本文件作为 9.14 主计划；建立新的 split manifest、prompt 版本号、schema 版本号和 tie-break 规则。
- 记录 DecompRL 原文中的模型、数据、`nmax`、`k`、组合预算、训练阶段和限制。
- 复核作者是否发布官方代码、配置或 checkpoint；若没有，保存 arXiv 版本号和检索日期，不自行假定实现细节。
- 在报告模板中强制区分“机制复现”“DecompRL-lite”“严格复现”。

**可行性**：高。只需要 Markdown、JSON manifest 和现有数据，不需要 GPU。

**风险**：把 prompt-only M2a/M2b 写成 DecompRL，或沿用旧候选池造成协议混淆。

**验收**：任何结果都能追溯到题目 split、prompt、seed、模型、预算和 private 使用位置；没有验收通过则不采集新数据。

**预计工作量**：0.5--1 天。

### P1：建立分解生成器和静态验证器

**动作**

1. 新增独立的 decomposition generator，以 prompt version 选择 M2a/M2b，不修改旧 `generator.py` 的单程序协议。
2. M2a 解析 Python skeleton；解析失败只记录，不做自动语义修复。M2b 解析 JSON；失败时保留 raw response，允许一次格式修复调用，但把修复调用计入预算，并分开报告 raw/repaired valid rate。
3. 用 Python `json`、`ast` 和签名解析检查 skeleton/schema、函数名、entrypoint、依赖 DAG 和重复函数。
4. 生成验证报告：paper skeleton valid、JSON schema valid、AST valid、API preservation、DAG valid、平均函数数和失败类型。

**可行性**：高。验证器可以只用 Python 标准库，3B 推理只生成短 JSON；不需要训练。

**主要难点**：模型可能把“函数职责”写成实现细节、输出未定义变量、生成环依赖或忘记 starter signature。不能用正则静默修复语义错误。

**降级路径**：M2b 先允许函数体为 `pass` 的骨架，只验证 schema 和接口；若 JSON 仍不稳定，改用 fenced Python skeleton，但最终必须转成同一内部 schema。M2a 不随 M2b 改 prompt，避免失去论文基线。

**首个 gate**：development 题上 M2b raw schema valid 至少 90%，entrypoint 保留率 100%，DAG valid 至少 90%。低于此值先改 M2b prompt，不进入其组合实验。M2a 的低解析率或低 API 保留率是论文 prompt 迁移到本地任务的待报告结果，不通过调 M2a prompt 掩盖；组合器本身则必须对固定 skeleton fixtures 100% 解析。

**预计工作量**：1--2 天。

### P2：实现确定性组合器和 public-only 执行流程

**动作**

- 为每个函数实现建立 `function_id -> implementation_index -> code` 映射。
- 用 AST 或受控字符串模板组合 helper 和 entrypoint，禁止重复定义、未声明 import 和覆盖 starter API。
- 把选择阶段和最终评测阶段分开：选择函数只接收 public tests；冻结选择与候选池后，独立评测函数才接收 private tests，并分别输出 selected 指标与候选池 `solve@E`/oracle。
- 为每个组合写入 `decomposition_id`、实现 tuple、代码 hash、组合索引、AST 状态、public 结果和耗时。

**可行性**：中高。组合本身简单，但现有 `execute_candidate` 默认同时执行 public/private，需要增加 public-only 路径或在上层严格隔离数据。

**主要难点**：函数之间可能共享隐式状态、实现依赖未生成的 helper、类型注解或 import 冲突；这正是要测量的失败，不应全部当作系统 bug。

**安全限制**：当前执行器没有 OS 级安全沙箱，只运行固定 APPS 数据和受控模型输出；不加入 adversarial code，不把当前执行器写成安全执行环境。

**首个 gate**：固定的人工组合样例 100% 可重复；组合 AST 合法率至少 80%；所有 private 字段在 selection trace 中为零。

**预计工作量**：2--3 天。

### P3：prompt-only 层级机制复现

**首轮设置**

```text
题目：development 20 题
分解数 d：每题 2 个
函数数 n：M2b 为 2--4；M2a 保留模型输出并受总预算约束
每函数实现数 k：2
每分解 public 组合上限：8 或 16
模型：Qwen2.5-Coder 3B
温度：沿用已有配置并固定
seed：42；确认轮使用 42/43/44
```

**动作**

- 运行 M0、M1、M2a、M2b；M3 在 8--10 道题上先做人工分解，用于上限诊断。
- 记录模型调用数、生成 token、public 执行次数、组合数、有效组合数、去重数、CPU 时间和最终 private 结果。
- 旧候选池只用于回归对照，不与新协议结果混合。

**规模估算**：若 M2a/M2b 都是每题 2 个分解、平均每个分解 3 个函数，首轮模块部分约为 `20 * 2 * 2 = 80` 次分解调用和 `20 * 2 * 2 * 3 * 2 = 480` 次函数实现调用，即约 560 次模型调用；尚未包含 M0/M1 和格式修复调用。public 组合执行上限由每题预算控制，不能简单取理论 `k^n` 总和。全流程必须断点恢复，单题失败不能中断全局。

**可行性**：中高。GPU 只负责短分解和函数实现，评测在 CPU；真正的不确定性是 Ollama 单请求时延和组合器失败率，不是显存。

**必须报告的负结果**：无 RL 层级方法在 selected pass@1 低于 M0 是预期可能结果，不得事后删除；若高预算没有收益，应停止 RL 投入。

**预计工作量**：4--7 天，取决于本地 Ollama 单请求时延、格式修复率和 public 测试并发能力。先跑 3 题测得真实 calls/hour，再估算整批 wall-clock，不能把模型调用数直接换算成天数。

### P4：人工盲评和分解质量分析

**动作**

- 从 development 题中抽取 10 道，覆盖简单、边界复杂、需要多步算法和易发生接口耦合的任务。
- 对 M2a、M2b、M3 分解做盲评；评审只看题目与分解，不看 private 结果。
- 每个分解按 0--2 分记录：职责覆盖、输入输出一致、依赖清晰、独立可实现、冗余/过度拆分；另记“是否保留 entrypoint”。
- 至少对 20% 样本隔 48 小时重复评分，报告自我一致率；有第二位评审时报告题目级一致率。

**可行性**：高。人工工作量可控，且不依赖 GPU。

**主要风险**：单人评分主观性，或把“函数多”误当成“分解好”。评分表必须先冻结，不能看 private 结果后修改标准。

**输出**：分解质量表、失败案例集、质量分与组合成功率/最终通过率的题目级关系。

**预计工作量**：1--2 天。

### P5：严格同预算比较和 go/no-go

**动作**

- 先在 30 道 Introductory pipeline hold-out 上冻结并验证 P1--P4 的 prompt 和参数；这里只决定工程协议是否稳定。
- 再在预注册的 30--60 道中等/困难题上比较 M0/M1/M2a/M2b；M3 只作为诊断，不作为自动主方法。中等/困难数据获取、测试格式和执行器审计未通过时，P5 只能标为 blocked，不能用 Introductory 结果替代主结论。现已用 fetch 脚本固定并审计 APPS Interview-30，完成了其中 25 道函数题的正式比较；当前记录仍属于本地 custom split，不等同于官方 APPS test。
- 每个方法报告 `selected pass@1`、`solve@8/32/64`、private selected pass rate、候选池 oracle、有效组合率、模型 token、调用数、CPU 时间和 public tie rate。
- 用题目级 paired bootstrap 或 paired permutation，报告 95% 区间；不要把组合数当作独立题目样本。

**Go 判定**：满足以下至少一条才进入 P6：

1. M2a 或 M2b 在至少一个高执行预算档的题目级差值相对 M1 为正，且 3 seed 方向一致；
2. 自动拆分的高预算收益虽未达到统计确定，但 M3 明显优于 M0，且自动分解与 M3 的质量差距可定位；这说明下一步应优化分解器，而不是马上训练 RL。

**No-Go 判定**：

- M2a/M2b 在所有预算档都不如 M1，且 M3 也不优于 M0；
- schema/组合有效率不足 80%；
- 收益只来自更多生成 token，固定 token 预算下消失；
- private 数据在 selection trace 中出现；
- 同分规则改变后结论方向反转且没有稳定的预注册规则。

No-Go 后保留完整负结果，主线转为“模块独立性和分解失败边界”，不追加 RL 训练。

**P5 已执行结果（2026-09-17）**：固定的 APPS Interview-30 数据经审计后含 25 道函数题和 5 道 stdin/stdout 题；后者在结果产生前按协议排除，M0/M1 也过滤到同一 25 题。Qwen2.5-Coder 7B、seed 42、public-only selection、10 秒单测和 10 秒候选总预算下，M0/M1/M2a/M2b 的 selected private full pass 分别为 9/25、6/25、5/25、5/25；候选池 private oracle 分别为 9/25、8/25、6/25、5/25。M2a/M2b 未显示稳定收益且成本显著更高，故按 No-Go 条件停止 RL。随后补做了入口参数一致性复核，剔除 3 条 M2a 和 2 条 M2b 不合规分解；结果仍为 M2a 5/25、M2b 5/25。完整 paired bootstrap、solve@k、tie rate、调用/token/执行预算和失败边界见 `docs/basic-require/9.18当前研究结果与后续工作.md` 及 `codeprm-reproduction/reports/p5_interview_function25_analysis_20260917.md`。

因此 P6（7B QLoRA gate 和 3B DecompRL-lite）本轮明确跳过，不是因为没有尝试，而是因为预注册的进入条件没有满足。保留 7B 推理基线和 3B 训练 smoke 的已有记录；下一轮若要继续，必须先更换或改进分解策略，并重新预注册题目、预算和成功标准。

**预计工作量**：3--5 天。

### P6：可选 DecompRL-lite

只有 P5 Go 才执行。目标是检验“学习分解策略”是否比最佳 prompt-only M2a/M2b 更能产生有用组合，不追论文数字。

**建议设置**

```text
backbone：先用 Qwen2.5-Coder 3B 跑通；7B 通过 P6a smoke 后可替换
量化：4-bit NF4 + double quantization
策略：共享一个冻结 base，串行切换 decomposition / implementation 两个 LoRA adapter
nmax：3
k：2
每题组合：4--8
训练题：P5 中等/困难数据的 development 20--40 题；Introductory 只做训练 smoke
更新：先冻结 implementation 更新 decomposition，再冻结 decomposition 更新 implementation
每阶段：50--200 optimizer steps 起步
reward：完整组合的 private pass reward；private 只作为环境 reward/标签，不进入 prompt
baseline：group mean 和 leave-one-out 都记录
```

**为什么不是直接照搬论文**：本机没有异步分布式 RL、80 张 H100、15k 题或两个阶段各 30k steps 的吞吐条件。即使 7B 权重能放进显存，也不等于能承担论文规模的 rollout 和更新。在线 PPO 也不是当前代码库已有能力；首版应使用小规模、可恢复的 policy-gradient/REINFORCE 风格训练，并把算法差异写清楚。

**P6a：7B 单策略显存 gate**

1. 获取与许可证允许的 7B coder instruct 权重，不覆盖现有 3B 模型；先核对磁盘和 hash。
   `ollama` 中的 GGUF/Q4 文件只能直接用于推理，不能原样作为 bitsandbytes + PEFT 的 QLoRA 训练底座；训练 gate 需要 Hugging Face safetensors（或明确支持训练的等价格式）。
2. 使用 `batch_size=1`、sequence length 256、gradient checkpointing、`use_cache=false`、NF4、LoRA rank 4/8 做一次 forward/backward。
3. 连续运行 20 optimizer steps，记录 allocated/reserved/peak VRAM、tokens/s 和是否发生 CPU offload。
4. 峰值 `<7.5GB` 且无 OOM/NaN 才逐档测试 512、1024；超过 7.5GB、明显换页或吞吐不可接受就保留 7B 推理、训练退回 3B。

**可行性**：3B QLoRA 为高；7B 单策略 QLoRA 为中低、待 smoke。训练数据量、奖励稀疏性、两策略非平稳和组合器吞吐仍是高风险。无论用 3B 还是 7B，都必须先做单 batch advantage smoke，再做短阶段训练。

**分级降级路径**：

1. 7B smoke 不过：训练退回已验证的 3B；7B 仍可保留为推理基线。
2. 3B 双 adapter 仍 OOM：一次只启用一个 adapter/checkpoint；再不行则改 1.5B。
3. online rollout 太慢：使用 P3 记录的离线轨迹做 decomposition ranking/监督微调，只报告“学习分解器”而不称 DecompRL。
4. reward 太稀疏：先用 public 结果做训练开发信号，private 只做最终评估；报告这与论文 verifiable reward 的差异。
5. 平均函数数坍缩：停止继续训练，分析 `n=1` 比例、entropy 和组合收益。

**P6 Go 条件**：held-out 题上相对最佳 M2a/M2b 的高预算 `solve@E` 或有效组合率有稳定提升，且不存在连续 checkpoint 的 `n=1` 坍缩。训练 reward 上升但 held-out 不升，判为 No-Go。

**预计工作量**：1--2 周；这是整个计划中唯一需要 GPU 和较高工程风险的阶段。

### P7：扩展到 AST、局部修复或自适应粒度

P7 不属于 9.14 第一轮交付。只有 P5 或 P6 说明模块化拆分具有可重复收益，才从以下方向选一个：

- 在函数内部加入 AST/control-flow 结构摘要；
- 只重写失败模块并测量正确代码回归率；
- 让模型在不拆分、函数级拆分、控制流块拆分之间做成本感知选择。

三个方向不能同时开始。每次只改变一个因素，并沿用 P5 的同预算和 private 隔离协议。

## 6. 指标定义

### 6.1 分解质量

| 指标 | 定义 |
| --- | --- |
| schema valid | JSON、字段和类型全部通过 |
| API preservation | starter 规定的 entrypoint 名称、参数和返回约定保留 |
| DAG valid | `depends_on` 无环、引用存在 |
| composition valid | 组合后代码可解析、无重复定义和基本接口冲突 |
| independent solvability | 单函数实现放入接口 stub 后可解析/可执行 |
| semantic score | 盲评的覆盖、接口、独立性、冗余综合分 |
| recombination yield | 有效且去重后的组合数 / 理论组合数 |

### 6.2 结果和成本

- `selected pass@1`：按冻结的 public 选择和 tie-break 取一个候选，再看它是否通过 private，反映格式税和单次部署质量。
- `solve@E`：先固定最多 `E` 个候选的生成/执行预算并冻结候选池，再离线用 private 评估其中是否至少有一个通过；该经验覆盖率承认候选相关性，不使用标准 pass@k 的独立采样假设，也不是部署时可见的选择信号。
- private selected pass rate：只对 public 选择出的候选做最终 private 评估。
- pool oracle：候选池中 private 最优值，只作上界，不参与选择。
- 生成 token、LLM 调用数、public 执行数、CPU wall-clock、峰值显存。
- public tie rate：题内候选在 public 分数相同的比例；必须和 tie-break 一起报告。

### 6.3 归因分析

至少按以下题目层分组：

1. 分解 invalid / 组合 invalid；
2. 有效分解但所有实现失败；
3. 有正确组合但 public 未区分；
4. public 选错、private 选对；
5. 候选池中不存在 private 全过解。

这样可以区分“分解器失败”“实现器失败”“组合没有覆盖正确解”和“public 信号无法选择”，不能把所有失败归因于 RL。

## 8. 必须保留的研究纪律

1. **不把 9.14 的“LLM 调控 LLM”写成泛泛的多智能体系统。** 第一版具体对象是 decomposition policy 和 implementation policy。
2. **不把 prompt-only M2a/M2b 写成 DecompRL。** 需要 RL 才能称 DecompRL-lite，且必须说明缩小规模差异。
3. **private 测试绝不进入 prompt、public 选择或人工评审材料。** 训练时作为标签/环境 reward 的用法单独记录。
4. **所有比较冻结候选池、题目 split、token 预算、执行预算、seed 和 tie-break。**
5. **不使用 `183/200` 作为“函数拆分失败”的证据。** 当前 prompt 已经使它近似定义使然。
6. **不把高预算组合收益等同于 pass@1 提升。** 低预算 format tax 和高预算搜索收益必须分开。
7. **不在 P5 前训练 RL，不在 P5 后同时加入 AST、局部修复和自适应粒度。**
8. **当前结果最多称“APPS custom split 的缩小规模机制复现”。** 获取 official test 后另表报告，不能混合。

5. `data/processed/recombination_records_*.jsonl`：实现 tuple、组合代码 hash、public 结果和 tie-break 信息；
6. `reports/decomposition_quality_*.csv`：人工评分和一致性记录；
7. `reports/decomprl_mechanism_ablation_*.md`：M0、M1、M2a、M2b、M3 的同预算结果、成本和置信区间；
8. 若 P6 通过，再增加训练 checkpoint、advantage 诊断、函数数/entropy 曲线和 held-out 结果。

## 10. 最终汇报口径

第一阶段应这样汇报：

> 我没有把 DecompRL 的大规模 RL 训练直接搬到 8GB 本机，而是先复现它最关键的机制：模型生成带签名、docstring 和依赖的函数分解，另一个模型为每个函数生成多个实现，再用 public 测试评估重组程序。实验在固定 token 和执行预算下与整段生成、文字计划和人工分解比较；private 测试只用于标签和最终评估。若层级方法只在高预算有效，我将把结论限定为组合搜索收益；若连有效分解和同预算收益都不成立，则停止 RL，报告模块独立性和分解失败边界。
