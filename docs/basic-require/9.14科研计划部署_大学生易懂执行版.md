# 9.14 科研计划：大学生也能照着做的执行版

更新时间：2026-09-14  
适用目录：`D:\yaorz\research`

这份文件不是论文综述，而是一份“下一步具体做什么”的施工说明。读者不需要先学会强化学习、Transformer 或复杂统计学；只要会运行 Python、看 JSON、记录实验结果，就可以完成第一轮。

## 一、先用一句话说明我们要研究什么

我们要比较四种写代码的方法：

1. **整段写**：模型直接写完整程序。
2. **先列计划再写**：模型先用文字说明步骤，然后再写完整程序。
3. **拆成函数再写**：一个模型先把题目拆成几个函数，另一个模型分别实现这些函数，最后拼回完整程序。
4. **人工拆分**：人先设计函数，再让模型实现，用来当作“理想拆分”的参考。

核心问题只有一个：

> 在总调用次数、总生成 token 和测试时间差不多时，拆成函数是否更容易找到正确程序？

如果答案是否定的，就不继续训练 RL；如果答案在高预算下是肯定的，再研究“能不能训练一个更会拆题的模型”。

## 二、先把容易混淆的词说清楚

### 1. 什么是 7B

7B 表示模型大约有 70 亿个参数。它不是“必须用 70 亿显存”。

- **7B Q4 推理**：模型被压缩成 4 bit，只负责回答问题。当前 RTX 4060 Laptop 8GB 已经实测可以运行 Qwen2.5-Coder 7B。
- **7B QLoRA 训练**：模型边运行边学习，除了模型权重，还要存激活、梯度和优化器，显存要求高得多。当前没有直接证明它能训练，必须先做小测试。
- **论文原版 DecompRL**：不仅要 7B/32B，还要 15,000 道题、两阶段各 30,000 steps、很多组合评测和大量 GPU。这个规模不适合本机。

所以本计划的说法是：**7B 推理能跑；7B 训练待测试；论文规模不复现。**

### 2. 什么是 public 和 private 测试

- **public 测试**：模型可以看到，用来挑选候选程序。
- **private 测试**：模型不能看到，只在最后检查真实效果。

如果 private 测试提前给模型看，实验就像考试时偷看答案，结果不能作为科研证据。

### 3. 什么是候选

同一道题可以让模型写多个版本。每个版本叫一个候选。public 测试负责从候选中选一个；private 测试负责最后打分。

### 4. 什么是 gate

gate 就是“先做小检查，合格才进入下一步”。例如：JSON 解析率低于 90%，就先修格式，不急着跑大实验。

## 四、开始前只做一次的准备

### 第 0 步：确认电脑状态

在 PowerShell 中运行：

```powershell
cd D:\yaorz\research
ollama list
nvidia-smi
```

应看到：

- `qwen2.5-coder:3b`：训练保底和第一轮机制实验；
- `qwen2.5-coder:7b`：已经下载，可做 7B 推理基线；
- RTX 4060 Laptop，显存总量约 8188 MiB。

如果 7B 没有出现在列表中，不要重复改代码，先运行：

```powershell
ollama pull qwen2.5-coder:7b
```

### 第 1 步：确认 7B 推理不是假象

运行一个短请求：

```powershell
$body = @{
  model='qwen2.5-coder:7b'
  prompt='Return only Python code for solve(data) that returns sum(data).'
  stream=$false
  options=@{num_ctx=4096; num_predict=128; temperature=0}
} | ConvertTo-Json -Depth 5
Invoke-RestMethod http://localhost:11434/api/generate -Method Post `
  -Body $body -ContentType 'application/json'
```

通过标准：有 Python 函数返回；`ollama ps` 显示 `100% GPU`；没有报 CUDA out-of-memory。当前实测约 7B 4-bit、4096 context、约 6952/8188 MiB。

注意：这个测试只证明“会回答”，不证明“会做题”。

## 五、按周执行的主计划

下面按 5 周写。每天可用时间少时，保持顺序不变，只把每天的工作拆成两天。

### 第 1 天：冻结规则，不写新模型

要做：

1. 新建一个实验目录，例如 `codeprm-reproduction/experiments/decomprl_20260914/`。
2. 复制并固定题目清单：development 20 题，hold-out 30 题。不要实验跑到一半再换题。
3. 写一个 `manifest.json`，至少包含题目 id、模型名、prompt 版本、seed、token 上限和日期。
4. 写明 private 测试只在最终评测脚本中出现。

交付：一个 manifest 和一页 `run_log`。

通过标准：换一个人打开 manifest，也能知道本轮究竟测了什么。

常见错误：把已有旧结果直接混进新实验。旧候选只能作回归参考，不能混入新候选池。

### 第 2--3 天：做分解格式检查器

模型输出必须长这样：

```json
{
  "functions": [
    {
      "name": "parse_input",
      "signature": "parse_input(text: str) -> list",
      "docstring": "Read the input and return structured data.",
      "depends_on": []
    },
    {
      "name": "solve",
      "signature": "solve(text: str) -> str",
      "docstring": "Call helpers and produce the required output.",
      "depends_on": ["parse_input"]
    }
  ]
}
```

检查器要检查：

- JSON 能否解析；
- 是否有 `functions`；
- 每个函数是否有 name/signature/docstring/depends_on；
- 函数名是否重复；
- `solve` 是否存在且在最后；
- 依赖是否成环；
- 是否保留题目的 starter API。

先用 5 道 development 题测试。通过标准：

- raw JSON 合格率至少 90%；
- `solve` 保留率 100%；
- 依赖图合格率至少 90%。

不通过时，只修 prompt 和检查器，不能偷偷把错误 JSON 自动改成正确 JSON。

### 第 4--5 天：做函数拼接器

拼接器接收：

```text
题目 starter API
+ 一份分解
+ 每个函数的若干实现
```

输出一个完整 Python 程序。

必须固定这些规则：

1. 每个函数最多出现一次；
2. `solve` 入口不被覆盖；
3. 不允许模型偷偷添加没有记录的 helper；
4. 每个组合保存代码 hash；
5. 拼接阶段不能读取 private 测试。

先不用模型，手写 3 个固定 fixture 测试拼接器。通过标准：3 个 fixture 100% 得到相同代码，AST 解析全部通过。

### 第 2 周：先跑最小规模机制实验

只用 20 道 development 题、3B 模型、seed 42。

每题的首轮设置：

| 项目 | 数值 |
|---|---:|
| 分解数量 | 2 |
| 每份分解的函数数 | 2--4 |
| 每个函数的实现数 | 2 |
| 每份分解最多组合数 | 8 或 16 |
| temperature | 沿用已有配置并固定 |
| private 测试 | 不进入选择过程 |

必须跑四个方法：

- M0：直接生成完整程序；
- M1：先生成文字计划，再生成完整程序；
- M2a：输出 Python skeleton 分解；
- M2b：输出 JSON 分解。

每道题都记录：调用次数、生成 token、有效分解数、有效实现数、组合数、public 通过情况、CPU 时间和最终 private 结果。

通过标准不是“准确率一定提升”，而是：流程能断点恢复、单题失败不影响其他题、所有记录完整。

### 第 2 周末：人工看 10 道题

从 20 道 development 题中抽 10 道，不看 private 结果，只看题目和分解。

每项打 0--2 分：

1. 是否覆盖了题目要求；
2. 输入输出是否一致；
3. 依赖是否清楚；
4. 每个函数能否独立实现；
5. 是否过度拆分或重复拆分。

不要因为函数数量多就给高分。一个只有 2 个函数但边界清楚的分解，可能比 6 个互相依赖的函数好。

### 第 3 周：准备主结论数据

第一轮 20 题只是工程试跑。要形成科研主结论，还需要 30--60 道中等/困难题。

准备顺序：

1. 下载或固定题目；
2. 检查每道题的 starter code、public tests、private tests 格式；
3. 随机抽题手工核对输入输出；
4. 确认执行器超时和错误分类；
5. 生成新的 hash manifest；
6. 再跑 M0/M1/M2a/M2b。

如果中等/困难数据或执行协议没有审计完成，不能用 introductory 20 题冒充主结论，只能写“机制 smoke”。

### 第 3 周末：做 Go/No-Go 判断

继续做 RL 的条件：

- M2a 或 M2b 至少在一个高执行预算档优于 M1；
- 这个方向在 seed 42/43/44 中一致；
- 提升不是单纯因为多用了 token；
- 有效组合率至少 80%；
- private 没有泄漏到 prompt 或 public 选择。

停止 RL 的条件：

- 所有预算下层级方法都不如 M1；
- M3 人工拆分也不如 M0；
- 组合器或 schema 有效率低于 80%；
- 改 tie-break 后结论反向；
- 所谓提升只来自更多调用或更多 token。

No-Go 不是失败。它说明“在当前任务和预算下，拆分没有带来可重复收益”，应整理失败案例，不再盲目增加训练。

### 已执行的 P5 结果（2026-09-17）

这一步已经实际完成。我们从 APPS train 的 Interview 难度固定了 30 道题：25 道是函数题，5 道是标准输入输出题。因为 M2 的拼接器需要可调用函数入口，所以先按题目格式排除这 5 道，再让 M0/M1 也只在同一批 25 道上比较；这个排除在看结果前完成，不是挑成绩。

所有方法都使用本机 Ollama 的 Qwen2.5-Coder 7B、seed 42、只看 public 选候选、每个测试最多 10 秒、每个候选在一个 split 最多 10 秒。最终数字如下：

| 方法 | 有候选 | public 全通过 | 选中候选的 private 全通过 | 候选池中至少有一个 private 全通过 |
| --- | ---: | ---: | ---: | ---: |
| M0 直接生成 | 25/25 | 11/25 | 9/25 | 9/25 |
| M1 先写计划 | 23/25 | 8/25 | 6/25 | 8/25 |
| M2a skeleton 分解 | 20/25 | 3/25 | 5/25 | 6/25 |
| M2b JSON 分解 | 18/25 | 7/25 | 5/25 | 5/25 |

结论很直白：在这批更难题上，自动分解没有超过 M0 或 M1，而且 M2a/M2b 要多很多模型调用和 token。即使把所有候选都事后放到 private 上检查，模块化候选池也没有覆盖到更多正确程序。因此按原计划停止 RL，不继续“为了证明能提升”而训练。入口参数复核后没有改变这一结论。完整结果与后续计划见 `docs/basic-require/9.18当前研究结果与后续工作.md`，原始记录和统计见 `codeprm-reproduction/reports/p5_interview_function25_analysis_20260917.md`。

## 六、通过 Go 后，才做 DecompRL-lite

### 先做 7B QLoRA 小测试

不要把 Ollama 的 GGUF 文件直接拿去训练。QLoRA 需要 Hugging Face safetensors 权重，并且要安装 bitsandbytes/PEFT 环境。

单策略 smoke 设置：

```text
batch size = 1
sequence length = 256
gradient checkpointing = on
use_cache = false
4-bit NF4
LoRA rank = 4 或 8
连续 20 steps
```

每一步记录：peak allocated、peak reserved、tokens/s、是否 OOM、是否出现 NaN。

通过标准：峰值小于 7.5GB、20 steps 无 OOM/NaN、没有明显 CPU offload。然后才试 sequence length 512，再试 1024。

不通过时：

1. 7B 继续做推理基线；
2. 训练退回已验证的 3B；
3. 不要为了“证明能跑”偷偷关闭重要记录或扩大 swap。

### DecompRL-lite 的最小设置

只做短实验，不宣称复现论文数字：

- 一个冻结 base；
- 两个 LoRA adapter，分别对应 decomposition 和 implementation；
- 两个 adapter 串行使用，不同时加载两份完整模型；
- `nmax=3`、每函数 `k=2`、每题 4--8 个组合；
- 每个阶段先做 50--200 optimizer steps；
- 先更新 decomposition，再更新 implementation；
- reward 使用完整组合是否通过测试；
- 训练题与 held-out 题分开。

训练中如果函数数长期变成 1，说明发生了拆分坍缩，应停止训练并分析原因；不能只看 reward 上升就宣布成功。

## 七、每天都要记录的最小日志

每次运行后追加一行：

```text
日期 | git/文件版本 | 方法 | 模型 | 题目数 | seed | token上限 | 调用数 | 组合数 | public结果 | private结果 | GPU峰值 | CPU时间 | 错误
```

遇到错误时记录四件事：

1. 哪道题；
2. 哪个 prompt 或函数；
3. 原始模型输出；
4. 是格式错误、拼接错误、执行超时还是答案错误。

不要只记录“这题失败了”。科研需要知道失败发生在哪一层。

## 八、最容易犯的十个错误

1. 把 7B 能推理写成 7B 能训练。
2. 把 prompt-only 层级方法叫作 DecompRL。
3. 用 private 测试挑候选。
4. 只报告最好的一次 seed。
5. 组合数量增加后，却不报告 CPU 时间。
6. 只看 `pass@1`，不看高预算 `solve@E`。
7. 把相关的组合候选当成独立样本算普通 pass@k。
8. 旧候选池和新候选池混在一起。
9. JSON 解析失败后静默修复，不记录修复调用。
10. RL reward 上升就宣布泛化成功。

## 九、最短可执行版本

如果现在只能做一件事，按下面顺序：

1. 用 7B 做一次推理 smoke，保存显存和速度；
2. 固定 development20/holdout30 split；
3. 写 M2b JSON 分解 prompt 和验证器；
4. 用 3B 跑 5 道题，确认 schema 合格率；
5. 写固定 fixture 的组合器；
6. 用 20 道题跑 M0/M1/M2a/M2b；
7. 看同预算下是否有正信号；
8. 有正信号才做 7B QLoRA smoke 或 3B DecompRL-lite。

## 十、最终应该怎样汇报

可以直接使用下面这段话：

> 本研究先在本地资源范围内复现 DecompRL 的核心机制，而不是声称复现论文的大规模训练。我们比较整段生成、文字计划、自动函数分解和人工函数分解，并固定题目、模型、seed、token 预算、组合预算及 public/private 隔离规则。当前本机已实测 Qwen2.5-Coder 7B 4-bit 推理可行，但 7B QLoRA 训练仍需显存 gate；3B 作为训练保底。只有当 prompt-only 层级方法在留出题目和同等预算下显示稳定正信号，才进入小规模 DecompRL-lite；否则保留负结果，研究分解失败边界。
