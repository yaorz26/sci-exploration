你真正的主线应是：
怎样把自然语言任务拆成真正有意义、且能对应到代码 AST 结构的 subtask，并让 AI 按这些 subtask 生成、组合、局部修改代码？

这和 CodePRM、FunPRM 的核心缺口直接相关。
CodePRM：把自然语言 thought 当步骤
问题：thought 往往不能精确对应到哪几行代码。

FunPRM：把函数当步骤
问题：一个函数可能包含多个子任务；一个子任务也可能跨多个函数。

你的方向：把语义 subtask 与 AST 子树对齐
目标：每个 subtask 都知道“自己负责代码树的哪一块”。
AST 不是魔法。它只能告诉你代码长什么样，例如有几个 if、for、函数调用、返回值；它不能自动告诉你算法是否正确。但 AST 可以让“子任务”有明确的代码位置、输入、输出和依赖关系。
最值得研究的主问题
相比只让 AI 先写文字计划、再一次性写完整代码，如果先生成“subtask—AST 骨架”，再逐块填充代码，能否在相同计算预算下提高最终代码的正确率和可修正性？

把它写成日常语言：
普通方法：
题目 → 想一想 → 一次性写完整代码

你的方法：
题目 → 拆出子任务 → 为每个子任务规定 AST 位置
     → 先生成代码骨架 → 按子任务填充骨架 → 组合为完整代码
举例，题目是“计算数组中所有正数的平方和”。
普通文字计划可能是：
1. 遍历数组。
2. 找到正数。
3. 求平方并相加。
4. 返回结果。
但这份计划没有规定代码如何组织。
AST 对齐后的计划则类似：
S1：初始化累加器
AST 位置：Assign 节点
输入：无
输出：total

S2：遍历数组
AST 位置：For 节点
输入：nums
输出：当前元素 x

S3：只处理正数并累加平方
AST 位置：For 内的 If + AugAssign 节点
输入：x、total
输出：更新后的 total

S4：返回结果
AST 位置：Return 节点
输入：total
输出：最终答案
再生成骨架：
def square_sum(nums):
    total = 0             # S1
    for x in nums:        # S2
        if x > 0:         # S3
            total += x*x
    return total          # S4
这里“拆分”不只是写四句文字，而是让每个子任务绑定到一个明确的代码结构。
它为什么可能真的增强代码生成能力？
它有四种可能帮助。
1. 降低一次性生成整段代码的负担
   模型不必同时记住所有变量、循环、边界和返回逻辑，可以逐块完成。
2. 明确子任务接口
   每块都写清输入和输出。例如 S1 产生 total，S3 才能使用 total。这可减少变量未定义、函数参数不匹配、返回值遗漏等错误。
3. 保留已经正确的部分
   如果 S3 有问题，可以只重写对应的 If 或循环体，而不是让模型重写整段程序并把原本正确的 S1、S2、S4 改坏。
4. 使“过程监督”有真正对象
   CodePRM 的 thought 太抽象，FunPRM 的函数又太粗。AST 子树提供介于“整段函数”和“单行代码”之间的代码单元。
但这只是一种假设，不是结论。
你应该怀疑它为什么可能无效
你的怀疑非常必要。AST 方法至少有五个明显风险：
风险	具体含义
AST 是语法，不是语义	有 for、if、return 不代表算法正确
拆错任务会连锁出错	如果一开始把“求和”误拆成“计数”，骨架会把错误固定下来
子任务往往不是一棵干净的树	一个循环可能同时负责过滤、统计、更新状态，很难硬分给一个子任务
多步生成更贵	先规划、生成骨架、逐块填充，可能只是因为调用次数更多才变好
强模型可能无需拆分	对简单函数题，直接写完整代码可能反而更好、更快


所以实验不能只比较“AST 方法是否更高分”，必须比较：
在相同 token、相同调用次数、相同候选数下，AST 对齐拆分是否比“普通文字计划”更好？

否则即使 AST 方法效果更好，也可能只是因为它多调用了几次模型。
可选的三个真正相关方向
方向	核心问题	与你的主线关系
AST 对齐子任务生成	子任务能否映射到 AST 子树，并逐块生成？	最直接，推荐
AST 局部修正	出错后，只改对应 AST 子树，能否少破坏正确代码？	拆分后的自然第二阶段
自适应粒度	单函数时按控制流块拆，多函数时按函数拆，仓库级按调用图拆，是否更合理？	长期主张


方向一：AST 对齐子任务生成
这是我最推荐的起点。
它的真正研究问题是：
子任务应当由“函数边界”决定，还是应当由 AST 中的初始化、分支、循环、调用、返回等结构决定？

对比方法可以是：
A：题目 → 直接生成完整代码
B：题目 → 文字 subtask 计划 → 生成完整代码
C：题目 → AST 对齐 subtask 计划 → AST 骨架 → 分块填充
若 C 在相同预算下比 B 的隐藏测试通过率更高，才能说明 AST 对齐本身有用；若 B 和 C 一样，则文字规划已经足够；若 C 更差，则说明 AST 骨架限制了模型。
这比直接重训 PRM 更贴近你的主题，也更容易解释。
方向二：AST 局部修正
这一步是在“先生成”之后。
完整代码失败
    ↓
定位到 AST 中某个子树
    ↓
只重写该子树
    ↓
保留其他 AST 子树
例如：
for x in nums:
    if x >= 0:      # 出错子树
        total += x
只重写 if 块，而不让模型再碰函数定义、循环、初始化和返回。
这与 CodePRM 的“定位后修正”有关，也与 LDB 的“利用执行轨迹定位代码块”有关。但你的不同点是：定位和修改的单位明确是 AST 子树，而不是模糊的 thought 或整段代码。
风险是：对 wrong answer，测试往往只能告诉你“输出错了”，不能自动告诉你错在树的哪一块。因此第一阶段应优先研究生成和结构对齐；局部修正作为后续扩展。
方向三：自适应粒度
这是更长期、也更有研究味道的版本：
简单单函数任务 → 用 AST 控制流块作为 subtask
多函数任务     → 用函数作为 subtask
类级任务       → 用方法和调用关系作为 subtask
仓库级任务     → 用模块/调用图社区作为 subtask
它对应一个很自然的假设：
代码生成的有效 subtask 粒度，不应固定为函数或 thought，而应随代码结构复杂度变化。

FunPRM 固定将函数视为步骤；SecCodePRM 已使用 AST 调用图传播跨函数风险。你的潜在切入点是把“AST 局部结构”和“调用图全局结构”统一为自适应 subtask 图。
但这不能直接作为明天就做的大实验，因为你首先要定义：
- 一个 subtask 的输入、输出、边界是什么；
- AST 的哪些节点可单独成为 subtask；
- 两个子任务是否允许共享或跨越同一 AST 子树；
- 子任务之间是线性顺序还是依赖图。
最简单、最有意义的探索
先不要训练 PRM，也不要做代码修正。只验证最基础的问题：
AI 能否稳定地把一个代码任务拆成“有明确输入输出、且能对应 AST 子树”的 subtask？

可用 20—30 道中等复杂度 Python 题做探索，步骤如下：
1. 让模型输出 3—5 个 subtask，每项必须写输入、输出和职责；
2. 让模型输出可解析的 Python AST 骨架，每个骨架位置标注 S1、S2 等；
3. 用 Python ast.parse 检查骨架是否语法合法；
4. 人工检查每个 subtask 是否真的能对应某一棵 AST 子树；
5. 记录四个量：
要记录什么	它说明什么
骨架能否被 AST 解析	方法在语法上是否可运行
每个 subtask 是否有明确 AST 位置	拆分是否真正落到了代码  结构
subtask 是否覆盖主要算法步骤	是否只是把无意义的文字贴标签
子任务输入输出是否一致	拼接代码时是否容易出现接口错误


这一步还不证明代码能力提升，但会回答“这个方法是否值得做”。
若这一步可行，才进入正式对照实验：直接生成、文字计划生成、AST 对齐生成，在相同预算下比较隐藏测试通过率。
明天最准确的表达是：
我希望将代码生成中的 subtask 从抽象的自然语言 thought 或固定函数，变成可操作的“语义目标—AST 子树”对。第一步不急于训练过程评分器，而是验证这种对齐是否稳定；若对齐稳定，再检验 AST 对齐的分块生成是否能在相同计算预算下提升未见测试正确率。


你提出的“相比只让 AI 先写文字计划、再一次性写完整代码，如果先生成“subtask—AST 骨架”，再逐块填充代码，能否在相同计算预算下提高最终代码的正确率和可修正性？  ”这个想法，和后面的三个方向。目前的研究进度如何，查阅已有论文、搜索相关论文。


结论先说：这个想法有研究价值，但原来的表述已经过于宽泛，不能直接当成“全新方向”。
截至 2026 年 9 月，已有工作分别做过：
- 先生成 AST/语法轮廓，再补充代码细节；
- 把问题拆成函数或子模块，分别生成后组合；
- 把错误代码拆成多个层次，逐块定位和修复；
- 根据问题或执行结果动态决定是否拆分。
真正尚未被充分回答的问题是：
“显式建立语义子任务与函数内部 AST 区域之间的对应关系”，是否比单纯文字计划、单纯 AST 骨架、单纯函数拆分更有效？

这才是我们应当保留的核心。
一、核心问题的研究进度
你原来的问题是：
相比文字计划后一次性生成代码，先生成 subtask—AST 骨架，再逐块填充，能否在相同计算预算下提高正确率和可修正性？

这个问题可以拆成三部分。
1. “先生成骨架，再补细节”已经有人做过
最接近的是 ICML 2023 的 ChainCoder：Outline, Then Details。
它不是先生成普通代码，而是通过 AST 把代码分成四层：
1. 粗略程序轮廓；
2. 核心算法结构；
3. AST 布局框架；
4. 变量名、常量等细节。
然后从粗到细逐层生成。
所以，如果我们只说：
先生成 AST 骨架，再填代码。

这基本已经与 ChainCoder 撞题。
但 ChainCoder仍有明显空缺：
- 它的骨架是从正确代码的 AST 自动提取出来的训练目标；
- 骨架主要表达“循环、条件、赋值”等语法结构；
- 它没有明确说明每块代码负责哪个语义子任务；
- 没有记录每个子任务的输入、输出和依赖；
- 它使用专门训练的模型和 I/O 样例，不是当前通用代码 LLM 的推理流程；
- 它没有与“文字计划”“函数拆分”进行严格的同预算比较。
因此，“AST 骨架生成”不新，但“语义子任务与 AST 区域显式对齐”仍可能构成创新。
2. “拆成子任务再分别生成”已经非常活跃
这一部分已经比较拥挤。
Parsel 先把任务拆成自然语言函数描述，再分别搜索函数实现并组合。
FunCoder，NeurIPS 2024 在写父函数时动态提出子函数，只生成子函数签名和说明，之后递归实现，再从叶子向上组合。它已经非常接近“子任务拆分—逐块生成”。
CodeChain，ICLR 2024 让模型生成模块化代码，提取和聚类其中的子模块，再利用代表性模块反复修订完整代码。
最新的 DecompRL 更进一步：训练模型自动把题目拆成若干带签名和 docstring 的函数，分别生成每个函数的多个实现，再廉价地交叉组合。
因此，如果我们的 subtask 最终只是“一个子任务对应一个函数”，那么它很难超过 FunCoder、Parsel 和 DecompRL 的工作范围。
3. “相同计算预算下是否有效”仍未被完全回答
这一点反而是原问题中最有价值的部分。
现有论文中的性能提高经常来自更多模型调用：
- FunCoder 每个函数会采样多个实现，实验中通常使用 11 个候选；
- FunPRM 是 Best-of-8 选择，不是单次生成；
- DecompRL 的主要优势来自大量函数组合和 CPU 测试；
- ChainCoder使用专门训练的模型，不能直接说明通用 LLM 多调用是否划算。
DecompRL甚至明确指出：它不预期分解方法在单次 pass@1 上天然优于完整代码生成。其优势主要在高推理预算下出现；在较低 token 预算下，有时还不如普通生成。
这说明你的怀疑是合理的：
分块生成不一定更好。它可能只是花了更多 token、更多调用和更多测试，最后才得到更高准确率。

所以“严格同预算比较”确实还是值得研究的。
二、方向一：subtask 与 AST 对齐后生成
当前进度：已有非常接近的组成部分，但完整交叉点尚不成熟。
最接近的论文包括：
- ChainCoder：AST 粗到细生成；
- ANPL：程序草图、自然语言 hole、递归实现和局部修改；
- Statically Contextualizing LLMs with Typed Holes：利用 typed holes 和语言服务器为局部生成提供类型与绑定上下文；
- TreeDiff：在扩散式代码模型中按 AST 节点控制掩码和恢复；
- SynCode：在解码时用语法规则过滤非法 token。
其中 ANPL 也很接近我们的设想：代码草图负责控制流和数据流，尚未实现的模块被表示成自然语言 hole，用户可以局部修改。但它主要是人机交互式编程，不是让模型自主完成 subtask—AST 对齐。
仍可能存在的研究空缺
我们不应假设“一个 subtask 对应一个 AST 子树”，而应建立显式表示，例如：
{
  "subtask": "过滤所有负数",
  "inputs": ["numbers"],
  "outputs": ["positive_numbers"],
  "depends_on": [],
  "ast_region": {
    "type": "ListComp",
    "hole": "H2"
  }
}
模型先产生：
1. 语义子任务；
2. 子任务的输入、输出、依赖；
3. AST 中的待填充区域；
4. 按依赖顺序填充每个 hole；
5. 最后组合与检查。
与 ChainCoder 的主要区别是：
- ChainCoder：从语法角度把代码分层；
- 我们：先说明每块代码要完成什么，再把这个语义目标绑定到语法区域。
有效性并不确定
TreeDiff 的实验给出了一个重要警告：直接按完整 AST 子树进行粗粒度处理，在 MBPP 上有时比随机 token 处理更差；更细的节点级 AST 引导反而更稳定。
也就是说：
AST 结构不是越强、越完整越好。整个子树一次性填充可能丢失局部上下文。

因此这个方向的价值不在于“用了 AST”，而在于找到适当的语义—语法粒度。
我的判断：这是三个方向中最适合作为主线的，但必须围绕“显式语义对齐的独立贡献”重新定义。
三、方向二：AST 局部修复
当前进度：研究已经比较成熟，竞争较强，更适合作为主线的第二阶段。
经典 AST 修复已经包括：
- TBar：基于 AST 修复模板；
- Recoder：通过语法引导的编辑解码器生成补丁。
LLM 时代的接近工作包括：
- LDB：把代码拆成基本块，观察每块执行后的变量值，再定位问题；
- MGDebugger：把错误代码重构成多层子函数树，逐层生成测试并自底向上修复；
- SCOPE：把程序要求拆成语义 subgoal，分析当前代码缺少哪些要求，再指导局部修改。
尤其是已被 ICSE 2026 接收的 MGDebugger，已经做了“多粒度分解—逐块测试—局部修复”，与我们原本的第二方向非常接近。
它与潜在 AST 方案的区别是：
- MGDebugger让 LLM 把连续语句重构成辅助函数；
- 我们可以不改变程序的函数结构，直接定位和替换原 AST 子树；
- MGDebugger主要根据子函数测试修复；
- 我们可以利用“该 AST 区域对应哪个语义子任务”来限制修复范围。
因此局部修复仍可做，但不能只宣称“分块修复”。比较有意义的研究问题应当是：
相比重新生成整个函数、按基本块修复、按辅助函数修复，基于 subtask—AST 对齐的局部替换能否减少对原本正确代码的破坏？

SCOPE 的最新结果也说明该方向可能有效，但收益还不稳定：它在 LiveCodeBench V6 上比 Reflexion 多解决了 5/175 道题，而且 SFT 版本甚至低于未经训练的结构化 critic。因此还不能认为“语义 subgoal 一定能稳定指导修复”。
我的判断：可以作为主方向的应用或第二贡献，不适合单独作为第一创新点。
四、方向三：自适应拆分粒度
当前进度：已有动态拆分，但“在多个代码粒度之间进行成本感知选择”仍不成熟。
相关工作包括：
- FunCoder：递归拆函数，模型认为足够简单时停止；
- DecompRL：模型学习生成不同数量的函数；
- AdaCoder：先直接生成，失败后才启动规划与调试；
- CodePlan：根据代码依赖和修改影响动态生成仓库级编辑计划；
- CodeS：按照仓库—文件—函数的多层草图生成完整项目；
- MGDebugger：在多个子函数层次上自底向上修复。
但这些方法通常只在一种预先确定的结构内变化：
- FunCoder和DecompRL主要改变函数数量；
- AdaCoder主要决定是否启用规划；
- CodeS使用固定的仓库—文件—函数层级；
- MGDebugger沿已经生成的层次树进行修复。
尚未充分研究的是：
模型能否根据任务和代码结构，在“不拆分、按函数拆分、按 AST 控制块拆分、按语句块拆分”之间选择，并同时考虑正确率与 token 成本？

这是一个更有创新性的方向，但难度也最高。因为必须先证明每一种固定粒度本身有意义，之后才有资格研究如何选择粒度。
因此正确顺序是：
1. 先验证固定的 subtask—AST 对齐；
2. 再比较函数级、AST 块级和整体生成；
3. 最后训练或设计自适应选择器。
FunPRM 的本地原文也支持这种谨慎态度：其 Chain-of-Function 消融只带来较小的整体提升，而且部分难题仍只生成一个函数，说明“题越难就一定要拆得越多”并不成立。2601.22249v1.pdf
五、建议重新确定的研究问题
不建议继续使用原来的宽泛表述。更有防御性的版本是：
在严格相同的模型调用和 token 预算下，显式预测“语义子任务—AST 区域”对齐关系，并按照依赖顺序填充 AST holes，是否能够比文字规划、纯 AST 粗到细生成和函数级分解，提高复杂单函数代码生成的 pass@1，并减少局部修复造成的正确代码回归？

这个问题明确比较了四类方法：
1. 直接生成；
2. 文字计划后生成；
3. ChainCoder 式 AST 骨架；
4. FunCoder 式函数拆分；
5. 我们的语义 subtask—AST 对齐。
只有第五种显著优于第三、第四种，才能说明贡献来自“语义与 AST 的对齐”，而不是来自多写了一次计划或多调用了几次模型。
六、三个方向的最终定位
方向	当前拥挤程度	剩余创新空间	建议定位
subtask—AST 对齐生成	中高	中等	主线
AST 局部修复	高	较小到中等	第二阶段/应用
自适应拆分粒度	中等	较大，但实现困难	长期扩展


推荐的科研路线是：
固定的语义—AST 对齐生成 → 对齐区域的局部修复 → 成本感知的自适应粒度。

推荐阅读顺序
1. ChainCoder：AST 粗到细生成，最接近原始设想
2. FunCoder：动态函数拆分与组合
3. ANPL：代码草图、holes 与局部修正
4. MGDebugger：多粒度分解与局部修复
5. DecompRL：学习函数分解与高预算组合
6. TreeDiff：AST 粒度对生成效果的影响
7. Parsel：层次化函数描述与组合
8. SCOPE：语义 subgoal 指导代码修复
9. CodeChain：模块化生成与子模块复用
10. Self-planning Code Generation
11. Structured Chain-of-Thought
本次检索没有发现一篇同时完整实现“语义 subtask—函数内部 AST 显式对齐—按 hole 生成—同预算比较”的论文，但这不能证明绝对不存在。可以确定的是：原想法必须收窄到这个交叉点，才有较可信的创新空间。

这几个感觉都好没用啊

你的感觉是对的。重新站在“提高AI生成代码的正确率”这个目标上看，这三个方案目前确实有点为了结合 subtask 和 AST 而结合，缺少一个真正需要解决的关键问题。
为什么感觉没用
一个方法要真正提高代码生成能力，至少应当提供以下一种东西：
- AI原本不知道的新信息；
- 能判断代码对错的可靠反馈；
- 能明显缩小正确答案的搜索范围；
- 能阻止某类具体错误发生。
而前面三个方案没有很好地做到这些。
方案一：先生成AST骨架
它主要改变了代码的书写顺序：
原来：直接写完整代码
现在：先写骨架，再填细节
但它没有告诉AI：
- 算法到底该怎么设计；
- 边界条件是什么；
- 某个判断是否正确；
- 代码能不能通过隐藏测试。
如果AI不知道正确算法，生成再漂亮的AST骨架也没用。
更严重的是，现在的大模型本来就很少出现低级语法错误。它们真正容易错的是算法、边界条件和题意理解。AST主要表达语法结构，因此不一定解决主要错误。
所以方案一可能只是：
把一次生成拆成五次生成，成本更高，但没有增加可靠信息。

方案二：AST局部修复
局部修复在工程上有用，因为它能减少误改。
但它有一个前提：
系统已经知道哪一块代码错了。

真正困难的恰恰是找到错误位置。AST只能告诉我们这里是循环、判断或函数调用，不能告诉我们这个判断的算法是否正确。
例如：
if x >= 0:
语法完全合法，AST也完全正常。但如果题目要求“严格大于0”，它仍然是错的。
所以局部修复的大部分能力其实来自：
- 测试失败信息；
- 错误定位；
- 执行轨迹；
- 对题意的理解。
AST只是帮助系统修改某个区域，并不是修复成功的核心原因。
方案三：自适应粒度
这个方案的问题更直接：我们还没有证明“按AST拆”或“按函数拆”真的有效，就开始研究如何选择它们。
相当于：
我们还不知道三种药能不能治病，就开始训练一个模型决定病人该吃哪一种药。

逻辑顺序反了。
因此，方案三现在不应做。
真正值得研究的问题
Subtask拆分真正容易出问题的地方，可能不是“怎么拆”，而是：
拆完以后，各个子任务能不能正确地连接起来？

例如AI把任务拆成：
S1：读取数据
S2：过滤数据
S3：统计数据
S4：排序结果
每个子任务单独看可能都合理，但组合时可能出现：
- S1输出list，S2却按dict使用；
- S2修改了原始数据，S3仍以为原数据没变；
- S3返回两个值，S4只接收一个；
- S2过滤的是x >= 0，实际要求是x > 0；
- S3需要排序前的数据，S2却改变了顺序；
- 子任务分别正确，执行顺序却错了。
这叫“子任务接口与组合错误”。
这个问题与subtask直接相关，而且AST、数据流和调用关系确实能够提供部分可靠信息。
更有用的候选方向
可以改成：
基于子任务接口约束和程序结构分析的代码生成：检查并减少多个子任务组合时产生的接口、数据流和依赖错误。

方法大致是：
题目
 ↓
AI拆分子任务
 ↓
为每个子任务说明输入、输出、数据类型、是否修改变量
 ↓
AI生成代码
 ↓
AST和数据流工具检查各子任务是否正确连接
 ↓
发现接口冲突后定向修改
例如：
S1
输入：nums: list[int]
输出：positive_nums: list[int]

S2
输入：positive_nums: list[int]
输出：squares: list[int]
但实际代码却是：
def get_positive(nums):
    return set(x for x in nums if x > 0)

def get_squares(positive_nums):
    return [positive_nums[i] ** 2 for i in range(len(positive_nums))]
这里S1实际返回set，S2却把它当成可以下标访问的list。
这种错误可以被结构和类型分析发现。它不是让AST“帮助AI思考”，而是让AST和分析工具阻止具体错误。
不过，现在也不能直接认定这个方向一定有效。首先需要证明：
子任务生成失败时，接口和组合错误是否真的占了较大比例。

当前最应该做的实验
不要马上实现新方法，先做一个小型诊断实验。
选择30—50道中等或困难代码生成题，在相同token预算下比较：
- 直接生成；
- 先写文字计划再生成；
- 拆成子任务或函数后生成。
然后把失败原因分成：
1. 算法根本错误；
2. 遗漏题目要求；
3. 子任务拆分错误；
4. 子任务输入输出不一致；
5. 数据依赖或执行顺序错误；
6. 边界条件错误；
7. 语法或API错误。
实验结果将直接决定方向：
- 如果大部分是算法错误，subtask和AST帮助不大，应换方向；
- 如果大量是接口、依赖和组合错误，可以研究结构约束；
- 如果大部分代码只有一小块错，可以研究局部修复；
- 如果分解方法整体不如直接生成，就应该放弃这条路线。
建议向导师这样表达
经过文献检查，我发现简单的函数拆分、AST骨架生成和分块修复已经有较多研究，而且它们是否真正提高功能正确率仍不明确。因此我暂时不直接提出新的复杂框架，而准备先做等预算对照和失败归因，确认subtask生成的主要瓶颈。如果错误主要集中在子任务接口、数据依赖和组合过程，再研究利用AST和数据流分析约束子任务组合；如果不是，就及时放弃该方向。

这比强行提出一个“subtask+AST新框架”更可靠，也更像真正的科研判断。
