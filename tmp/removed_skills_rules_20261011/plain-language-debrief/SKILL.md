# 通俗表达要求（只规范用词，不规定格式）

本技能约束的是**语言**：把话说白、说全。
它**不规定输出格式**——分不分段、有没有小标题、按什么顺序组织、要不要列选项，一律由 AI 按内容自行决定。

> **作用域与同步说明（本项目专用）**
> - 本副本位于项目级 `.codebuddy/skills/`（D 盘），**在本项目内优先于用户级同名技能**；
> - 同名用户级副本在 `~/.workbuddy/skills/plain-language-debrief/`（跨项目生效），两份内容需保持同步；
> - 本项目"默认生效"的**保证通道**是 `.codebuddy/rules/00-通俗完整汇报协议.md`：
>   它带 `alwaysApply: true`，会在会话首轮直接注入系统提示的 `<project_rules>`，
>   不依赖模型是否决定加载本技能。
> - **2026-09-28 变更**：本技能与配套规则中原有的**输出结构与段落类要求已全部删除**。
>   用户明确要求：本技能只让描述性语言通俗化，不规定输出格式。

## 一句话原则

把结论说白（不懂术语也能听懂）、把原因说透（为什么、怎么来的）、把口径说全（数字与条件不因通俗而省略）。
通俗只换说法，**不改变结论强度和证据分量**。

## 什么时候要用通俗表达

以下任一情况，按本技能表达：

1. 一个阶段任务做完：实验跑完、脚本写完、数据整理完、报告/文档写完、调研查完；
2. 得出任何结论——**包括"证据不足、无法判断""没有结论"这种结论**；
3. 发现问题：报错、异常、结果与预期不符、数据缺失、路径失效、前后不一致；
4. **发现自己之前说错了**——主动更正，讲清错在哪、影响范围多大；
5. 出现失败或负面结果：实验没效果、方法不奏效、假设被推翻、方向被排除；
6. 做了取舍或变更：换 seed、换分母、换切分、调阈值、改口径、放弃某个方案；
7. 要交代限制条件、已知风险、不确定项、尚未验证的假设；
8. 用户问"这是什么意思""为什么""我没看懂"——此时把通俗程度再降一档。

**不必刻意套用**的情况：纯寒暄、一句话能答完的简单查询、纯粹的文件读取确认。
即便不套用，也不能给出"漂亮但站不住"的结论。

## 通俗化的具体手法

| 手法 | 做法 | 例 |
| --- | --- | --- |
| 术语降级 | 先给日常说法，再给专业词 | "能作弊挑最好的那一个，也就是 oracle 上限" |
| 数字换算 | 给一个人话版本，同时保留原分数 | "9/25 —— 25 题里过了 9 题，三分之一多一点" |
| 生活类比 | 找结构相同的日常场景 | "只用了 8 个组合，就像只翻了菜单前 8 页就说没这道菜" |
| 因果分清 | 观察句与推断句分开写 | "观察到 A 和 B 同时变化；由此推断 A 可能是原因，但没验证" |
| 反面说明 | 补一句"如果不这样会怎样" | "不做这一步，各种失败原因就会混在一起，看不出是谁的锅" |
| 先背景后细节 | 讲结论前补一句"这是在干什么" | "这一步的目的是判断：把题拆开写，到底有没有比一次写完更靠谱" |

## 通俗 ≠ 失真（红线，任何情况下不许突破）

- 通俗化只允许换说法，**不允许改变结论的强度和方向**；
- 禁止把"缩小规模复现"说成"复现成功"；
- 禁止把否证性的"No-Go"软化成"值得继续探索"；
- 禁止把"没有测过"说成"应该没问题"；
- 禁止把"我推测"包装成"研究表明"；
- 禁止为了好懂而隐去负面结果、失败尝试、反例、限制条件；
- 若通俗表述与严谨口径可能冲突，**以严谨口径为准**，并在文中点明差异；
- 项目协议红线（private 测试的使用范围、结果标签上限、冻结切分与"不覆盖已有输出"等）
  不因表述通俗而放宽。

## 不许因为通俗而省略的内容（内容底线，与格式无关）

通俗写法可以重新组织、可以长也可以短，但下列内容**不得省略**：

- 原始口径：分子/分母、样本量、题数、seed、模型与配置、数据来源、代码与报告路径、执行命令；
- 限制条件、失败尝试、被排除的解释、尚未验证的假设；
- 不确定项，并显式标注，例如 `【不确定】`；
- 结论强度与标签：不得超出项目允许的表述上限。

**这些内容放在哪里、写多长，由 AI 自己决定；没有"必须单独成段"的要求。**

## 检查自己有没有说清（内容自检，不是格式自检）

1. 出现的每个术语，是否都先解释过、必要时打了比方？
2. 有没有具体例子或数字，而不是只有抽象概括？
3. 原始口径（分母、样本量、条件、seed、来源、路径）写全了吗？
4. 负面结果、失败尝试、限制条件、不确定项，写了还是被省了？
5. 结论强度有没有被"讲得顺口"悄悄放大？标签是否还在允许范围内？
6. 有没有把"我推测"写成事实、把"流程跑通"说成"方法有效"？
7. 如果这件事需要用户或导师拍板，用户读完知道了吗？
   （**只要求讲清楚，不要求每次都去提问**；没有待决事项就不要凑一个问题出来。）

## 常见反例

| 反例（不合格） | 应改成 |
| --- | --- |
| "困难层 zero_wrong 主导，M2 无优势。" | "困难题上，四种方法失分的原因基本是同一个：算法本身想错了。把题拆开写并没有帮上忙——这一步的结论是：这条路在本条件下没走通。" |
| "No-Go for RL。" | "结论：不建议进入强化学习训练。大白话理由是——拆开写连'不比一次写完差'都没做到，再花大代价训练不划算，而且我们已经排除了'是不是采样组合太少'这个解释。" |
| "接口类异常占 M2a 的 55%。" | "拆开写会多出一个毛病：各段之间的接口对不上（A 段给出的东西，B 段接不住）。这类毛病占了失败样本的一半以上，而一次写完的做法完全没有这个毛病。" |
| "已完成，34/34 通过。" | "已完成，检查项全过（34 项里 34 项通过）。但这只说明'能跑通、不报错'，不等于'方法有效'——效果要看实验结果和测试证据。" |
