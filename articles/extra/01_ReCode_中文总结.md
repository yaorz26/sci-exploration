# 01. ReCode：用“推理过程奖励”训练代码模型

原文：[ReCode: Reinforcing Code Generation with Reasoning-Process Rewards](https://aclanthology.org/2026.acl-long.2031/)（ACL 2026）  
对应文件：[01_ReCode_Reasoning_Process_Rewards.pdf](01_ReCode_Reasoning_Process_Rewards.pdf)

## 先用一句话记住

**ReCode 研究的不是“怎样从已有候选里挑一份”，而是“怎样让代码模型在训练时学会更可靠的推理过程”；它用执行是否正确当硬门槛，防止模型只把过程写得像样却把代码写错。**

## 它想解决什么问题

常规代码强化学习常把“单元测试是否通过”当最终奖励。这个信号可靠，却很稀疏：整份程序写完、跑完测试才知道对错。研究者希望加入“推理过程写得好不好”的奖励，让模型较早学到好习惯。

困难在于两点：

1. 很难得到大量人工标注的“这段思考比那段思考好”的数据；
2. 如果直接奖励“看起来严谨的思考”，模型可能学会堆砌漂亮解释，却不提高代码通过率。这就是奖励投机（reward hacking）。

可以把它理解为：老师既想奖励解题草稿写得清楚，又不希望学生用漂亮草稿掩盖最后答案错误。

## 方法：两个部件

### 1. CRPL：自动造出可比较的推理过程，训练过程评分器

对同一题和一段原始推理，论文让模型构造两个版本：

- **优化版**：尝试提升事实准确性、逻辑严密性和叙述连贯性；
- **劣化版**：故意植入细微的事实错误、逻辑跳步或不连贯处。

这样就得到“优化版优于原版、原版优于劣化版”等成对偏好，而不必人工给每一步打绝对分。评分器学习在同一题下给较好过程更高分。论文将此称为 CRPL（Contrastive Reasoning-Process Reward Learning）。

### 2. CG-GRPO：只对功能正确的代码开启过程奖励

训练生成器时，总奖励由格式、最终执行正确性和过程奖励组成。但关键设计是：**只有代码通过严格测试时，过程奖励才生效。**

```text
代码没通过测试  →  过程分不参与奖励
代码通过测试    →  再用过程分区分“同样做对了”的不同推理
```

这样做有两个作用：第一，避免模型为了过程高分牺牲功能正确性；第二，当同一批候选都通过测试、普通二元奖励都相同的时候，过程分仍能提供学习差异。这是论文最值得借鉴的思想：**神经过程分应被可验证的功能信号约束，而不是凌驾于它之上。**

论文还构建了 LiveCodeBench-RewardBench：219 对人工核查过的优/劣代码推理过程，用来检查评分器是不是确实在区分推理质量，而不是只记住最后代码是否通过。

## 作者报告了什么结果

在 HumanEval(+)、MBPP(+)、LiveCodeBench、BigCodeBench 上，作者报告 Qwen2.5-Coder-7B-Instruct 经 ReCode 训练后，综合指标从 50.4 提升到 58.5（相对提升 16.1%），并称其接近 GPT-4-Turbo 的表现。该结果说明：在他们的训练和评测设置里，经过门控的过程奖励可以帮助代码生成器，而不是仅仅让理由更好看。

## 它没有证明什么

- CRPL 的偏好样本主要是自动合成的；“优化版/劣化版”的风格可能与真实程序员的推理错误不同。
- 过程质量与代码正确性有关，不代表读起来好的解释一定会产出正确代码。
- 这是强化学习训练工作，需要数据、训练算力和较完整的评测；它不能直接证明一个 3B、本地、小候选池的过程选择器会有效。
- 219 对人工核查样本适合做初步验证，但不足以覆盖所有代码任务和推理错误。

## 与当前研究最直接的关系

你当前是在**推理时选择/修正候选**，还不是训练一个新的生成器。因此 ReCode 不是应立刻复现的基线，而是后续路线：

1. 先严格证明过程 tie-breaker 在 public 同分候选上有稳定的 private 增益；
2. 再考虑将过程评分作为训练信号；
3. 若走到这一步，应借鉴其“硬门控”原则：过程分只能在公开可验证的条件相同时帮助区分，不能用 private 信息作门控或奖励。
