# 02. LEVER：学习用执行结果验证并重排代码候选

原文：[LEVER: Learning to Verify Language-to-Code Generation with Execution](https://arxiv.org/abs/2302.08468)（ICML 2023）  
对应文件：[02_LEVER_Learning_to_Verify_with_Execution.pdf](02_LEVER_Learning_to_Verify_with_Execution.pdf)

## 先用一句话记住

**LEVER 从“题目、候选程序、程序运行结果”学习一个正确性概率，用它和模型原始生成概率一起重排多份候选。**

## 背景：为什么只看报错还不够

多次采样时，模型常常已经生成了正确程序，只是系统不知道该交哪一份。最简单的做法是删掉编译错误或运行报错的候选；问题是，两个候选都能运行也可能一个正确、一个错误。

运行输出本身常带有更细的信息。例如，SQL 查询都不报错，但一个返回人数、另一个返回姓名列表；Python 程序都能执行，但一个输出整数、另一个输出列表。仅用“能不能跑”这个二元规则会丢掉这些信息。

## 方法：生成、执行、验证、重排

```text
自然语言任务
    ↓
代码模型生成多份程序，并保留生成概率
    ↓
执行器得到每份程序的结果或报错
    ↓
LEVER 验证器读取：任务 + 程序 + 执行结果
    ↓
输出“这份程序正确”的概率，并与生成概率结合重排
```

验证器不是只给执行结果打分。它同时看任务描述、代码和结果，因此可判断“这个输出的类型、数值范围和语义是否像题目想要的”。论文还会把执行结果相同的候选合并考虑，避免大量行为完全一样的代码重复左右排序。

## 作者报告了什么结果

论文在表格问答、数学问答和基础 Python 编程等四类数据集上评估。以 code-davinci-002 为例，作者报告相对于强执行过滤基线有 4.6% 到 10.9% 的提升，并在当时各任务达到较强结果。

它支持的结论很具体：**执行结果不只是过滤错误的开关，也可以是学习型验证器的输入。**

## 它没有证明什么

- 它仍需要能安全执行程序或查询的环境；现实中很多程序依赖网络、文件、数据库或副作用，不能随意运行。
- 验证器需要正确/错误监督来训练，且可能学到特定数据集的输出模式，而非真正理解规格。
- 执行结果只是有限输入下的行为；没有覆盖到的边界错误仍会漏过。
- 使用执行结果不等于可以使用 private 测试结果。推理时只能送入 public 或方法自己生成的可见输入。

## 与当前研究最直接的关系

它是你的 **最直接外部基线之一**。你可在固定候选池上比较：

1. 首候选；
2. public pass-rate 选择；
3. 固定同分规则；
4. LEVER 式“题目 + 候选代码 + public 运行细节”的学习验证器；
5. 你的过程 tie-breaker。

关键控制是：训练验证器、选择候选、调阈值都不能看到对应题目的 private 测试输出；private 只在最后报告一次效果。这样才能分清过程信号是否真的超过了“直接学习执行结果”。
