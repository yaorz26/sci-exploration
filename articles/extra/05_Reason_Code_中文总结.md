# 05. Reason-Code：失败后才启动的测试驱动树搜索

原文：[Reason-Code: Reliable Code Generation via Test-Driven Monte Carlo Tree Search](https://aclanthology.org/2026.acl-industry.30/)（ACL 2026 Industry）  
对应文件：[05_Reason_Code_Test_Driven_MCTS.pdf](05_Reason_Code_Test_Driven_MCTS.pdf)

## 先用一句话记住

**Reason-Code 先用贪心方式写一次；若可见测试失败，才用执行报错驱动少量 MCTS 修正搜索，因此把额外预算集中花在难题上。**

## 背景：多采样有效，但代价可能太高

给每题生成十份代码，正确候选出现的机会会增加，但 token、延迟和执行成本也近似线性增加。对简单题而言，这十次尝试多数是浪费。论文追问的是：能否先用便宜的一次生成解决简单题，把搜索预算留给真正失败的题？

## 方法：完整程序节点的 MCTS，而非逐 token 搜索

Reason-Code 的树节点是一份**已经可执行的完整程序**及其测试结果，不是一个 token。边是一条根据父节点报错提出的整段修正建议。

1. 先以温度 0 生成初始程序；若通过可见测试，直接输出；
2. 若失败，收集 `AssertionError`、traceback 等执行反馈，转换为修正提示；
3. 以 MCTS 的 UCB1 规则选择优先扩展的候选：既偏好过去成功率高的分支，也给较少尝试的分支探索机会；
4. 生成少量修正后的完整程序，运行沙箱；通过为 1，失败为 0；
5. 将这个二元结果向上回传，直至耗尽小预算；最后返回成功候选或最佳搜索结果。

它不训练 PRM，也不需要模型输出 token 概率，因此理论上可用于量化模型或黑盒 API。文中的 Reflexion 文本反馈是用来产生新候选的工具，不是把错误信息直接伪装成连续奖励。

## 作者报告了什么结果

论文在 HumanEval 和 MBPP-Sanitized 上评估。其部署导向结果中，自适应 MCTS 的平均 token 成本约为单次贪心的 1.5 倍，在 HumanEval 达到 88.4% pass@1；对比 Best-of-10 的约 10 倍成本，展示了较好的成本—准确率权衡。

更值得注意的是作者自己的受控结论：在他们研究的小预算下，执行引导的自适应推理优于独立采样/过滤，但 UCB 引导 MCTS 相比更简单的树搜索或迭代修正，差异并不显著。这是很好的科研写法：不能只因用了 MCTS 就把增益都归功于 MCTS。

## 它没有证明什么

- 它假设推理阶段存在可运行的测试。没有测试时，方法的二元回报与“是否触发搜索”都失去依据。
- 如果选择、停止和最终评价都使用同一批测试，容易只说明对已见测试拟合得更好；你的实验必须保留 private 测试做最终评价。
- 完整程序级节点比 token 级搜索简单，但仍可能反复探索相似错误；树结构本身未必比简易修正更划算。
- 小预算下得出“更省”的结论，不会自动扩展到更复杂任务、长程序或不同执行环境。

## 与当前研究最直接的关系

它非常适合作为“**何时额外花计算**”的对照。当前可先做简单版本，而不急于实现 MCTS：

```text
public 测试已能明确选出候选 → 不调用过程模型
public 测试最高分并列          → 才调用过程 tie-breaker
初始候选都失败                → 才考虑一轮执行反馈修正
```

这和 Reason-Code 的条件预算思想一致，但你的首要问题仍是过程 tie-breaker 是否在独立 private 评价上有效。应先将简单的“失败后一次修正”作为基线，再判断树搜索是否真的值得增加复杂度。
