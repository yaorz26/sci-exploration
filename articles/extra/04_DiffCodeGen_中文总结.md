# 04. DiffCodeGen：没有公开测试时，用候选间的行为差异选程序

原文：[Code Generation by Differential Test Time Scaling](https://arxiv.org/abs/2605.20473)（2026 预印本）  
对应文件：[04_DiffCodeGen_Differential_Test_Time_Scaling.pdf](04_DiffCodeGen_Differential_Test_Time_Scaling.pdf)

## 先用一句话记住

**DiffCodeGen 不问“哪个候选通过了标准答案测试”，而是让多个候选在模糊测试输入上互相比较：行为最接近多数、又最居中的候选，被当作更可信的答案。**

## 背景：现实中往往没有 public 测试

已有很多测试时扩展方法依赖公开单元测试或额外调用大模型作为评委。这在比赛题里可行，但在真实需求刚提出时，用户可能只写了一段自然语言说明，没有现成测试。

DiffCodeGen 使用软件测试中的“差分测试”思想。若多个实现都声称实现同一个规格，那么在同一输入上出现不同输出时，至少有一个实现有问题；若大多数实现行为一致，偏离者更值得怀疑。它把模型的多个采样候选视为“同一规格的多个实现”。

注意：这是一个合理但不绝对成立的假设。多数候选可能一起误解题意。

## 方法：模糊测试、行为聚类、选群体中心

```text
同一题目 → 用不同采样/提示生成多份候选
              ↓
覆盖率引导的 fuzzing 自动产生大量输入
              ↓
在这些输入上运行所有候选，记录每份候选的输出行为
              ↓
按行为相似度把候选聚成群
              ↓
选最大群中距离其他成员最近的候选（medoid）
```

这里不需要每个输入的“正确输出”。fuzzer 的目标是尽可能走到不同代码路径、暴露不同候选间的差异；聚类的目标是找行为最一致的一群；medoid 是该群中最居中的实际候选，而不是虚构的平均程序。

论文强调选择阶段不再额外调用 LLM，因此相较“再找一个模型当裁判”的方法，额外 token 成本很低；执行和模糊测试仍然有计算成本。

## 作者报告了什么结果

作者在四个不同类型和规模的代码模型上评估，并报告在 LiveCodeBench 等数据上持续提升 pass@1。论文还报告，相对于先前需要额外模型调用的测试时扩展方法，在本地模型条件下执行时间约为其五分之一，在 API 模型条件下约为其 5%，且输入 token 更少。

因为它目前是预印本，以上数字应视为作者报告的初步证据；在将它作为核心结论或主基线前，应检查代码、完整设置和后续同行评审状态。

## 它没有证明什么

- **多数一致不等于多数正确。** 候选若共享同一算法误解，最大群会稳定地选错。
- fuzzing 要能生成合法输入、在沙箱中运行候选，并处理超时、异常和副作用；通用竞赛题的输入格式会增加工程难度。
- 覆盖率高也不等于覆盖了题目语义的关键边界。
- 它不使用公共测试，不代表它没有成本：fuzzing、插桩和 N 份候选的反复执行都要计入时间预算。

## 与当前研究最直接的关系

这是当前 tie-breaker 方向的**优先比较对象**。它提供的不是过程语义分数，而是纯动态行为证据。推荐的公平问题是：

> 当 public 最高分相同且无法决定时，过程评分、差分行为一致性、固定规则，谁能在独立 private 测试上带来更稳定的增益？

为公平起见，三种方法必须使用相同的初始候选池；若 DiffCodeGen 需要额外候选、fuzzer 时间或执行次数，须单列预算。它可以帮助你证明过程信息是否真的有额外价值，而非仅仅代替了一个更简单的动态测试选择器。
