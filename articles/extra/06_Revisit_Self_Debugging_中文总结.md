# 06. Revisit Self-Debugging：模型自己写的测试，为什么会把自己带偏

原文：[Revisit Self-Debugging with Self-Generated Tests for Code Generation](https://arxiv.org/abs/2501.12793)（2025 预印本）  
对应文件：[06_Revisit_Self_Debugging_with_Self_Generated_Tests.pdf](06_Revisit_Self_Debugging_with_Self_Generated_Tests.pdf)

## 先用一句话记住

**“模型根据自己写的测试把自己的代码修到通过”不等于修正确了；错误的测试期望输出会制造错误反馈，甚至使修正后在真实隐藏测试上更差。**

## 背景：没有标准测试时，自测试看起来很诱人

自调试的常见流程是：模型写代码 → 跑测试 → 看到失败信息 → 修改代码。若拥有可信的 oracle 测试，这很自然。问题在于现实中通常没有现成 oracle，于是人们让模型根据题目自己写测试（输入和期望输出）再调试。

这篇论文不急着提出更复杂的新算法，而是先做必要的追问：这种自生成测试到底可靠吗？它把两种反馈严格分开。

| 方式 | 模型能看到什么 | 主要风险 |
| --- | --- | --- |
| 后执行（post-execution）调试 | 输入、模型写的期望输出、实际输出、报错 | 期望输出若错，模型会被错误“标准答案”带偏 |
| 执行中（in-execution）调试 | 程序运行过程中的基本块、变量状态/轨迹 | 信息更细，但需要插桩，并不直接告诉模型什么输出才对 |

## 方法：把“失败后的结果”与“运行中的状态”分开实验

论文让 GPT-4o、Claude-3.5-Sonnet、Llama-3-70B、Qwen2.5-Coder-7B 在 HumanEval、MBPP、LiveCodeBench 的 Python 题上：先生成代码和十条测试，再分别使用两种反馈调试。

后执行方式将“实际输出不等于模型自写的期望输出”作为失败信号；执行中方式把程序切成基本块，记录每个块执行前后的变量状态，让模型据此定位可疑处。论文同时以可信 oracle 测试作参照，测量模型自写测试的输入、输出和整套测试是否可靠。

## 作者报告了什么结果

- 使用**可信 oracle 测试**时，反复调试通常能提高表现；这说明模型并非完全不会利用执行反馈。
- 但使用**自生成测试**做后执行调试时，HumanEval/MBPP 等基础题上常出现下降；例如 Qwen2.5-Coder-7B 的 HumanEval+ 从一次生成的 81.7% 降至约 75.6%--79.3%（取决于反馈和迭代设置）。
- 原因是测试偏差：即使单个测试输入多数合法，模型仍常写错期望输出。论文中强模型生成的“整套测试全部正确”的比例也仅约 57%--59%，Qwen2.5-Coder-7B 约 44%--45%。
- 对更困难的 LiveCodeBench，部分强模型和简短标签反馈出现提升；但并非所有模型、难度或反馈细节都提升。
- 使用执行中轨迹、避免依赖自写的期望输出后，作者观察到更有希望的改进。

## 它没有证明什么

- 研究范围主要是自包含 Python 函数；结论不应直接推广到仓库级工程、编译型语言或有真实用户测试的情形。
- 执行中轨迹并非免费：需要安全插桩、记录状态，并可能给模型较长上下文。
- 基础题上的下降不表示“所有自调试都无效”；它指出的是**自生成 oracle 的可靠性是关键条件**。
- 论文是预印本，适合用作严谨的警告和实验设计依据，不宜单独作为定论。

## 与当前研究最直接的关系

这篇论文是你 public/private 隔离设计的强支撑。它说明为什么以下两句话必须分开：

```text
“候选通过了当前可见测试”
≠
“候选对题目真的正确”
```

若你加入 CodeT 式自生成测试或 Reason-Code 式反馈修正，必须始终在独立 private 测试上验收，并报告自生成测试本身的正确率/覆盖率。否则，即使 public 或自测试分数提高，也可能只是模型更擅长迎合它自己写错的测试。
