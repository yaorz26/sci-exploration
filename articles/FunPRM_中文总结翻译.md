# FunPRM：面向代码生成的“函数即步骤”过程奖励模型与元奖励校正

> 说明：本文档是基于原论文的中文总结式翻译，重点保留研究动机、方法、实验结果和局限性，并非逐句全文翻译。

## 论文信息

- 英文标题：FunPRM: Function-as-Step Process Reward Model with Meta Reward Correction for Code Generation
- 作者：Ruiyi Zhang、Peijia Qin、Qi Cao、Eric Xue、Pengtao Xie
- 机构：University of California, San Diego
- 来源：arXiv:2601.22249v1，2026 年 1 月/2 月版本

## 一句话总结

FunPRM 把代码中的函数视为过程奖励模型（PRM）的中间推理步骤，再用单元测试得到的可靠最终结果去校正蒙特卡洛方法产生的噪声中间奖励，从而在测试时从多个候选程序中更准确地选出高质量代码。

## 摘要翻译

代码生成是大语言模型的重要应用，但模型在复杂编程任务上仍经常失败。数学推理中的测试时扩展方法，尤其是基于过程奖励模型的 Best-of-N 选择，为提升代码生成效果提供了可能。然而，现有 PRM 用于代码生成时效果有限，主要原因是代码缺少自然且有意义的步骤划分，同时通过蒙特卡洛采样估计部分解正确性的奖励也存在较大噪声。

论文提出 FunPRM。它通过提示词引导模型生成按函数组织的模块化代码，并把函数作为 PRM 的推理步骤。此外，FunPRM 引入基于元学习的奖励校正机制，利用单元测试系统得到的干净最终解奖励来净化噪声较大的部分解奖励。在 LiveCodeBench 和 BigCodeBench 上的实验表明，FunPRM 在五个基础大模型上都稳定超过已有测试时扩展方法；与 O4-mini 结合时，在 LiveCodeBench 上取得 80.9 的 pass@1，达到论文报告的当时最佳结果。人工评估还显示，FunPRM 生成的代码更容易阅读和复用。

## 1. 研究背景与问题

### 1.1 为什么代码需要过程奖励模型

大语言模型一次可能生成正确代码，也可能生成错误代码。因此，可以先生成 N 个候选，再选择最有希望的一个。Outcome Reward Model（ORM）只判断最终代码，而 PRM 会评价生成过程中的多个中间步骤，理论上能更早识别“看起来有希望但最终会失败”的方案。

但数学题的思维链通常天然由若干推理步骤构成，代码没有统一的“步骤”定义：

1. 如果把每一行代码作为一步，程序可能有数百步，计算成本很高，语义也过于细碎。
2. 部分代码的真实正确性难以直接获得。蒙特卡洛方法通过继续采样完整程序来估计部分程序最终成功的概率，但样本有限时会产生噪声。

### 1.2 FunPRM 的核心观点

代码中的函数通常对应相对独立的逻辑模块。函数既比单行代码更有语义，也比整段程序更细粒度，因此适合作为代码 PRM 的步骤。

论文同时利用代码任务的一个特殊优势：完整程序可以通过单元测试直接判断。也就是说，部分解的奖励可能是噪声标签，但最终解可以获得相对可靠的“通过/失败”信号。FunPRM 用后者反过来修正前者。

## 2. 方法

### 2.1 Chain-of-Function：函数即推理步骤

FunPRM 的提示词要求模型：

- 将可独立处理的逻辑拆成不同函数；
- 先写高层函数，例如 `main()`，再写辅助函数；
- 避免嵌套函数，保持函数处于顶层；
- 为每个函数添加 docstring，说明算法、策略和作用。

以“两个有序数组的中位数”为例，模型可以生成：

1. `main()`：负责在较短数组上进行二分搜索并组织整体流程；
2. `get_part_val()`：读取分割点周围的四个边界值，并处理数组首尾情况；
3. `eval_part()`：判断当前分割是否正确，并决定向左还是向右继续搜索。

这样，函数不仅是代码模块，也成为 PRM 可以逐步评分的语义单元。该提示还会改善代码的可读性、复用性和维护性。

### 2.2 元学习奖励校正

对每条候选轨迹，论文准备两类监督信号：

- 噪声部分奖励：对每个部分解继续采样若干完整解，以最终通过率估计该部分解的奖励；
- 干净最终奖励：完整代码交给单元测试系统，直接得到最终通过/失败结果。

论文使用一个可训练的奖励校正表，为每个部分奖励添加可学习残差，并把结果截断到 `[0, 1]`。之所以使用轻量的表，而不是更大的校正网络，是因为代码数据集规模有限，大模型式校正器容易过拟合。

训练过程是一个双层优化过程：

1. 用当前校正后的部分奖励训练 PRM，并进行一步梯度更新；
2. 用更新后的 PRM 在干净最终解数据上计算元损失；
3. 根据元损失反向调整奖励校正表，使校正后的部分奖励能训练出更能泛化到最终结果的 PRM。

论文用有限差分近似元梯度，避免显式构造昂贵的二阶导数。

### 2.3 PRM 形式与测试时选择

FunPRM 使用 Qwen-2.5-Coder-7B 作为骨干，仅训练 LoRA 参数。它采用生成式奖励模型：模型被要求对当前代码前缀输出 `+` 或 `-`，再用两个标记的生成概率计算奖励：

```text
score = p(+) / (p(+) + p(-))
```

推理时，基础模型为同一个问题生成多个候选程序，FunPRM 对每个函数步骤打分，再聚合各步骤分数，选择得分最高的候选。论文的主实验通常为每题生成 8 个候选，且不依赖推理阶段的公开测试用例，因此成本低于多轮执行和修复型智能体方法。

整体流程可以概括为：

```text
代码问题
  -> 生成多个按函数组织的候选程序
  -> FunPRM 对函数步骤逐步评分
  -> 聚合步骤奖励
  -> 选择得分最高的程序
```

## 3. 实验与结果

### 3.1 实验设置

- LiveCodeBench：使用 2024-08-01 之前的 601 道题训练，之后的 454 道题测试；另在 2025-02-01 之后的 131 道题上进行较小规模的排行榜比较。
- BigCodeBench：800 道训练题，340 道测试题，包含需要调用多个库函数的实际编程任务。
- 泛化测试：HumanEval+ 和 MBPP+，不在这些数据集上额外训练。
- 基础模型：O4-mini、Qwen3-Coder、GPT-4o-mini、DeepSeek-Coder、Qwen2.5-7B-Coder 等。
- 对比方法：Self-Certainty、ORM、Skywork-PRM，以及不做测试时扩展的强大语言模型。

### 3.2 LiveCodeBench 排行榜比较

在 131 道较新的题目上，使用 O4-mini（High）生成候选时，结果如下，单位为 pass@1（%）：

| 方法 | Easy | Medium | Hard | Overall |
| --- | ---: | ---: | ---: | ---: |
| O4-mini（High，单次生成） | 100.0 | 89.7 | 57.4 | 77.1 |
| Self-Certainty | 100.0 | 86.5 | 59.8 | 77.3 |
| ORM | 100.0 | 89.7 | 62.3 | 79.4 |
| Skywork-PRM | 100.0 | 87.2 | 59.8 | 78.1 |
| **FunPRM** | **100.0** | **92.3** | **63.9** | **80.9** |

FunPRM 的总体结果超过 O4-mini 本身及其他测试时扩展基线，说明函数级过程评分能进一步利用强基础模型生成的多个候选。

### 3.3 不同基础模型上的稳定性

在较大的测试集上，FunPRM 在四个基础模型和两个代码基准上都取得最高总体分数：

| 基础模型 | LiveCodeBench 基础 | LiveCodeBench + FunPRM | BigCodeBench 基础 | BigCodeBench + FunPRM |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-Coder-30B-A3B | 33.12 | **36.34** | 46.29 | **47.94** |
| GPT-4o-mini | 27.50 | **29.74** | 41.80 | **43.82** |
| DeepSeek-Coder-33B-Instruct | 18.00 | **21.37** | 40.90 | **44.83** |
| Qwen2.5-7B-Coder | 16.87 | **19.60** | 36.30 | **39.71** |

论文报告 FunPRM 在 20 个难度/模型/数据集组合中有 18 个取得最佳结果。它超过 Self-Certainty，表明学习到的奖励比简单置信度启发式更有效；也超过 ORM，说明中间函数步骤的细粒度信息确实有价值。

### 3.4 跨数据集泛化与人工评估

- 在不额外训练的情况下，HumanEval+ 的 pass@1 从基础模型的 67.13 提升到 80.95；MBPP+ 从 68.52 提升到 82.32。
- 人工评估由 3 名计算机科学研究人员完成。在两种方法都生成正确代码的题目上，FunPRM 代码获得 54.2% 的偏好，基础模型为 45.8%；在两者都错误的题目上，FunPRM 在可复用性和易修复性方面获得 53.8% 的偏好，基础模型为 46.2%。

这说明 FunPRM 的收益不只体现在是否通过测试，也体现在代码组织质量上。

### 3.5 消融与步骤数量分析

在相同的 131 道 LiveCodeBench 题上：

| 版本 | Overall pass@1 |
| --- | ---: |
| 去掉 Chain-of-Function | 80.1 |
| 去掉元奖励校正 | 80.2 |
| **完整 FunPRM** | **80.9** |

两个模块都带来独立收益。随着题目难度提高，代码通常包含更多函数步骤，但也有一些困难题只需一个函数，说明“函数数量”不能单独代表问题难度。

## 4. 论文结论与评价

论文的主要贡献是把“代码如何划分步骤”和“部分步骤奖励如何获得”这两个问题同时处理：前者用函数结构提供语义清晰的过程单元，后者用最终单元测试结果做元学习校正。实验表明，这种组合能以一次生成、多候选筛选的方式提升代码正确率，并改善生成代码的可读性和复用性。

需要注意的是，FunPRM 依赖候选代码本身具有较好的函数组织结构；如果基础模型不愿意遵循提示，函数级步骤可能不稳定。它的主要实验也集中在 Python 代码和有限的代码基准上，不能直接推断到所有编程语言或软件工程任务。

## 5. 局限性与安全提醒

- 单元测试通过不等于代码绝对正确，仍可能存在未覆盖的边界条件或安全漏洞。
- 自动生成代码可能造成数据泄露、系统行为异常或安全漏洞，尤其不能未经审查就在高风险环境运行。
- PRM 只负责评分，最终候选仍可能全部错误；实际使用应配合代码审查、更多测试和沙箱执行。
- 论文主要在 Qwen2.5-Coder-7B 上训练 LoRA，其他 PRM 骨干和更大规模训练设置仍需验证。
- 当前重点是测试时扩展，没有系统研究将 FunPRM 奖励用于强化学习训练。
