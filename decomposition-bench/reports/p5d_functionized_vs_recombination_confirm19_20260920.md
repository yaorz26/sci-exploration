# P5d 确认实验：完整函数化候选、独立重组与直接生成

日期：2026-09-20  
性质：预注册的 19 题确认实验；APPS custom split、单 seed、机制层比较，不是官方 APPS 基准复现。

## 一句话结论

按预注册判读规则，F1“同一份完整程序内强制函数化”没有达到正向信号门槛：选择后私测为 `11/19`，只比直接生成 M0 的 `10/19` 多 1 题，但候选池上限与 M0 同为 `12/19`。M2a“独立拆分、分别实现、再组合”更差：选择后私测和候选池上限均为 `8/19`。因此当前证据支持继续研究“完整候选中的结构化评分/路由”，不支持在现有 prompt-only M2 管线上直接进入 RL。

## 1. 研究问题与预注册口径

本实验区分两个容易混在一起的问题：

1. 在一份完整程序中按多个顶层函数组织，是否有助于生成和选择正确程序？
2. 把函数分别实现后跨候选组合，是否能得到独立生成拿不到的正确程序？

三条路线：

- **M0 direct**：直接生成完整程序，每题 14 个候选；
- **F1 functionized**：一次生成完整程序，但要求 2--5 个顶层函数、入口函数最后、禁止嵌套函数，每题 10 个候选；
- **M2a modular**：JSON 分解，每题 2 份分解、每个函数 2 个实现、每份分解最多 8 个组合；使用 `repair_v1`，允许嵌套函数（A1），不允许未声明依赖和前向依赖。

F1 是 FunPRM 风格的“完整函数化候选”对照，不是 FunPRM 的完整复现；M2a 是 prompt-only 的独立重组机制，也不是 DecompRL 的完整复现，因为没有训练分解器或实现器。

### 数据与成员

- 模型：Ollama `qwen2.5-coder:7b` Q4_K_M；seed `42`；
- 数据：APPS `train`、revision `21e74ddf8de1a21436da12e3e653065c5213e9d1`、`introductory`；
- private 安全数据 SHA-256：`06dbea3990fe9185c84edeef16501d2c9ca84a9216128ad79d34c8ece9d3b11d`；
- 确认集：19 道，内部 ID 为 `apps-train-2710`、`2711`、`2712`、`2713`、`2714`、`2717`、`2718`、`2719`、`2723`、`2724`、`2725`、`2726`、`2727`、`2728`、`2730`、`2731`、`2732`、`2733`、`2734`；
- 预先标记的“结构适用”子组：13 道，成员见 `data/processed/p5d_confirm19_analysis_20260920.json`。

题目成员、提示和候选预算在确认生成前冻结。public 只用于选择，private 只在选择冻结后评测；private pool oracle 是事后诊断，不参与任何选择。

## 2. 预注册预算与实际成本

试跑以 M2a 每题 `971.2` output token 为目标，冻结：M0 14 候选/题、F1 10 候选/题，M2a 保持 `d=2/i=2/c=8`。预算清单见 `experiments/p5d_functionized_candidates_20260920/budget_manifest.json`。

| 方法 | 确认请求/组合 | output token | 每题平均 output token | 相对 M0 | 模型时间 | prompt token |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| M0 direct | 266 生成请求 | 26,689 | 1,404.7 | 1.00x | 861.496 秒 | 99,246 |
| F1 functionized | 190 生成请求 | 31,251 | 1,644.8 | 1.17x | 1,028.458 秒 | 82,670 |
| M2a modular | 38 分解 + 240 实现请求 | 20,104 | 1,058.1 | 0.75x | 871.959 秒 | 158,694 |

这里的实际 token 与试跑外推不同，尤其 M2a 低于目标、F1 高于 M0。因而主结论同时报告冻结预算和实际成本，不把 M2a 的较低 output token 误写成等预算优势。

## 3. 主结果

“选择后私测”是：只看公开测试挑出一份候选，再检查这份候选是否通过全部 private 测试。  
“pool oracle”是：把同一批候选全部拿出来，事后假设可以直接挑出 private 全通过的最好一份；它是候选池的上限，不是可部署成绩。

| 方法 | 有候选题 | 有效生成/实现 | 唯一候选/程序 | public 选优全通过 | 选择后 private 全通过 | private pool oracle |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| M0 direct | 19/19 | 263/266 | 141 | 14/19 | **10/19** | **12/19** |
| F1 functionized | 19/19 | 140/190 | 120 | 15/19 | **11/19** | **12/19** |
| M2a modular | 19/19 | 分解 38/38；实现 240/240 | 105 个独特可组合程序 | 10/19 | **8/19** | **8/19** |

### 成对变化

- F1 相对 M0：3 道题从失败变成功，2 道题从成功变失败，选择后净增 `+1`；pool oracle 净变化 `0`。
- M2a 相对 M0：3 道题从失败变成功，5 道题从成功变失败，选择后净变化 `-2`。
- 13 道预先标记的结构适用子组：M0 `7/13`、F1 `7/13`、M2a `4/13`；pool oracle 分别为 `8/13`、`8/13`、`4/13`。

这说明 F1 的 +1 主要是公开测试挑选效果的小变化，并没有证明函数化让候选池本身出现更多正确解。M2a 则在总体和结构子组都没有正向信号。

## 4. 结构与失败分析

### F1：同一份完整程序内函数化

190 次生成中 140 次通过结构解析，50 次被拒绝。错误计数如下；同一响应可能同时触发多类错误：

- `function_count_out_of_range`：21；
- `nested_function_definitions`：24；
- `entrypoint_not_last`：13；
- `invalid syntax`：5；
- `missing_entrypoint`：3；
- `signature_mismatch`：3。

因此，强制结构带来约 `26.3%` 的生成无效率（50/190）。不过每道题仍至少保留一个可测试候选，未造成题目级空池。

### M2a：独立函数实现再组合

M2a 的解析流程全部通过，但 284 个组合只产生 105 个独特程序，重复组合为 `179/284`。这说明“组合数量”明显大于“新的完整解法数量”。

更重要的是，候选池中已经观察到跨函数契约断裂。例如 oracle 复测中出现 `NameError: name 'dict_scores' is not defined`：某个函数内部使用了另一个函数实现应提供的变量，但组合器没有发现这种隐式共享状态。换句话说，局部函数单看像是合理的，拼到一起却接不上。

### 观察与推断分开

- **我观察到的是**：M2a 的分解和实现解析率为 100%，但 pool oracle 只有 `8/19`；F1 的 pool oracle 与 M0 相同，结构适用子组也没有高于 M0。
- **我由此推断的是**：当前主要瓶颈不是“有没有把代码写成函数”，而是函数边界、共享状态和完整算法之间的协调。这个推断与具体的 `NameError` 反例一致，但仍不能单独证明所有题目的失败都由同一个原因造成。

## 5. 与论文正收益的关系

本实验不否定论文，而是说明操作对象不同：

- CodePRM 主要拆自然语言思路，并用执行反馈定位和修正，不做跨候选函数拼装；
- FunPRM 选择的是完整、按函数组织的候选，函数是评分单位，不是独立零件池；
- DecompRL 才接近独立分解和组合，但它的正收益依赖训练后的分解策略、实现策略和组合后奖励；论文中的无 RL 层级结果本身低于直接生成；
- 本地 M2a 只有 prompt-only 分解、独立实现、固定组合和 public 选择，没有让模型学习“何时拆、如何拆、如何遵守阶段契约”。

因此可以得到的窄结论是：在当前模型、提示、预算和 APPS custom split 下，“只靠提示词独立拆分再组合”没有形成正向信号；不能把它写成“函数拆分永远无效”，也不能把本实验称为 DecompRL 复现。

## 6. 判读、限制与下一步

### 按预注册规则的判读

预注册要求 F1 同时在选择后 private 和 pool oracle 两个指标上高于 M0，并且实际 output token 不超过 M0 的 1.5 倍。实际结果是：

- 成本条件满足：`31,251 / 26,689 = 1.17x < 1.5x`；
- 选择后 private 高于 M0：`11/19 > 10/19`；
- pool oracle 未高于 M0：`12/19 = 12/19`。

所以 F1 **未达到预注册的正向信号标准**，只能记录为“选择层面的探索性 +1”。M2a 的两个主要指标都低于 M0，不支持继续扩大当前独立重组管线。

### 运行记录中的非科学失败

- M0 第一次启动把来源数字题号误当成内部 `apps-train-*` ID；runner 在调用模型前就拒绝，未写入确认结果；修正 ID 后重新运行。
- M2a 第一次启动使用了脚本不存在的旧参数名；命令在参数解析阶段退出，未调用模型；改用 `--protocol json --prompt-variant repair_v1` 后重新运行。
- 这两次退出都发生在确认生成前，未改变题目、提示、预算、选择或 private 评测，因此不计入方法失败样本。

### 限制

- 只有一个 seed；不能称为稳定性结论；
- 只有 19 道确认题，且来自 APPS custom split，不等于官方 APPS 基准；
- F1 约 26.3% 结构无效响应，存在明显 format tax；
- M2a 实际 output token 低于 M0，三臂不是严格相同的真实 token 数；
- pool oracle 是事后诊断上限，不能当作真实部署结果；
- 本实验没有训练分解器、实现器、PRM 或 RL。

### 建议顺序

1. **优先**：做 FunPRM 风格的“完整函数化候选 + 函数级评分 + 完整候选选择”对照，隔离函数结构是否有价值；
2. **其次**：让更强模型只生成分解方案，本地模型负责实现，验证瓶颈是不是分解质量；
3. **若前两步在留出题上出现稳定正信号**：再训练分解器或路由器，并把“不拆分”作为合法动作；
4. **最后**：只有训练/排序阶段已显示正向信号，才考虑联合 RL。

当前不建议：继续增加 M2a 的组合数量、扩大 `repair_v1`，或把当前 prompt-only 管线直接送入 RL。
