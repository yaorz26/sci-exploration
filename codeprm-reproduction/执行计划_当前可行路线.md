# CodePRM 当前可行路线执行计划

更新时间：2026-09-04  
工作目录：`D:\yaorz\research\codeprm-reproduction`

本计划是在已有最小流程基础上继续执行的版本。已有离线 fixture、执行器、Ollama 候选生成、反馈记录、轻量 PRM、GVR 和简化 MCTS 不删除、不覆盖；真实 APPS 实验使用独立的数据文件名和输出后缀。

## 1. 当前结论

当前机器可以完成一条可信的“缩小规模 CodePRM 复现”路线：

```text
真实 APPS Introductory
→ Qwen2.5-Coder 3B 生成候选
→ public/private 执行反馈
→ Ridge/轻量 MLP CodePRM
→ GVR
→ 20/50/100 题对比实验
```

这条路线可以验证数据闭环、执行反馈标签、候选选择和 GVR 的机制，但不能宣称已经复现论文的 7B 神经模型或 Table 1 数字。

## 4. 阶段 A：真实数据闭环

目标：固定真实 APPS 子集，完成真实 APPS 20 题的候选和反馈记录。

### A0. 环境复查

执行：


产物：

- `reports/environment.json`；
- E0 回归结果。

验收：四类执行器测试全部通过；模型名称、GPU 和依赖状态已经写入环境快照。

### A1. 准备 APPS 数据（首个子集已完成）

已完成输入为 Hugging Face `codeparrot/apps` 的固定 revision `21e74ddf8de1a21436da12e3e653065c5213e9d1`，使用 `train` split 的前 20 道可用 Introductory 题。生成文件：

- `data/raw/apps_train_introductory20.json`；
- `data/splits/apps_train_introductory20.json`；
- 获取脚本：`scripts/fetch_apps_subset.py`。

输入必须能映射到以下字段：

```text
problem_id
question
starter_code（可选）
public_tests
private_tests
```

执行要求：

1. 记录来源、版本/commit、下载日期和许可证；
2. 先只选 APPS Introductory 的 20 道题；
3. 用现有 `src/data_loader.py` 转换；
4. 人工抽查 5 道题的题面、输入、输出和测试划分；
5. 生成固定 split manifest，禁止运行时随机改变题目集合。

验收已通过：20 道题、71 个 public 测试、82 个 private 测试；5 道题抽查字段和测试格式通过；重复运行得到相同题目 ID 和 SHA-256 `2fef66b2119b160ae90375485d34cb7190586bd053803efc37f98d4d79039d84`。

当前这份数据是 `train` split，且 public/private 为按 `input_output` 前半/后半样例的自定义划分，只能用于缩小规模和训练闭环。要做论文严格 test 评估，仍需在网络/带宽允许时获取官方 `test` split 的固定版本。

重要限制：如果原始数据没有官方 public/private 划分，必须显式记录自定义划分规则；这种结果只能称为自定义评测，不能称为严格论文复现。

### A2. 执行器安全和格式审计（函数式适配已完成）

先在 5 道题上检查：

- 标准输入是否能够传入；
- 输出空格和换行是否需要规范化；
- 超时后进程是否被清理；
- 长输出是否截断；
- 语法错误、运行错误、错误答案和超时是否分别记录。

本批 20 道题均被识别为函数式 APPS 任务；执行器现在根据 `starter_code` 自动导入并调用函数，并兼容 APPS 常见的单例输出包装。20 题阶段可使用当前执行器；扩大到 50/100 题前，优先增加进程树清理、输出长度限制和资源限制。运行来源不明的恶意代码前必须改用 Docker/WSL 等 OS 级隔离。

## 5. 阶段 B：候选生成和反馈

目标：获得不泄漏 private 测试的真实候选池和 CodePRM 训练记录。已完成 Qwen3B 的 20 题 × 4 候选批量收集，共 80 条反馈记录；函数 harness 已覆盖本批 20 道函数式任务。

### B1. 固定生成协议

使用：

```powershell
python scripts/run_baseline.py `
  --config configs/ollama.yaml `
  --apps-path <APPS_JSON_OR_JSONL> `
  --output-suffix apps_intro20_qwen3b
```

每个候选保存：

```text
模型名、prompt 版本、seed、temperature、原始响应、thoughts、code、解析状态
```

prompt 必须要求模型使用标准输入、禁止文件读写和交互式提示，并使用稳定的 `<thoughts>` 与 `<code>` 标记。

验收：20 题 × 4 候选均有记录；解析失败率单独报告；不能静默丢弃候选。

### B2. 收集 public/private 反馈

对每个候选运行 public 和 private 测试，生成：

- `data/processed/feedback_records_apps_intro20_qwen3b.jsonl`；
- `outputs/executions/` 下的逐测试执行记录；
- `outputs/generations/` 下的原始生成结果。

soft label：private pass rate。  
binary label：private 是否全部通过，仅用于标签消融。

验收：随机抽查 20 条记录，标签能由 private 执行结果重新计算；public 反馈未混入 private 测试内容。

## 6. 阶段 C：轻量 CodePRM 和消融

目标：在真实 APPS 反馈上验证“加入代码和执行反馈是否比普通 PRM 更有用”。已完成真实数据上的 Ridge 替身消融；神经 Transformer PRM 仍是条件任务。

### C1. 先完成当前环境可行的版本

第一轮不等待 Transformer 环境，直接使用：

- 题目 + 思路：normal PRM；
- 题目 + 思路 + 代码：code-only PRM；
- 题目 + 思路 + 代码 + public 反馈：CodePRM；
- CodePRM 的 soft/binary 标签对照。

训练集和测试集必须按题目分组，不能把同一道题的不同候选拆到两边。

验收：输出 train/test 误差、选择后的 pass rate、pass@1 和失败类型；样本过小时明确报告置信区间不稳定，而不是只报告单个高分。

### C2. 神经 PRM 的条件路线

如果 C1 结果支持继续投入，再单独建立 WSL2/Linux 的 Python 3.10/3.11 环境，安装 Transformers、Datasets、PEFT 等依赖。先尝试小型 backbone 的 LoRA/QLoRA；不要覆盖 Ridge 结果。

7B 全量微调在当前 8GB 显存上不作为承诺。若必须复现论文 backbone，需要外部 GPU 或远程训练环境，并单独记录成本和版本。

## 7. 阶段 D：GVR 和扩大实验

目标：验证评分器是否能帮助定位低质量思路并提升最终代码通过率。已在同一真实候选池上完成池替换 GVR、一次 Qwen3B 模型驱动重写和 8-rollout 简化 MCTS；20 题 baseline 的 3 个 seed 复验已完成。

### D1. GVR

固定最多一次修正：

```text
定位低分思路步骤
→ Qwen3B 重写该步骤
→ 重新生成代码
→ 重新执行 public tests
→ public 分数提升才接受
```

同时保留“候选池替换版”作为无模型对照。保存修正前后思路、代码、分数、执行反馈和接受/拒绝原因。

验收：报告修正前后 pass rate、pass@1、平均修正次数和退化比例；至少整理 3 个成功案例和 3 个失败案例。

### D2. 规模扩大

按以下顺序扩大：

```text
20 题 → 50 题 → 100 题
```

每个规模至少运行 3 个 seed，报告均值、标准差和失败类型。每次只改变一个因素，不同时改变候选数、模型和 rollout。

验收：单题失败不会中断整批；中间结果可恢复；结果文件带有数据规模、模型和 seed 后缀。

### 有条件可以完成

- 更严格的执行隔离，需要 Docker/WSL 配置；

### 当前不能可靠承诺

1. **论文级 Qwen2.5-Coder-7B 神经 PRM 微调**：当前 8GB 显存和 Windows/Python 3.13 环境不适合直接完成；
2. **严格复现论文 Table 1**：缺少论文完全一致的数据、模型、训练配置和计算预算；

5. **无官方 public/private 划分时的严格比较**：可以做自定义评测，但不能把它标为论文协议。

这些任务不是项目失败，而是应当降级、延期或转移到外部环境，避免产生不准确结论。

## 9. 预期结果和研究作用

### 9.1 工程层面的预期产出

完成阶段 A-D 后，项目应至少产生：

- 固定版本的真实 APPS 20/50/100 题 split；
- 每题多个候选的原始响应、思路、代码和执行反馈；
- normal PRM、code-only PRM、CodePRM 的对照表；
- soft label 与 binary label 的消融结果；
- GVR 修正前后结果和成功/失败案例；
- 多 seed 的均值、方差和失败类型统计；
- 一套从数据、生成、执行、训练到评估的可重跑命令。

### 9.2 研究层面的预期结论

不预先承诺具体提升数值，但应检验以下方向：

1. 加入代码和 public 执行反馈后，评分器是否比只看题目和思路更能识别高质量候选；
2. soft pass-rate 标签是否比 binary 标签提供更稳定的排序信息；
3. public 选择是否比 first/random 选择提高 private pass rate 或 pass@1；
4. GVR 修正的收益是否超过修正导致的退化；
5. Qwen3B 的候选质量是否足以支撑后续 PRM 训练。

如果某项没有提升，也应视为有效结果：它可以定位问题在候选生成、测试划分、反馈格式、评分器容量还是 GVR 接受规则。

### 9.3 对后续研究的作用

完成这条路线后，可以回答三个关键问题：

- 执行反馈是否确实提供了普通 PRM 没有的信息；
- 当前瓶颈是生成器质量还是过程评分器质量；
- 是否值得进一步投入 7B 神经 PRM、AST 或 FunPRM。

只有在 CodePRM 基线和失败类型稳定后，才进入 AST/FunPRM 扩展；否则结构特征实验无法判断收益来自哪里。

## 10. Go/No-Go 门槛

### Go：继续扩大实验

- 真实 APPS 20 题能稳定读取；
- 95% 以上候选能够解析并执行到明确状态；
- 没有 private 数据泄漏；
- 单题失败可恢复；
- 轻量 PRM 的消融可以重复运行。

### No-Go：暂停扩大，先修复协议

- public/private 划分无法解释；
- 解析失败率过高；
- 执行器无法清理超时进程；
- train/test 存在题目重叠；
- 结果只能依赖单个 seed；
- 生成代码大量使用文件或交互输入。
