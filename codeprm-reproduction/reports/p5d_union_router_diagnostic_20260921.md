# P5d 后验诊断：M0/F1 合并候选池的路由上限

日期：2026-09-21  
性质：使用既有 P5d 确认输出的后验诊断，不是新的确认性模型实验。

## 结论

M0 和 F1 的候选合并后，事后池上限从各自的 `12/19` 增加到 `13/19`，说明 F1 在 `apps-train-2714` 额外产生了一个 M0 没有的私有全通过候选。但只按公开测试分数在两池之间选择，实际私有通过仍为 `11/19`，没有超过单独 F1 的 `11/19`。

这给出了下一阶段的明确验收目标：评分器或路由器必须在不使用 private 的情况下，把合并池的选择结果从 `11/19` 提高到至少 `12/19`，否则它没有部署价值。当前数据只能证明“候选池里还有一点潜力”，不能证明训练评分器一定能把潜力兑现。

## 诊断规则

- 把同一道题的 M0 和 F1 候选合并；
- 只看每个候选的 public pass rate；
- 公开分数相同，固定优先 M0，再按候选序号升序；
- 选择冻结后，才读取既有 pool oracle 的 private 结果；
- private 只用于事后统计，不改变任何原始候选或正式选择结果。

因此这是一个“公共选择能否找到已有正确答案”的诊断，不是新的模型生成实验。

## 结果

| 指标 | 结果 |
| --- | ---: |
| M0 pool oracle | 12/19 |
| F1 pool oracle | 12/19 |
| M0 ∪ F1 pool oracle | 13/19 |
| M0/F1 合并后 public-only 路由的 selected private | 11/19 |
| 合并路由选择 M0 | 17/19 |
| 合并路由选择 F1 | 2/19 |

唯一新增池上限题是 `apps-train-2714`：M0 没有 private 全通过候选，F1 有；合并路由在该题选到 F1，因此该题确实能通过公共测试被选中。另一方面，`apps-train-2728` 的两边池中都有 private 全通过候选，但合并路由优先 M0，仍然选错，说明公开测试与私有泛化之间存在选择误差。

## 对研究方向的影响

### 保持 RL No-Go 的含义

当前不启动 RL，意思是：现有独立分解与组合管线还没有稳定正向信号，直接训练只会把未经验证的失败机制优化得更复杂。这个 No-Go 是一个阶段性门槛结论，不是“所有 RL 或所有函数化方法都无效”。

### 优先方向及预期结果

优先做完整函数化候选上的评分/路由，而不是继续增加独立组合数量。它有三种清晰结果：

1. **达到 `12/19` 或更高**：说明候选池已有可兑现信息，才值得做留出题和小规模监督/排序训练；
2. **仍为 `11/19`，但池上限保持 `13/19`**：说明生成池有潜力，瓶颈在 public 选择器，需要改进测试区分度或评分器；
3. **仍为 `11/19` 且新增池上限消失**：说明 F1 的额外候选不稳定，函数化路径应暂时收束。

本机没有比 `qwen2.5-coder:7b` 更强的代码模型，因此“更强模型只生成分解”当前无法做成公平的本地实验；不应拿更弱模型代替教师模型并把结果解释为教师隔离结论。

## 限制

- 这是单 seed、19 题、APPS custom split 的后验诊断；
- 路由规则在已有结果上分析，不能替代新留出题上的预注册确认；
- 合并池上限使用 private oracle，只能作为诊断上限，不能作为部署成绩；
- 结论仍不能升级为“函数化方法稳定有效”或“RL 普遍无效”。
