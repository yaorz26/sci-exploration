# P5b 困难 stdin seed42 离线 API 重验证

## 阶段目的

检验已有 M2a/M2b 输出是否会因当前 starter API/分解校验门而被错误保留或错误淘汰。该步骤只读取已有 JSONL，并重放确定性验证、公共候选选择和私有评测；不调用模型、不生成新分解、不修改正式 seed42 结果。

## 预先设定

- 范围：冻结困难 stdin 20 题，仅 M2a skeleton 和 M2b JSON。
- 输入：已有 seed42 分解与组合 JSONL，以及冻结的 `apps_stratified60_20260918.json`。
- 工具：`scripts/revalidate_modular_run.py`。
- 预算：2 次离线重验证；模型调用 0 次。
- 通过条件：若重验证改变候选形成率、公共选择或私有全通过，说明 API 门控可能是重要混杂；否则关闭该解释分支。

## 结果

| 方法 | 原始候选题数 | 重验证候选题数 | 原始选择后私有全通过 | 重验证选择后私有全通过 | 选中候选 ID 一致 |
| --- | ---: | ---: | ---: | ---: | ---: |
| M2a skeleton | 15/20 | 15/20 | 0/20 | 0/20 | 20/20 |
| M2b JSON | 13/20 | 13/20 | 0/20 | 0/20 | 20/20 |

重验证后的组合数和可组合数也未改变：M2a 为 `178/178`，M2b 为 `152/152`。两种方法的私有通过值均为 20/20 题一致。M2a 重验证识别 4 个无效分解，M2b 识别 5 个无效分解；这些记录在原始组合阶段已经没有改变候选选择，因此没有形成结果差异。

## 阶段审查

**状态：通过。** 预设的“若 API 门控造成结果差异则继续诊断”条件未满足；离线 API 重验证不能解释困难层 M2 的 No-Go，也不能提高池 oracle。

## 方向审查

- **拒绝：原样启动 seed43。** 不修复已识别的结构瓶颈，信息增益低且不能改变当前 RL 决策门。
- **拒绝：直接启动 RL。** 困难层 M2 仍未超过 M1，且池 oracle 为 0/20。
- **保留：协议修改后的 3--5 题未评分审计。** 只有明确修改提示、输出协议或实现池策略后，该审计才有可区分的新问题。

## 限制

这是对现有 seed42 输出的离线重放，不估计新协议、新模型或新 seed 的性能；正式结果和成员资格均未改变。
