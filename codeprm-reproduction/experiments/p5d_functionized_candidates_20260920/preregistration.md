# P5d 预注册：完整函数化候选、独立重组与直接生成

创建时间：2026-09-20
状态：**试跑前冻结**。本文件冻结试跑和确认集、方法定义、隔离规则与预算换算；试跑结果不能用于调整确认集成员或私有评测口径。

## 1. 研究问题

本实验要区分两个经常被混在一起的问题：

1. 函数结构本身能否帮助模型生成和选择完整程序？
2. 如果把函数分别生成再交叉组合，是否会因为接口和组合成本抵消函数结构的潜在收益？

对应三条路线：

- **M0 direct**：直接生成一份完整程序；
- **F1 functionized**：一次生成一份完整程序，但要求它按多个顶层函数组织，并由入口函数统一编排；
- **M2a modular**：先生成函数骨架，再分别实现函数，最后从实现池组合完整程序。

F1 是 FunPRM 风格的结构化候选生成对照，不是 FunPRM 的完整复现：本地不训练 PRM，只比较函数化完整候选和独立重组的差异。

## 3. 冻结模型与提示

- 模型：`qwen2.5-coder:7b`，本地 Ollama，Q4_K_M；
- seed：42；
- public/private：沿用已冻结的 custom split；private 只在 public 选择冻结后访问；
- 每测试超时：10 秒；确认集候选总预算沿用现有 runner 的显式参数；
- M0/F1：使用 `src/whole_program.py`；
- M2a：JSON 分解，`repair_v1` 实现提示，允许嵌套函数（A1），不允许未声明依赖和前向依赖；
- M2a 的允许嵌套规则只放宽实现解析与组合，不改变函数签名、入口或依赖验证；结果中单独记录 `allow_nested_functions=true`；
- F1 不允许分阶段独立响应：所有 helper 和入口函数必须出现在同一份完整程序中；
- 任何 prompt 在开发试跑后不得因 private 结果而修改。若试跑发现代码级 bug，只能修复 runner/解析 bug，并在报告中披露。

## 4. 开发试跑

开发试跑固定为 5 题，三臂均运行：

- M0：每题 2 份完整程序；
- F1：每题 2 份完整函数化程序；
- M2a：每题 2 份分解、每个函数 2 个实现、每份分解最多 8 个组合。

试跑只检查：

1. F1 是否能稳定生成至少一个完整、入口签名正确的程序；
2. M2a A1 是否能正常组合并记录嵌套实现；
3. 三臂是否都能断点续跑、只在选择后访问 private；
4. 每臂的 output token、调用数和失败类型，用于冻结确认集的等预算换算。

如果试跑发现 F1 的解析实现错误，修复后从 5 题重新开始；如果只是模型生成质量差，不改提示、不重试新 prompt，按失败结果记录并停止扩展。

## 5. 确认集预算换算

确认集预算以**模型 output token**为主，prompt token、模型时长和执行时长另报，不把它们混在主指标里。

试跑结束后，只使用三臂的 `eval_count` 和生成请求数计算每次请求的平均 output token，不查看任何 private 结果。以 M2a 试跑的每题总 output token 作为目标预算 `B`，再按以下公式冻结完整程序候选数：

```text
n_M0 = max(2, round(B / M0 每份完整程序平均 output token))
n_F1 = max(2, round(B / F1 每份完整程序平均 output token))
```

`n_M0` 和 `n_F1` 在确认生成前写入独立的 `budget_manifest.json`，确认阶段不得调整。M2a 保持 `decompositions=2`、`implementations=2`、`max_combinations=8`，并完整披露其分解/实现请求成本；若三臂无法在整数请求下完全等 token，只报告“近似等 output-token 预算”，同时给出实际 token 差异。

冻结结果：M2a 试跑为 `971.2 output token/题`；M0 为 14 候选/题（估计 961.8 token/题），F1 为 10 候选/题（估计 986.0 token/题）。详细计算见 `budget_manifest.json`。

## 6. 选择与评测

- 选择只看 public pass rate；同分按固定候选顺序；
- M0/F1 的 tie-break：候选序号升序；
- M2a 的 tie-break：分解序号、组合序号升序；
- private 只用于选择冻结后的最终评测和事后 pool oracle；
- private 测试不得进入 prompt、分解成员资格、候选数量、预算换算、阈值或人工审查。

主指标：

1. 选择后 private 全通过题数；
2. private pool oracle 全通过题数。

次要指标：候选形成率、完整程序解析率、函数实现有效率、public tie rate、public/private 通过率、输入/输出 token、模型调用数、模型时长、评测执行数、预算耗尽数和接口错误分类。

## 7. 事先判读规则

- F1 若在选择后 private 和 pool oracle 两个指标上都高于 M0，且实际 output token 不超过 M0 的 1.5 倍，记为“完整函数化候选出现正向信号”；
- M2a 若不高于 F1/M0，但 F1 高于 M0，说明函数结构可能有用，独立重组是主要损失；
- F1 和 M2a 都不高于 M0，说明当前模型/题目/函数粒度没有形成可复用的正向结构信号；
- 19 题单 seed 只作机制诊断，不升级为稳定性结论，也不直接触发 RL。

无论正负，都报告三臂结果和成本，不删除失败臂。

## 8. 停止条件与后续门

- 开发试跑无法稳定解析完整候选或组合器出现代码级错误：停止，先修复工程；
- 任何 private 泄漏或选择顺序不一致：停止并作废当前运行；
- 试跑仅显示模型质量差但流程正确：不调 prompt 追正，按冻结规则记录；
- 只有 F1 在确认集出现正向信号后，才考虑训练函数级评分器；
- 只有分解器/路由器在留出题目上有正向信号后，才重新讨论 RL。
